# #14 — Восстановление истории JSON: offline preparation

Сделано: stdlib helper `scripts/recover_history.py` объединяет два и более JSON
без запуска приложения, сети или БД. Источники задаются от старого к новому,
current — последним. Дедупликация по `(series, UTC instant)`, последняя запись
побеждает; пары сохраняют исходные timestamp и percent, сортируются хронологически.
Есть строгая валидация формы, дат, finite percent 0..100, duplicate JSON members,
dry run, atomic output, read-only sources и private snapshots с SHA256 manifests.
Невалидный input не создаёт merged output и не заменяет уже существующий.

Все восемь источников (daily 03–09 октября и root current последним) сохранены
в отдельном private каталоге; его путь и hash объединённого файла переданы
интегратору письмом, в git нет исходных данных или manifest. Snapshots — байты
прочитанной версии, а не обещание единого атомарного снимка работающего daemon.
При невалидном input snapshots остаются для расследования, merged не записывается.
Snapshot directory должен быть новым; существующий каталог не перезаписывается.

Тесты проверяют epoch / ISO Z / UTC offset, unordered points, duplicates,
оба направления приоритета источников, fractional percent, пустые series/object,

точные snapshot bytes/hash, повторяемые output bytes, dry run без output,

Probe временно подменяет только `merge` в памяти тестового процесса:
старые источники исключены → assertion о полном chronological union красный →
исходная функция возвращена через `finally` → все четыре теста зелёные.
Тесты не удалялись и не ослаблялись, implementation/source files не меняются пробой.

percent до integer и создаёт inferred cycles по падению percent. JSON не содержит
endpoint reset facts: такой факт из восстановленных cycles не заявляется.
