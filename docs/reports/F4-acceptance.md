## 2. Свежий клон собирается по тегам — ДА, с двумя условиями

`git clone https://github.com/unitcraft/claude-limits.git` в пустой каталог (HEAD `5caf80f`),
`NOVA_HOME` и `NOVA_CACHE` — новые ПУСТЫЕ каталоги, `./nova.sh build src/claude_limits.nv -o
target/claude-limits.exe` через Git Bash:

```
built: target/claude-limits.exe (190.23s)
binary: 65672192
fetched into the empty NOVA_HOME: nova-compress, nova-duckdb, nova-http, nova-polaris, nova-tls
```

Все пять пакетов скачаны из сети в пустой кэш по коммитам lock — ни локального кэша, ни
соседних каталогов для них. Предупреждения — только ожидаемые `[new-then-cap]` nova-compress
(README их называет).

**Условие 1 — duckdb по пути, как велит README шаг 3.** Нативная библиотека DuckDB строится
час и живёт в чекауте пакета, поэтому `nova.override.toml` указывает на
`../nova-duckdb`. Проверено, что чекаут стоит РОВНО на теге: `HEAD 674b12aac == v0.2.2`,
изменённых отслеживаемых файлов нет. Это и есть рецепт пользователя, а не обход.

**Условие 2 — `core.longpaths=true` на время прогона**, передан окружением git
(`GIT_CONFIG_COUNT`), глобальный конфиг не тронут. Причина — глубина МОЕГО каталога, а не
продукт: `NOVA_HOME` в песочнице сессии — 116 символов, каталог checkout на 79 длиннее, и
файлы пакетов переходят 260. Без него резолв падал (сперва на nova-compress, при 129; потом на
nova-duckdb, при 115). У пользователя `~\.nova` — около двух десятков символов, до предела
далеко. **Найдено по дороге:** отказ git при этом не назван в выводе `nova build` вовсе —
проба `probes/dep-error-drops-git-cause/` (контроль: с `core.longpaths=true` резолв проходит).
