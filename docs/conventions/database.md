# Конвенция по организации базы данных

**Статус:** ПРИНЯТА 2026-09-06, редакция 2. Общая для любого проекта, который хранит данные в
реляционной базе — встраиваемой (SQLite, DuckDB) или серверной (PostgreSQL). Правила сформулированы
независимо от движка; где движки различаются, стоит примечание «Движки». Проект, применяющий
конвенцию, ссылается на неё из документа своей схемы и ведёт там раздел «Отклонения» (§16).

**Нарушение конвенции — блокер ревью.** Ревьюер обязан вернуть изменение, в котором появилась
колонка момента без суффикса `_at`, статус кириллицей, деньги во `float`, перечисление нативным
`ENUM` или таблица без служебных колонок. Единственный законный способ отступить — записанное и
отревьюенное отклонение (§16); «локально в этом модуле», устная договорённость и комментарий в коде
отклонением не считаются.

Правила выбраны так, чтобы **не требовать предсказаний на старте**: не нужно заранее знать, будет ли
у системы один процесс или несколько, один источник записей или много, один автор или сотня. Форма
одна для всех случаев; там, где более простой вариант мог бы сработать «пока», он не предлагается,
потому что переход с него потом дороже, чем правило с первого дня.

Каждое правило устроено одинаково: **правило и причина · схема · API · правильно / неправильно**,
чтобы проверка на ревью была механической и не требовала чтения бизнес-логики.

## 1. Время

**Правило.** Момент времени хранится и передаётся **только в UTC**. Колонка момента называется с
суффиксом **`_at`**: `created_at`, `occurred_at`, `expires_at`, `synced_at`. Локальное время
существует только на экране; пояс берётся из профиля пользователя, по умолчанию — из настройки
приложения. Если предметной области нужен «местный» пояс объекта (склад, филиал, устройство), он
хранится отдельным полем с идентификатором IANA (`Asia/Yekaterinburg`), а не вшивается в момент.
На всех серверах — NTP.

Почему. Данные приходят из разных источников и поясов: внешние API отдают время со смещением,
серверы и клиенты живут в своих поясах, один и тот же экран открывают из разных городов. Если каждый
компонент запишет «своё» локальное время, события из разных мест перестают быть сравнимыми: товар
«использован» за три часа до того, как «выдан». Единый UTC плюс синхронизированные часы убирают этот
класс ошибок целиком. Суффикс в имени делает намерение автора видимым в ревью без чтения кода.

**Схема.** Тип момента **с поясом**; сессия БД работает в UTC. Тип без пояса запрещён: он молча
теряет смещение и превращает ошибку в невидимую. Точность — секунды или доли секунды по потребности.

Движки: PostgreSQL — `timestamptz`, DuckDB — `TIMESTAMPTZ`; сессионный параметр пояса — `UTC`. SQLite
не имеет типа времени: хранить `INTEGER` секунд Unix UTC, колонка всё равно `_at`, и это записано как
отклонение (§16) с представлением `datetime(x, 'unixepoch')` для чтения человеком.

**API.** ISO 8601 **с обязательным суффиксом `Z` и без смещения**: `"2026-08-01T09:00:00Z"`; точность
до секунды или до миллисекунды, оба варианта допустимы, но один на весь API. Смещения вида `+03:00` в
исходящих значениях не используются. Входящее значение со смещением сервис **принимает и нормализует**
в UTC, а не отвергает — это упрощает жизнь внешним интеграциям.

Правильно: `issued_at TIMESTAMPTZ NOT NULL` → `"issued_at": "2026-08-01T09:00:00Z"`.
Неправильно: `issued_date TIMESTAMP NOT NULL` (нет пояса, нет суффикса); `"issued_at":
"2026-08-01T12:00:00+03:00"` (смещение в исходящем контракте); `"issued_at": "01.08.2026 12:00"`.

## 2. Календарные даты

**Правило.** Если сущность календарная по природе — дата акта, дата поставки, день свёртки, — это
**дата, а не полночь какого-то пояса**. Такие колонки называются с суффиксом **`_on`**:
`signed_on`, `delivery_on`, `day_on`.

Почему. У даты нет пояса: акт подписан первого числа и в Москве, и в Екатеринбурге. Дата, записанная
моментом `00:00`, при показе в другом поясе съезжает на сутки — одна из самых частых и самых обидных
ошибок учётных систем. Разные суффиксы (`_at` — момент, `_on` — дата) делают ошибку видимой в имени.

**Схема.** Тип `DATE`. Если дата вычисляется из момента (день свёртки, отчётный день), документ схемы
называет пояс усечения и хранит его в метаданных базы; смена пояса — пересчёт производных дат, а не
тихая порча.

**API.** Строка `YYYY-MM-DD`, без времени, без `Z`, без смещения.

Правильно: `signed_on DATE NOT NULL` → `"signed_on": "2026-08-01"`.
Неправильно: `signed_at TIMESTAMPTZ` для даты подписания; `day TEXT` «как получится».

## 3. Идентификаторы и ключи

**Правило.** Первичный ключ таблицы — **UUID версии 7**, генерируется **приложением** единым
генератором из общей библиотеки. Не автоинкремент, не `SEQUENCE`, не UUID v4, не составные ключи в
роли первичного.

Почему UUID, а не последовательность. На старте не известно, будет ли у системы один процесс и один
источник записей; как только появляется второй — офлайн-клиент, агент синхронизации, второй контур,
импорт из соседнего экземпляра — последовательные номера требуют центральной выдачи, которой у
второго источника нет, и начинается перенумерация. UUID генерируется на месте создания, коллизий и
перенумерации нет никогда, а цена — 16 байт на ключ — предсказуема и одинакова для всех таблиц.

Почему версия 7, а не 4. UUID v7 начинается с временной метки, поэтому ключи **сортируемы по времени
создания**: вставки ложатся в конец B-tree индекса, а не разбрасываются по нему, как у случайного v4;
сортировка по `id` даёт порядок создания — ровно то, что нужно курсорной пагинации без дополнительного
поля; при разборе инцидента по идентификатору видно, когда запись появилась. Плата — идентификатор
раскрывает время создания; наружу ключи не показываются (§3.3), поэтому это приемлемо, а где нет —
поверх берётся отдельный публичный непрозрачный код.

**Схема.** Тип `UUID` (в SQLite — `BLOB(16)` или текст 36 символов, записано в §16). Значение
подставляет приложение; серверный `DEFAULT` для `id` **не ставится**, чтобы не появилось второго
источника идентификаторов. Естественная уникальность сущности — **отдельным `UNIQUE`** по
нормализованному атрибуту: `email`, `path`, `(device_id, channel)`. Нормализация закреплена `CHECK`
(`email = lower(email)`), чтобы дубликаты в разном регистре не могли появиться.

### 3.1. Факты и временные ряды

Таблица фактов (замер, показание, событие с фиксированным источником) тоже получает `id UUID v7` как
первичный ключ и **обязательный `UNIQUE (измерение, момент)`** — `(sensor_id, measured_at)` — как
естественный ключ, по которому идут идемпотентные вставки (§11) и запросы по диапазону. Единый вид
ключа для всех таблиц дороже составного на 16 байт на строку, но избавляет от второго правила
пагинации, второго правила ссылок и второго правила удаления; для рядов в сотни тысяч строк это
мегабайты, для рядов в миллиарды — вопрос, который решается партиционированием, а не другим ключом.

### 3.2. Ключи внешних систем

Идентификаторы записей внешних систем (номер в учётной системе, код в CRM, ключ у внешнего провайдера)
**не кладутся в поля наших сущностей**. Для них — отдельная таблица соответствий
`external_ref (id, entity_type, entity_id, system, external_key)` с `UNIQUE (system, external_key)` и
`UNIQUE (entity_type, entity_id, system)`. Тогда у одной сущности может быть несколько внешних
соответствий, смена внешней системы не ломает нашу схему, а внешний ключ не становится нашим.
Атрибут, который является **свойством самой сущности** (почта пользователя, путь каталога), остаётся
атрибутом с `UNIQUE` и нормализацией — это не ключ внешней системы.

### 3.3. В API

Идентификатор — строка UUID в каноническом виде, нижним регистром, с дефисами. Версия проверяется
только у **наших** идентификаторов; идентификаторы субъектов из внешних систем аутентификации
описываются как UUID любой версии. Пользователю первичный ключ не показывается: человеку — номер или
название сущности со своей нумерацией; идентификатор живёт в адресе страницы и технических панелях.

Правильно: `id UUID PRIMARY KEY` (значение из общей библиотеки), `email VARCHAR NOT NULL UNIQUE CHECK
(email = lower(email))`; `UNIQUE (sensor_id, measured_at)` у ряда.
Неправильно: `id BIGSERIAL PRIMARY KEY`; `id UUID DEFAULT gen_random_uuid()` (v4 и второй источник);
`crm_code VARCHAR(30)` прямо в сущности; составной первичный ключ вместо `id` + `UNIQUE`.

## 4. Перечисления и статусы

**Правило.** Значения перечислений — **латиницей в `snake_case`** в базе, в API, в событиях и в коде:
`in_progress`, `awaiting_acceptance`, `http_429`. Русских значений и числовых кодов в данных нет;
перевод — на стороне интерфейса, **один словарь на приложение**, а не перевод по месту.

Почему. Статус — техническое значение, по которому строятся логика, фильтры и индексы. Кириллица в
данных приносит вопросы регистра, буквы «ё» и пробелов, а переименование статуса на экране
превращается в миграцию данных. Числовой код нечитаем в логах и ломается при перенумерации.

**Схема.** **`VARCHAR` с `CHECK (col IN (...))`, не нативный тип-перечисление.** Добавить значение в
нативный `ENUM` — это `ALTER TYPE`: в PostgreSQL он плохо живёт в транзакционных миграциях, в DuckDB
невозможен вовсе (тип и все колонки пришлось бы пересоздать), в SQLite нативных перечислений нет.
`VARCHAR` + `CHECK` меняется обычной миграцией и откатывается без сюрпризов; словарное сжатие
колоночных движков делает его таким же компактным. **Полный перечень значений каждого списка живёт в
одном месте документа схемы**; `CHECK` в DDL — его копия, тест сверяет их с кодом. Справочная таблица
уместна для открытых, редактируемых пользователем списков (категории, теги) и для статусной модели,
которую администрирует бизнес; для закрытых технических списков — `CHECK`.

**API.** Та же строка: `"status": "awaiting_acceptance"`. Перечень значений — часть контракта;
добавление значения согласуется с потребителями, удаление — ломающее изменение.

Правильно: `status VARCHAR(32) NOT NULL CHECK (status IN ('draft','in_progress','accepted','rejected'))`.
Неправильно: `status ENUM(...)`; `"status": "В работе"`; `"status": "InProgress"`; `"status": 3`.

## 5. Скалярные типы

- **Логические** — `BOOLEAN`, не `0/1`, не `'Y'/'N'`, не `NULL` как «ложь».
- **Деньги** — `DECIMAL(p, s)` с валютой отдельным полем (ISO 4217), никогда `DOUBLE`/`FLOAT`; в API —
  строка `"1234.50"`, а не число, чтобы клиент не потерял копейки в плавающей точке.
- **Количества** — `DECIMAL` с явной точностью; единица измерения — отдельным полем или в имени
  (`weight_kg`, `duration_sec`), а не «подразумевается».
- **Проценты** — целые с `CHECK (x BETWEEN 0 AND 100)`, если источник даёт целые; иначе `DECIMAL`.
- **Плавающая точка** допустима только для измерений, где погрешность — часть природы данных
  (координаты, латентность, сенсоры).
- **Строки** — `VARCHAR` без искусственных ограничений длины, кроме перечислений (§4); ограничение
  смысла — через `CHECK`, а не через длину. `NOT NULL` по умолчанию; `NULL` — только где отсутствие
  значения честно возможно, и никогда пустая строка вместо `NULL`.
- **ФИО** — три поля `last_name`, `first_name`, `middle_name NULL`; собранное «Иванов И. И.» —
  вычисляемое представление. **Адрес** — структурно, по полям. И то и другое — ПДн (§13).
- **Телефоны** — нормализованная строка E.164 (`+79161234567`); форматирование — на экране.
- **Длительности** — целые с единицей в имени (`_sec`, `_ms`); интервал «от–до» — две колонки
  моментов (§7), а не начало плюс длительность.
- **JSON** — только для полей с заведомо разной формой (payload события, сырой ответ внешней
  системы); всё, по чему фильтруют, сортируют или считают, лежит колонками.
- **Двоичные данные** — в объектном или файловом хранилище, в базе — ключ и контрольная сумма.
- **Секреты и токены** — в базе не хранятся ни в каком виде (§14).

## 6. Обязательные колонки

**Правило.** Каждая таблица предметной области содержит **один и тот же служебный набор**, без
исключений по классам и без предсказаний «здесь авторов не будет»:

- `id UUID PRIMARY KEY` — v7, из приложения (§3);
- `created_at TIMESTAMPTZ NOT NULL` — момент создания записи;
- `updated_at TIMESTAMPTZ NOT NULL` — момент последнего изменения, обновляется при каждом;
- `deleted_at TIMESTAMPTZ NULL` — мягкое удаление там, где оно уместно (§8);
- `created_by UUID NOT NULL`, `updated_by UUID NOT NULL` — **субъект изменения**: идентификатор
  человека из проверенного токена, identity сервиса или агента. Для записей, которые создаёт сам
  процесс без человека, пишется identity этого процесса, а не «системный ноль»: при расхождениях
  между экземплярами иначе невозможно понять, кто внёс запись.

Почему один набор. Без него невозможны разбор инцидента («кто и когда это поменял»), курсорная
пагинация, восстановление ошибочно удалённого. Набор по классам таблиц («здесь автор не нужен»)
требует угадать будущее: второй автор появляется вместе с первым интерфейсом или первым агентом, и
тогда колонки добавляются задним числом без истории. Дополнительные доменные моменты — `first_seen_at`,
`last_seen_at`, `synced_at` — добавляются **сверх** набора, а не вместо него.

**Служебные таблицы механизмов** (ключи идемпотентности, обработанные события, outbox, метаданные схемы,
staging) этот набор не соблюдают: это не учётные записи предметной области. Их форма задана в §11 и в
документе схемы, список **закрыт**, пятая такая таблица — через §16.

## 7. Интервалы и открытые записи

**Правило.** Интервал — две колонки моментов `started_at`/`ended_at`, конец `NULL`, пока идёт;
`CHECK (ended_at IS NULL OR ended_at >= started_at)` обязателен. Переход состояния — **закрыть старую и
открыть новую** запись в одной транзакции, а не `UPDATE` существующей: история остаётся полной, и
«кто когда» строится без догадок.

Если у сущности «сейчас» может быть только один открытый интервал (одна открытая смена на сотрудника,
одна активная запись на каталог), инвариант **«не больше одной открытой записи»** держится частичным
уникальным индексом:

```sql
CREATE UNIQUE INDEX shift_open_uidx ON shift (employee_id) WHERE ended_at IS NULL AND deleted_at IS NULL;
```

Движки: PostgreSQL и SQLite частичные индексы дают; DuckDB — нет. Где движок не даёт, инвариант держит
единственный владелец записи в одной транзакции, а тест проверяет запросом `SELECT key FROM t WHERE
ended_at IS NULL GROUP BY key HAVING count(*) > 1` → пусто. Это отклонение записывается в §16.

## 8. Удаление

**Правило.** Всё, что участвует в учёте или на что ссылаются другие записи, **не удаляется
физически**: у него `deleted_at`, и **каждая выборка текущего состояния фильтрует `deleted_at IS
NULL`**. Забытый фильтр — типичная причина «удалённое снова появилось в отчёте». Одно поле для всех
случаев: и «пользователь удалил», и «сущность исчезла из источника» — это `deleted_at`; причина, если
она нужна, — отдельным атрибутом `deleted_reason` с перечислением (§4), а не вторым полем момента.

Два следствия:

1. Уникальные индексы у мягко удаляемых таблиц — **частичные**, `WHERE deleted_at IS NULL`, иначе
   удалённая запись навсегда блокирует повторное использование своего кода. Где движок частичных
   индексов не даёт — уникальность держит код, и это записано в §16.
2. Физическое удаление — только для журналов и кэшей по ретенции (§12), для служебных таблиц
   механизмов и там, где этого требует законодательство о персональных данных (право на удаление,
   §13.6): такие команды описаны в документе схемы с порядком удаления зависимых строк и покрыты
   тестом.

На каскады базы не полагаться даже там, где они есть: порядок удаления зависимых строк записан явно,
чтобы схема пережила смену движка (DuckDB `ON DELETE`-действий не поддерживает). История, которая
принадлежит не удаляемой сущности, а её окружению, при удалении **теряет ссылку, а не строку**.

## 9. Именование

| что | шаблон | пример |
|---|---|---|
| база данных | `<система>_<модуль>` | `karkas_works` |
| схема с персональными данными | `pdn` внутри БД | `karkas_tmc.pdn` |
| таблица | `snake_case`, **единственное число**, по сущности | `account`, `login_dir`, `measurement` |
| колонка | `snake_case`; момент `_at`, дата `_on`, ссылка `<таблица>_id`, длительность с единицей `_sec`/`_ms`, флаг — прилагательное или причастие (`locked`, `active`), без префикса `is_` | `measured_at`, `day_on`, `sensor_id`, `retry_after_sec` |
| индекс | `<таблица>_<колонки>_idx`, уникальный — `_uidx` | `shift_open_uidx` |
| ограничение | `<таблица>_<колонки>_<uq\|ck\|fk>` | `limit_window_account_kind_model_uq` |
| представление | `v_<что показывает>` | `v_current_occupancy` |
| промежуточная таблица | `stage_<цель>` | `stage_measurement` |
| значение перечисления | `snake_case` латиницей | `awaiting_acceptance` |
| тип события | `<модуль>.<сущность>.<действие в прошедшем времени>` | `tmc.issue.completed` |
| переменная окружения | `<СИСТЕМА>_*`, SCREAMING_SNAKE_CASE | `KARKAS_DB_DSN` |
| миграция | `NNNN_<что_делает>`, четыре цифры, сквозная нумерация | `0001_init` |

Сокращения — только общепринятые (`id`, `sec`, `ms`, `tz`, `dir`, `url`); `usr`, `cnt`, `dt` — нет.
Зарезервированные слова движка в имени колонки запрещены даже в кавычках (`at`, `user`, `order`,
`end`): `measured_at`, `app_user`, `purchase_order`, `ended_at`.

## 10. Запись данных

- **Транзакция на единицу работы.** Одна бизнес-операция — одна транзакция: журнал, факты, переходы
  интервалов, обновления справочников, запись в outbox (§11) — вместе. Половинчатого состояния на диске
  не бывает.
- **Массовая запись — массовым путём.** Аналитические (колоночные) движки медленны на построчном
  `INSERT` (DuckDB: около 2 мс на строку); ряды пишутся пакетом (Appender, `COPY`) в `stage_*` и
  переносятся одним `INSERT … SELECT`. Точечный `UPDATE` допустим, когда строк единицы.
- **Параметры, не конкатенация.** Любой SQL с данными — через параметризованный запрос; склейка строк
  запрещена без исключений. Имена таблиц параметром не передаются — они из закрытого списка в коде.
- **Один владелец соединения на встраиваемых движках**: соединение принадлежит одному потоку или
  файберу, остальные общаются с ним сообщениями; привязка закреплена типом, где язык это умеет. На
  серверных движках — пул с лимитом и таймаутом ожидания, не «по соединению на запрос».
- **Checkpoint после записи**, если движок пишет журнал отдельно от файла: на диске всегда целостная и
  копируемая база.
- **`updated_at` и `updated_by`** обновляются в той же операции, что и данные — триггером или слоем
  доступа, но не «когда вспомнили».

## 11. Идемпотентность и надёжная доставка

Повтор — нормальное событие, а не сбой: клиент повторил запрос после таймаута, брокер доставил
сообщение дважды, агент синхронизации перезапустился посреди пакета. Схема обязана делать повтор
безвредным на трёх уровнях.

### 11.1. Идемпотентная запись

- Справочники и сущности пишутся `INSERT … ON CONFLICT (<естественный UNIQUE>) DO UPDATE SET …,
  updated_at = excluded.updated_at, updated_by = excluded.updated_by` — повторный импорт той же
  записи не создаёт дубликат и не роняет транзакцию.
- Факты и ряды — `INSERT … ON CONFLICT (измерение, момент) DO NOTHING` — повторная доставка того же
  замера безвредна.
- Переходы интервалов (§7) — по условию «открытая запись отличается», а не «пришло событие».

### 11.2. Ключ идемпотентности входящих команд

Каждая изменяющая команда извне (HTTP-запрос, сообщение) несёт **ключ идемпотентности**, который
клиент генерирует один раз на операцию (UUID) и повторяет при ретраях. Сервер хранит его в служебной
таблице и на повтор отдаёт **тот же ответ**, не выполняя операцию второй раз:

```sql
CREATE TABLE idempotency_key (
  key           UUID PRIMARY KEY,                 -- от клиента
  actor         VARCHAR NOT NULL,                 -- издатель токена + субъект: чей ключ
  request_hash  VARCHAR NOT NULL,                 -- хэш тела: тот же ключ с другим телом → 422
  response_code SMALLINT NOT NULL,
  response_body JSON,
  created_at    TIMESTAMPTZ NOT NULL,
  expires_at    TIMESTAMPTZ NOT NULL              -- окно хранения; по истечении строка удаляется ретенцией
);
```

Проверка ключа и выполнение операции — **в одной транзакции** с записью результата; окно хранения
записано в настройках и зависит от того, как долго клиент может повторять (офлайн-клиенты — дольше).

### 11.3. Дедупликация потребителя событий

Потребитель события хранит идентификаторы обработанных событий и пропускает повтор:

```sql
CREATE TABLE processed_event (
  event_id     UUID PRIMARY KEY,
  consumer     VARCHAR NOT NULL,                  -- имя потребителя: одно событие, несколько потребителей
  processed_at TIMESTAMPTZ NOT NULL,
  UNIQUE (event_id, consumer)
);
```

Запись в `processed_event` — в той же транзакции, что и эффект обработки; иначе сбой между ними даёт
либо потерю, либо дубль.

### 11.4. Transactional outbox для исходящих событий

Событие о факте пишется **в ту же транзакцию, что и сам факт**, в таблицу `outbox`; отдельный
процесс читает `outbox`, публикует в брокер и помечает отправленное. Публиковать из бизнес-транзакции
напрямую в брокер запрещено: сбой между коммитом и публикацией теряет событие, сбой между
публикацией и коммитом рождает событие о факте, которого нет.

```sql
CREATE TABLE outbox (
  id           UUID PRIMARY KEY,                  -- v7: порядок публикации = порядок создания
  event_type   VARCHAR NOT NULL,                  -- <модуль>.<сущность>.<действие>
  aggregate_id UUID NOT NULL,                     -- ключ маршрутизации / партиции
  payload      JSON NOT NULL,                     -- envelope события целиком
  created_at   TIMESTAMPTZ NOT NULL,
  published_at TIMESTAMPTZ NULL                   -- NULL = ждёт публикации
);
CREATE INDEX outbox_pending_idx ON outbox (created_at) WHERE published_at IS NULL;
```

Опубликованные строки удаляются ретенцией (§12). Потребитель обязан быть идемпотентным (§11.3): outbox
гарантирует «хотя бы один раз», ровно-один-раз даёт пара outbox + дедупликация.

### 11.5. Что проверяет тест

Каждая изменяющая операция имеет тест «дважды подряд»: второй вызов не меняет состояние и отвечает так
же; каждый потребитель — тест «то же событие дважды»; каждая транзакция с outbox — тест с инъекцией
сбоя между записью факта и публикацией: факт и событие либо оба есть, либо обоих нет.

## 12. Ретенция и свёртки

- У каждого ряда, журнала и служебной таблицы **записан срок хранения**, срок — в настройках, не в
  коде. Сущности и интервалы, нужные истории, хранятся без срока.
- Дневные (или иные) свёртки делаются **до** удаления сырья за период, одной операцией `INSERT …
  SELECT … ON CONFLICT DO UPDATE`. Свёртки за ещё хранящееся сырьё **не материализуются** там, где
  движок считает их достаточно быстро: материализованная копия — второй источник истины.
- Свёртка привязана к календарному дню в **записанном** поясе (метаданные базы); смена пояса —
  пересчёт свёрток за хранящееся сырьё и обновление записи, а не тихий разъезд старых и новых дней.
- Удаление по ретенции — `DELETE` по колонке момента порциями, затем checkpoint; `VACUUM` или
  пересборка файла — по факту разрастания, а не по расписанию.
- `idempotency_key` по `expires_at`, `processed_event` и `outbox` по окну, записанному в настройках,
  — та же ретенция.

## 13. Персональные данные (ПДн)

**Правило.** Персональные данные — всё, что прямо или в сочетании указывает на человека: ФИО, почта,
телефон, адрес, дата рождения, документы, идентификаторы во внешних системах, фотографии, точная
геопозиция, а также технические следы, привязанные к человеку (IP-адрес, идентификатор устройства,
пути домашних каталогов с именем пользователя). **Каждая такая колонка помечена в документе схемы**
(`pdn: yes`, категория, законное основание обработки, срок хранения). Колонка без пометки считается
не-ПДн, и ревьюер обязан это оспорить, если видит почту или телефон.

Почему отдельным разделом. Утечка ПДн — юридическая ответственность, а не только инцидент; требования
регулятора (законодательство о персональных данных в России, GDPR в ЕС) диктуют изоляцию, учёт,
сроки и право на удаление. Эти требования нельзя «добавить потом»: они меняют схему, роли доступа,
логи и бэкапы. Поэтому они входят в конвенцию схемы наравне с типами.

### 13.1. Минимизация

Хранится **только то, что нужно для функции**, и не дольше, чем нужно. Почта нужна как ключ учётки —
хранится почта; ФИО, телефон и адрес для этой функции не нужны — не запрашиваются и не хранятся, даже
если внешний источник их отдаёт. Каждое ПДн-поле в документе схемы отвечает на вопрос «для какой
функции»; поле без ответа удаляется.

### 13.2. Изоляция

ПДн лежат в **отдельной схеме `pdn`** (или отдельных таблицах с префиксом `pdn_` там, где движок схем
не имеет), связанных с основными сущностями по `id`. Аналитические таблицы, журналы и свёртки
ссылаются на человека **только идентификатором**, никогда почтой или ФИО: отчёт строится по
`account_id`, а расшифровка в почту делается при показе через `JOIN` с `pdn`-таблицей под правами
смотрящего. Так утечка аналитической таблицы или её экспорт не раскрывают людей.

Движки: PostgreSQL — схема `pdn` с отдельным владельцем; SQLite и DuckDB — отдельный файл базы
`<приложение>-pdn.<ext>`, подключаемый `ATTACH`, с более строгими правами файла.

### 13.3. Шифрование

ПДн-колонки шифруются **на уровне приложения** ключом из хранилища секретов (Vault transit, KMS,
системное хранилище ключей), а не только шифрованием диска: бэкап, дамп или скопированный файл базы без
ключа не читаются. Ключ не хранится ни в базе, ни в репозитории, ни в конфиге рядом с базой; ротация
ключа — перешифрование, процедура записана. Для поиска по зашифрованному полю хранится отдельно
детерминированный хэш с солью (`email_hash`), по нему — индекс; само значение по индексу не ищется.

Движки: серверная база — шифрование в приложении обязательно; встраиваемая база одного пользователя —
шифрование в приложении либо, как минимум, шифрованный файл (DuckDB `ENCRYPTION_KEY`, SQLCipher для
SQLite) с ключом в системном хранилище учётных данных, а не в файле рядом.

### 13.4. Доступ и аудит

К `pdn` — **отдельная роль базы** с минимальными правами; сервисы, которым ПДн не нужны, роли не
имеют. Каждое чтение и изменение ПДн из приложения пишется в журнал аудита: кто (субъект из токена),
что (сущность, поля), когда, зачем (операция). Журнал аудита сам ПДн не содержит — только
идентификаторы. Массовые выборки ПДн (экспорт, отчёт) — отдельная операция с отдельным правом и
записью в аудит.

### 13.5. ПДн вне таблиц

- **Логи** — ПДн не пишутся ни в каком виде: ни почта, ни ФИО, ни телефон, ни путь с именем
  пользователя; в логе — идентификатор. Тексты ошибок проходят маскирование до записи.
- **События и очереди** — в payload только идентификатор; потребитель, которому нужна почта, берёт
  её по своим правам.
- **URL и заголовки** — ПДн и идентификаторы записей о людях не передаются в пути и query-строке:
  адрес оседает в журналах веб-сервера, прокси, браузера и `Referer` в открытом виде даже под TLS.
  Всё такое — в теле запроса.
- **Экспорт и выгрузки** — по умолчанию с маскированием (`i***@example.com`); полный экспорт — по
  отдельному праву, с аудитом, в зашифрованный файл.
- **Тестовые данные и фикстуры** — только синтетические (`user1@example.com`, вымышленные ФИО);
  копия прода в тестах запрещена, обезличенная копия — только через записанную процедуру
  псевдонимизации.
- **Бэкапы** — шифруются тем же классом ключей; срок хранения бэкапа не длиннее срока хранения самих
  данных плюс окно восстановления.

### 13.6. Сроки и право на удаление

- У каждого ПДн-поля **записан срок хранения** и основание; по истечении — удаление или обезличивание
  автоматически, ретенцией (§12), а не «когда-нибудь руками».
- **Право на удаление** реализовано одной командой (`forget <субъект>`), порядок которой записан в
  документе схемы и покрыт тестом: ПДн-строки удаляются физически, аналитические и исторические
  записи **теряют ссылку, а не строку** или получают псевдоним, если история должна сохраниться в
  агрегате. После команды поиск по всем хранилищам, логам и бэкапам в пределах окна не находит
  субъекта — это проверяется тестом с обратной пробой.
- Мягкое удаление (§8) **не является** удалением ПДн: строка с `deleted_at` по-прежнему хранит данные;
  для ПДн-полей мягкое удаление дополняется обезличиванием в момент удаления.

### 13.7. Реестр ПДн

Документ схемы проекта содержит таблицу «Реестр ПДн»: колонка → категория → функция → основание →
срок → способ защиты (схема, шифрование, роль) → как удаляется. Изменение любой ПДн-колонки без
правки реестра — блокер ревью.

## 14. Безопасность данных вне ПДн

- **Секретов в базе нет**: токены, ключи, пароли не хранятся ни в колонках, ни в JSON, ни в текстах
  ошибок. Текст ошибки перед записью обрезается и проходит фильтр, заменяющий похожие на токен строки
  на `***`; тест ищет подстроки настоящих секретов из фикстур по файлу базы и логам и падает, если
  нашёл.
- Версии конфигов и снимки настроек в базе хранятся с замаскированными секретами.
- База не обращается в сеть сама (автозагрузка расширений, телеметрия — выключены сборкой и
  соединением); тест держит мок сети с нулём вызовов за прогон.
- Файлы встраиваемой базы — в каталоге данных пользователя с правами `0600`, не индексируются
  поисковиками; копировать базу — только вместе с журналом или после checkpoint. Серверная база —
  только по TLS, только с ролями минимальных прав, без суперпользователя у приложения.
- Резервные копии проверяются восстановлением по расписанию; непроверенный бэкап бэкапом не считается.

## 15. Миграции

- Схема меняется **только пронумерованными миграциями** в репозитории проекта; версия схемы, версия
  движка и набор расширений — в таблице метаданных базы.
- Миграции применяются по одной в транзакции, при старте или отдельной командой, **после
  автоматического бэкапа**. Приложение, встретившее схему новее, чем знает, отказывается стартовать с
  понятным текстом.
- Миграция должна применяться на **непустой** базе и быть обратимой, либо содержать явное объяснение,
  почему откат невозможен; в этом случае откат — восстановление бэкапа, сделанного перед миграцией.
- Ломающие изменения (удаление колонки, смена типа, смена смысла) — **двухшаговые**: добавить новое,
  перелить, убрать старое следующей версией, чтобы предыдущая версия приложения работала с базой во
  время выкатки.
- **Автогенерация миграции без ревью запрещена**: автогенератор регулярно предлагает пересоздать
  индекс, теряет умолчания, не видит переименований и генерирует `DROP COLUMN` там, где нужен
  двухшаговый переезд. Разработчик читает сгенерированный файл целиком и отвечает за него как за
  написанный руками.
- Схема и контракт API меняются вместе: контракт первичен, схема его обслуживает.

## 16. Отклонения

Правило, которое действительно мешает — внешняя система принимает только свой формат, объём требует
другого типа, движок не умеет нужной конструкции, — обходится **только записью** решения: ADR в
каталоге решений проекта либо, если проект ADR не ведёт, раздел «Отклонения от конвенции» в документе
схемы. Запись содержит: какое правило, почему здесь оно не подходит, рассмотренные варианты, что
сделано вместо него и что это стоит. Запись ревьюится вместе с кодом; принятое отклонение
санкционировано, всё остальное — нарушение. Если отклонение оказалось удачным и применимо ко всем
проектам, оно перестаёт быть отклонением: правило переносится сюда, а запись получает ссылку на
изменение.

Типовые отклонения встраиваемых движков: `INTEGER` секунд Unix вместо типа времени и `BLOB(16)`
вместо `UUID` (SQLite); инварианты открытых записей и порядок удаления — кодом и тестами вместо
частичных индексов и каскадов (DuckDB); один файл вместо схемы `pdn` у однопользовательского
приложения — с сохранением реестра, шифрования файла и правил логов.

## 17. Чек-лист ревью схемы

1. Каждый момент — тип с поясом и суффикс `_at`, сессия в UTC, в API — `Z`; каждая дата — `DATE` и
   суффикс `_on`.
2. Первичный ключ — `UUID` v7 из приложения, без серверного `DEFAULT`; естественный ключ — отдельным
