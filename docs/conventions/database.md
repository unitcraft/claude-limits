# Конвенция по организации базы данных

**Статус:** ПРИНЯТА 2026-09-06. Общая для любого проекта, который хранит данные в реляционной
базе — встраиваемой (SQLite, DuckDB) или серверной (PostgreSQL). Правила сформулированы независимо
от движка; там, где движки различаются, стоит примечание «Движки». Проект, применяющий конвенцию,
ссылается на неё из документа своей схемы и ведёт там раздел «Отклонения» (§14).

**Нарушение конвенции — блокер ревью.** Ревьюер обязан вернуть изменение, в котором появилась
колонка момента без суффикса `_at`, статус кириллицей, деньги во `float` или перечисление
нативным `ENUM`. Единственный законный способ отступить — записанное и отревьюенное отклонение
(§14); «локально в этом модуле», устная договорённость и комментарий в коде отклонением не
считаются.

Каждое правило устроено одинаково: **правило и причина · схема · API · правильно / неправильно**,
чтобы проверка на ревью была механической и не требовала чтения бизнес-логики.

---

## 1. Время

**Правило.** Момент времени хранится и передаётся **только в UTC**. Колонка момента называется с
суффиксом **`_at`**: `created_at`, `occurred_at`, `expires_at`, `synced_at`. Локальное время
существует только на экране; пояс берётся из профиля пользователя или настроек машины. Если
предметной области нужен «местный» пояс объекта (склад, филиал, устройство), он хранится отдельным
полем с идентификатором IANA (`Europe/Moscow`), а не вшивается в момент.

Почему. Данные приходят из разных источников и поясов: внешние API отдают время со смещением,
серверы и клиенты живут в своих поясах, один и тот же экран открывают из разных городов. Если
каждый компонент запишет «своё» локальное время, события из разных мест перестают быть сравнимыми:
товар «использован» за три часа до того, как «выдан». Единый UTC плюс синхронизированные часы
(NTP на серверах обязателен) убирают этот класс ошибок целиком. Суффикс в имени делает намерение
автора видимым в ревью без чтения кода.

**Схема.** Тип момента **с поясом**; сессия БД работает в UTC. Тип без пояса запрещён: он молча
теряет смещение и превращает ошибку в невидимую. Точность — секунды или доли секунды по
потребности; лишняя точность не хранится.

Движки: PostgreSQL — `timestamptz`, DuckDB — `TIMESTAMPTZ`; сессионный пояс `UTC`. SQLite не имеет
типа времени: хранить `INTEGER` секунд Unix UTC, колонка всё равно `_at`, а в документе схемы это
записано как отклонение (§14) с представлением `datetime(x, 'unixepoch')` для чтения человеком.

**API.** ISO 8601. Исходящее значение — с суффиксом `Z` (или явным смещением, если контракт так
договорился, но один стиль на весь API); входящее значение со смещением сервис **принимает и
нормализует** в UTC, а не отвергает.

Правильно: `issued_at TIMESTAMPTZ NOT NULL` → `"issued_at": "2026-08-01T09:00:00Z"`.
Неправильно: `issued_date TIMESTAMP NOT NULL` (нет пояса, нет суффикса); `"issued_at": "01.08.2026
12:00"` (локальный формат и локальное время попали в контракт).

## 2. Календарные даты

**Правило.** Если сущность календарная по природе — дата акта, дата поставки, день свёртки, — это
**дата, а не полночь какого-то пояса**. Такие колонки называются с суффиксом **`_on`**:
`signed_on`, `delivery_on`, `day_on`.

Почему. У даты нет пояса: акт подписан первого числа и в Москве, и в Екатеринбурге. Дата, записанная
моментом `00:00`, при показе в другом поясе съезжает на сутки — одна из самых частых и обидных
ошибок учётных систем. Разные суффиксы (`_at` — момент, `_on` — дата) делают ошибку видимой в имени.

**Схема.** Тип `DATE`. Если дата вычисляется из момента (день свёртки, отчётный день), документ
схемы называет пояс усечения и хранит его в метаданных базы, а не в коде; смена пояса —
пересчёт производных дат, а не тихая порча.

**API.** Строка `YYYY-MM-DD`, без времени, без `Z`, без смещения.

Правильно: `signed_on DATE NOT NULL` → `"signed_on": "2026-08-01"`.
Неправильно: `signed_at TIMESTAMPTZ` для даты подписания; `day TEXT` «как получится».

## 3. Идентификаторы и ключи

**Правило.** Класс таблицы определяет ключ; одного универсального ключа нет.

| класс | ключ | почему |
|---|---|---|
| **сущность / справочник** (пользователь, устройство, договор) | суррогатный `id` **плюс** естественная уникальность отдельным `UNIQUE` (`email`, `path`, `(device_id, channel)`) | суррогат стабилен при смене естественного ключа; `UNIQUE` не даёт дубликатов |
| **факт / временной ряд** (замер, событие с фиксированным источником) | **естественный составной ключ** «измерение + момент»: `(sensor_id, measured_at)` | суррогат здесь — лишние байты на каждой строке и лишний индекс; порядок по времени уже задан ключом |
| **журнал** (попытки, аудит, история) | суррогатный `BIGINT` | строк много, естественного ключа нет |
| **связь многие-ко-многим** | составной ключ из двух ссылок | суррогат не добавляет смысла |

**Вид суррогатного ключа** зависит от того, где создаются записи:

- **Один процесс, один источник записей** — целочисленная последовательность (`SEQUENCE`,
  `IDENTITY`); её выдаёт база. Дешевле, компактнее, индекс не фрагментируется.
- **Записи создаются в нескольких местах без центрального счётчика** — офлайн-клиенты, несколько
  контуров, синхронизация — **UUID версии 7**: генерируется на месте создания, при этом сортируем по
  времени (вставки ложатся в конец индекса, порядок по `id` — порядок создания, из идентификатора
  видно, когда запись появилась). UUID v4 в этой роли не использовать: случайный ключ разбрасывает
  вставки по всему индексу. Генератор UUID — **один на всю систему**, в общей библиотеке; серверный
  `DEFAULT` для таких `id` не ставится, чтобы не завелось второго источника.

Цена UUID v7 — идентификатор раскрывает время создания; это записывается как известное свойство,
и если оно неприемлемо (публичные ссылки на чувствительные записи), поверх берётся отдельный
публичный непрозрачный код.

**Идентификаторы внешних систем** (ключ в учётной системе, код в CRM, почта как ключ внешнего
провайдера) **не смешиваются с нашим ключом**. Если у сущности один внешний источник — внешний
ключ хранится атрибутом с явной нормализацией и `CHECK` на неё (`email = lower(email)`); если
источников может быть несколько — отдельная таблица внешних соответствий `(система, внешний ключ,
наш id)`, чтобы смена внешней системы не ломала нашу схему.

**API.** Идентификаторы — строка UUID в нижнем регистре с дефисами или целое число; никаких
«магических» чисел со смыслом. Пользователю первичный ключ не показывается: человеку — номер или
название, у которых своя нумерация.

Правильно: `id INTEGER PRIMARY KEY DEFAULT nextval('account_id_seq')` + `email VARCHAR NOT NULL UNIQUE
CHECK (email = lower(email))`; `PRIMARY KEY (sensor_id, measured_at)` у ряда.
Неправильно: `id VARCHAR` со склейкой полей; `crm_code VARCHAR(30)` прямо в сущности при нескольких
внешних системах; суррогатный `id` у таблицы замеров; UUID v4 как ключ таблицы с большим потоком
вставок.

## 4. Перечисления и статусы

**Правило.** Значения перечислений — **латиницей в `snake_case`** в базе, в API, в событиях и в
коде: `in_progress`, `awaiting_acceptance`, `http_429`. Русских значений и числовых кодов в данных
нет; перевод — на стороне интерфейса, **один словарь на приложение**, а не перевод по месту.

Почему. Статус — техническое значение, по которому строятся логика, фильтры и индексы. Кириллица в
данных приносит вопросы регистра, буквы «ё» и пробелов, а переименование статуса на экране
превращается в миграцию данных. Числовой код нечитаем в логах и ломается при любой перенумерации.

**Схема.** **`VARCHAR` с `CHECK (col IN (...))`, не нативный тип-перечисление и не справочная
таблица для закрытых списков.** Добавить значение в нативный `ENUM` — это `ALTER TYPE`: в
PostgreSQL он плохо живёт в транзакционных миграциях, в DuckDB невозможен вовсе (тип и все колонки
пришлось бы пересоздать), в SQLite нативных перечислений нет. `VARCHAR` + `CHECK` меняется обычной
миграцией и откатывается без сюрпризов; словарное сжатие колоночных движков делает его таким же
компактным, как `ENUM`. **Полный перечень значений каждого списка живёт в одном месте документа
схемы**; `CHECK` в DDL — его копия, тест сверяет их с кодом. Справочная таблица уместна для
открытых, редактируемых пользователем списков (категории, теги), а не для статусной модели.

**API.** Та же строка: `"status": "awaiting_acceptance"`. Перечень значений — часть контракта;
добавление значения согласуется с потребителями, удаление — ломающее изменение.

Правильно: `status VARCHAR(32) NOT NULL CHECK (status IN ('draft','in_progress','accepted','rejected'))`.
Неправильно: `status ENUM(...)`; `"status": "В работе"`; `"status": "InProgress"`; `"status": 3`.

## 5. Скалярные типы

- **Логические** — `BOOLEAN`, не `0/1`, не `'Y'/'N'`, не `NULL` как «ложь».
- **Деньги** — `DECIMAL(p, s)` с валютой отдельным полем (`ISO 4217`), никогда `DOUBLE`/`FLOAT`;
  в API — строка `"1234.50"`, а не число, чтобы клиент не потерял копейки в плавающей точке.
- **Количества и доли** — `DECIMAL` с явной точностью; единица измерения — отдельным полем или в
  имени (`weight_kg`, `duration_sec`), а не «подразумевается».
- **Проценты** — целые с `CHECK (x BETWEEN 0 AND 100)`, если источник даёт целые; иначе `DECIMAL`.
- **Плавающая точка** допустима только для измерений, где погрешность — часть природы данных
  (координаты, латентность, сенсоры).
- **Строки** — `VARCHAR` без искусственных ограничений длины, кроме перечислений (§4); ограничение
  смысла — через `CHECK`, а не через длину. `NOT NULL` по умолчанию; `NULL` — только там, где
  отсутствие значения честно возможно, и никогда пустая строка вместо `NULL`.
- **ФИО и адреса** — раздельными полями (`last_name`, `first_name`, `middle_name NULL`; структурный
  адрес), а не склеенной строкой: по частям сортируют, ищут, строят инициалы и документы.
- **Телефоны** — нормализованная строка E.164 (`+79161234567`); форматирование — на экране.
- **Длительности** — целые с единицей в имени (`_sec`, `_ms`); интервал «от–до» — две колонки
  моментов (§7), а не начало плюс длительность.
- **JSON** — только для полей с заведомо разной формой (payload события, сырой ответ внешней
  системы); всё, по чему фильтруют, сортируют или считают, лежит колонками.
- **Двоичные данные** — в объектном или файловом хранилище, в базе — ключ и контрольная сумма.
- **Секреты и токены** — в базе не хранятся ни в каком виде (§12).

## 6. Обязательные колонки по классам таблиц

У каждой таблицы одинаковый служебный набор для её класса. Без него нельзя ни разобрать инцидент
(«кто и когда это поменял»), ни правильно удалять, ни строить историю, ни делать курсорную
пагинацию.

| класс | обязательные колонки |
|---|---|
| **сущность / справочник** | `id` (§3); естественный `UNIQUE`; `created_at`, `updated_at`; `deleted_at NULL` там, где уместно мягкое удаление (§8); **автор изменения** `created_by`, `updated_by`, если авторов больше одного (§6.1) |
| **наблюдаемая извне сущность** (то, что мы не создаём, а обнаруживаем: каталог на диске, внешняя учётка, устройство в сети) | вместо `created_at`/`updated_at` — `first_seen_at`, `last_seen_at`; `removed_at NULL`, когда сущность исчезла из источника |
| **факт / временной ряд** | составной ключ «измерение + момент»; ссылка на цикл или период, если ряд разбит на циклы |
| **интервал** | `started_at NOT NULL`, `ended_at NULL`, `CHECK (ended_at IS NULL OR ended_at >= started_at)` (§7) |
| **журнал** | `id BIGINT`; момент события `_at`; исход перечислением (§4); ссылка на субъект |
| **служебная таблица механизма** (метаданные схемы, staging, outbox, ключи идемпотентности) | ровно то, что нужно механизму; без мягкого удаления и без авторов; список таких таблиц закрыт и каждая записана в §14 |

### 6.1. Автор изменения

`created_by` и `updated_by` заводятся, когда записи меняет **больше одного субъекта**: пользователи
через интерфейс, несколько сервисов, агенты синхронизации. Значение — идентификатор субъекта из
проверенного токена или identity сервиса; для операций, пришедших через агента, — identity агента, а
не безликий «системный ноль»: иначе при расхождениях невозможно понять, кто внёс запись. Если
единственный автор — сам процесс, колонки не заводятся, и это записано в §14; появился второй
автор — колонки добавляются миграцией.

## 7. Интервалы и открытые записи

**Правило.** Интервал — две колонки моментов `started_at`/`ended_at`, конец `NULL`, пока идёт;
`CHECK` на порядок обязателен. Переход состояния — **закрыть старую и открыть новую** запись в
одной транзакции, а не `UPDATE` существующей: история остаётся полной, и «кто когда» строится без
догадок.

Если у сущности «сейчас» может быть только один открытый интервал (одна открытая смена на
сотрудника, одна активная запись на каталог), инвариант **«не больше одной открытой записи»**
держится частичным уникальным индексом:

```sql
CREATE UNIQUE INDEX shift_open_uidx ON shift (employee_id) WHERE ended_at IS NULL;
```

Движки: PostgreSQL и SQLite частичные индексы дают; DuckDB — нет. Где движок не даёт, инвариант
держит **единственный владелец записи** в одной транзакции, а тест проверяет запросом
`SELECT key FROM t WHERE ended_at IS NULL GROUP BY key HAVING count(*) > 1` → пусто. Это отклонение
записывается в §14.

## 8. Удаление

**Правило.** Всё, что участвует в учёте или на что ссылаются другие записи, **не удаляется
физически**: у него `deleted_at` (наша сущность удалена пользователем) или `removed_at`
(наблюдаемая сущность исчезла из источника), и **каждая выборка текущего состояния фильтрует
`deleted_at IS NULL`**. Забытый фильтр — типичная причина «удалённое снова появилось в отчёте».

Два следствия:

1. Уникальные индексы у мягко удаляемых таблиц — **частичные**, `WHERE deleted_at IS NULL`, иначе
   удалённая запись навсегда блокирует повторное использование своего кода. Где движок частичных
   индексов не даёт — уникальность держит код, и это записано в §14.
2. Физическое удаление — только для журналов и кэшей по ретенции (§11), для технических таблиц и
   там, где этого требует законодательство о персональных данных (право на удаление): такие
   команды (`forget`) описаны в документе схемы с порядком удаления зависимых строк и покрыты тестом.

На каскады базы не полагаться даже там, где они есть: порядок удаления зависимых строк записан
явно, чтобы схема пережила смену движка (DuckDB `ON DELETE`-действий не поддерживает). История,
которая принадлежит не удаляемой сущности, а её окружению (кто сидел в каталоге, кто пользовался
устройством), при удалении **теряет ссылку, а не строку** (`… SET account_id = NULL`).

## 9. Именование

| что | шаблон | пример |
|---|---|---|
| база данных | `<система>_<модуль>` | `karkas_works`, `limits_core` |
| схема с персональными данными | `pdn` внутри БД | `karkas_tmc.pdn` |
| таблица | `snake_case`, **единственное число**, по сущности | `account`, `login_dir`, `measurement` |
| колонка | `snake_case`; момент `_at`, дата `_on`, ссылка `<таблица>_id`, длительность с единицей `_sec`/`_ms`, флаг — прилагательное или причастие (`locked`, `active`), без префикса `is_` | `measured_at`, `day_on`, `sensor_id`, `retry_after_sec` |
| последовательность | `<таблица>_id_seq` | `account_id_seq` |
| индекс | `<таблица>_<колонки>_idx`, уникальный — `_uidx` | `shift_open_uidx` |
| ограничение | `<таблица>_<колонки>_<uq\|ck\|fk>` | `limit_window_account_kind_model_uq` |
| представление | `v_<что показывает>` | `v_current_occupancy` |
| промежуточная таблица | `stage_<цель>` | `stage_measurement` |
| значение перечисления | `snake_case` латиницей | `awaiting_acceptance` |
| миграция | `NNNN_<что_делает>.sql`, четыре цифры, сквозная нумерация | `0001_init.sql` |

Сокращения — только общепринятые (`id`, `sec`, `ms`, `tz`, `dir`, `url`); `usr`, `cnt`, `dt` — нет.
Зарезервированные слова движка в имени колонки запрещены даже в кавычках (`at`, `user`, `order`,
`end`): `measured_at`, `app_user`, `purchase_order`, `ended_at`.

## 10. Запись данных

- **Транзакция на единицу работы.** Одна бизнес-операция — одна транзакция: журнал, факты, переходы
  интервалов, обновления справочников вместе. Половинчатого состояния на диске не бывает.
- **Идемпотентность.** Справочники — `INSERT … ON CONFLICT (<естественный ключ>) DO UPDATE SET
  updated_at = excluded.updated_at, …`; факты — `ON CONFLICT DO NOTHING` по составному ключу.
  Повторная доставка той же записи — не ошибка. Для входящих команд извне — ключ идемпотентности с
  окном хранения.
- **Массовая запись — массовым путём.** Аналитические (колоночные) движки медленны на построчном
  `INSERT` (DuckDB: около 2 мс на строку); ряды пишутся пакетом (Appender, `COPY`) в `stage_*` и
  переносятся одним `INSERT … SELECT`. Точечный `UPDATE` допустим, когда строк единицы.
- **Параметры, не конкатенация.** Любой SQL с данными — через параметризованный запрос; склейка
  строк запрещена без исключений. Идентификаторы (имена таблиц) параметром не передаются — они
  берутся из закрытого списка в коде.
- **Один владелец соединения на встраиваемых движках**: соединение принадлежит одному потоку или
  файберу, остальные общаются с ним сообщениями; привязка закреплена типом, где язык это умеет.
- **Checkpoint после записи**, если движок пишет журнал отдельно от файла: на диске всегда целостная
  и копируемая база.

## 11. Ретенция и свёртки

- У каждого ряда и журнала **записан срок хранения**, срок — в настройках, не в коде. Справочники
  и интервалы, нужные истории, хранятся без срока.
- Дневные (или иные) свёртки делаются **до** удаления сырья за период, одной операцией `INSERT …
  SELECT … ON CONFLICT DO UPDATE`. Свёртки за ещё хранящееся сырьё **не материализуются** там, где
  движок считает их достаточно быстро: материализованная копия — второй источник истины.
- Свёртка привязана к календарному дню в **записанном** поясе (метаданные базы); смена пояса —
  пересчёт свёрток за хранящееся сырьё и обновление записи, а не тихий разъезд старых и новых дней.
- Удаление по ретенции — обычный `DELETE` по колонке момента порциями, затем checkpoint; `VACUUM`
  или пересборка файла — по факту разрастания, а не по расписанию.

## 12. Приватность и безопасность данных

- **Секретов в базе нет**: токены, ключи, пароли, содержимое чужих файлов с кредами не хранятся ни в
  колонках, ни в JSON, ни в текстах ошибок. Текст ошибки перед записью обрезается и проходит фильтр,
  заменяющий похожие на токен строки на `***`; тест ищет подстроки настоящих секретов из фикстур по
  файлу базы и логам и падает, если нашёл.
- **Персональные данные** — в отдельной схеме или таблицах с отдельной ролью доступа и шифрованием на
  уровне приложения там, где это требуется регулятором; в события и логи ПДн без необходимости не
  попадают.
- Версии конфигов и снимки настроек в базе хранятся с замаскированными секретами.
- База не обращается в сеть сама (автозагрузка расширений, телеметрия — выключены сборкой и
  соединением); тест держит мок сети с нулём вызовов за прогон.
- Файлы встраиваемой базы — в каталоге данных пользователя с правами `0600`, не индексируются
  поисковиками; копировать базу — только вместе с журналом или после checkpoint. Серверная база —
  только по TLS, только с ролями минимальных прав.
- Удаление данных о человеке — одна команда с записанным порядком (§8).

## 13. Миграции

- Схема меняется **только пронумерованными миграциями** в репозитории проекта; версия схемы, версия
  движка и набор расширений — в таблице метаданных базы.
- Миграции применяются по одной в транзакции, при старте или отдельной командой, **после
  автоматического бэкапа**. Приложение, встретившее схему новее, чем знает, отказывается стартовать с
  понятным текстом.
- **Только вперёд.** Откат — восстановление бэкапа, сделанного перед миграцией; это честнее
  `downgrade`-скриптов, которые никто не проверяет. Исключение записывается в §14.
- Ломающие изменения (удаление колонки, смена типа, смена смысла) — **двухшаговые**: добавить новое,
  перелить, убрать старое следующей версией, чтобы предыдущая версия приложения работала с базой во
  время выкатки.
- Любой сгенерированный инструментом DDL читается целиком и правится руками; автогенератор регулярно
  предлагает пересоздать индекс, теряет умолчания и не видит переименований. Автор отвечает за
  миграцию как за написанную.
- Схема и контракт API меняются вместе: контракт первичен, схема его обслуживает.

## 14. Отклонения

Правило, которое действительно мешает — внешняя система принимает только свой формат, объём требует
другого типа, движок не умеет нужной конструкции, — обходится **только записью** в разделе
«Отклонения от конвенции» документа схемы проекта: какое правило, почему здесь оно не подходит, что
сделано вместо него и что это стоит. Запись ревьюится вместе с кодом; принятое отклонение
санкционировано, всё остальное — нарушение. Если отклонение оказалось удачным и применимо ко всем
проектам, оно перестаёт быть отклонением: правило переносится сюда, а запись получает ссылку на
изменение.

Типовые отклонения, ожидаемые у встраиваемых баз одного процесса: целочисленные ключи вместо UUID
(один источник записей); отсутствие `created_by`/`updated_by` (один автор — процесс); инварианты
открытых записей и порядок удаления — кодом и тестами вместо частичных индексов и каскадов (DuckDB);
`INTEGER` секунд Unix вместо типа времени (SQLite).

## 15. Чек-лист ревью схемы

1. Каждый момент — тип с поясом и суффикс `_at`; каждая дата — `DATE` и суффикс `_on`; сессия в UTC.
2. Перечисления — `VARCHAR` + `CHECK`, значения латиницей `snake_case`, список в одном месте.
3. Флаги — `BOOLEAN`; деньги и доли — `DECIMAL`; проценты — целые с `CHECK`; `NOT NULL` по умолчанию.
4. Ключ соответствует классу таблицы (§3): у сущности — суррогат **и** естественный `UNIQUE` с
   нормализацией в `CHECK`; у факта — составной естественный; UUID — только v7 и только при
   распределённом создании.
5. У интервалов — `CHECK` порядка и инвариант одной открытой записи (индексом или тестом).
6. Служебные колонки класса на месте (§6); авторы — если авторов больше одного.
7. Мягкое удаление где положено; частичные уникальные индексы у мягко удаляемых; порядок физического
   удаления записан и покрыт тестом.
8. Имена по §9; нет зарезервированных слов и произвольных сокращений.
9. Запись — транзакцией, идемпотентно, параметризованно, пакетно где строк много.
10. Сроки ретенции и пояс свёрток записаны в настройках и метаданных.
11. Ни одного секрета в схеме, тексте ошибки или фикстуре без маски; сети у базы нет; ПДн изолированы.
12. Миграция пронумерована, применяется на непустой базе после бэкапа, ломающее изменение — двухшаговое.
13. Всё, что не по конвенции, записано в «Отклонениях» с причиной и ценой.
