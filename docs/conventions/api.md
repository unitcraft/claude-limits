# Конвенция по HTTP API

**Редакция 1.0, 2026-09-06.** Общая конвенция для любого продукта с HTTP-интерфейсом: внутренний
сервис, публичный API, локальное приложение с веб-страницей. Она отвечает на вопросы «как выглядит
запрос» (адрес, метод, тело, заголовки) и «как выглядит ответ» (успех, ошибка, коллекция, повтор,
поток). Форматы значений и правила хранения заданы [конвенцией по БД](database.md) и здесь не
повторяются, только упоминаются там, где без них не прочитать пример.

Правила сформулированы так, чтобы их можно было проверить: линтером контракта, тестом, глазами на
ревью. Каждое правило снабжено причиной. Отклонение возможно, но только записанное (§19), с
причиной и ценой; «так было проще» причиной не считается.

## 0. Принципы

1. **HTTP используется по назначению.** Метод несёт семантику (безопасный, идемпотентный,
   изменяющий), код состояния несёт исход, заголовки несут метаданные транспорта, тело несёт
   данные. Продукт не изобретает свой протокол поверх `POST`, пока у него нет причины, которую
   нельзя закрыть более узким правилом.
2. **В URL нет персональных данных и идентификаторов субъекта.** URL пишется в журналы доступа,
   историю браузера, `Referer`, закладки и скриншоты, то есть в места, которые продукт не
   контролирует. Это правило, а не стиль адресации, решает задачу «идентификаторы не оседают там,
   где мы их не контролируем» (§2.3).
3. **Одна форма для одного понятия.** Один вид ошибки, одна форма страницы коллекции, одно имя
   для идентификатора, один формат времени. Расхождение форм оплачивает не автор, а все клиенты.
4. **Бэкенд источник истины по валидации и по правам.** Что проверил клиент, бэкенд не знает и
   знать не может.
5. **Молчаливых исходов нет.** Лишнее поле, обрезанный лимит, проигнорированный параметр,
   невалидный ключ идемпотентности: всё это громкие ошибки, а не тихая подстановка.
6. **Ошибка не особый режим работы**: это такой же ответ, отличающийся кодом состояния и типом
   тела. Диагностические заголовки и `request_id` присутствуют в ней так же, как в успехе.
7. **Наружу уходит только то, что нужно клиенту.** Версии, имена хостов, стеки, SQL, чужие данные,
   существование объектов, к которым нет доступа, остаются внутри.

## 1. Транспорт

### 1.1. TLS

- Все сетевые соединения только по TLS 1.2+, предпочтительно 1.3: между сервисами, из клиентов,
  для служебных путей и проб оркестратора, в dev-контуре. Причина: внутренний контур не является
  доверенным (в модели угроз есть скомпрометированный узел), а dev, который ведёт себя иначе, чем
  прод, приносит сюрпризы при первом же развёртывании (смешанное содержимое, недоступные
  защищённые Web API, неработающий HSTS).
- Открытого HTTP-слушателя у сервиса нет, редиректа с `80` тоже: к моменту редиректа первый
  запрос уже ушёл открытым текстом вместе с `Authorization` и телом.
- **Исключение**: процесс, слушающий исключительно loopback-интерфейс (`127.0.0.1`, `::1`). У
  такого соединения нет сетевого пути, шифровать нечего. Как только слушатель привязывается к
  сетевому интерфейсу, TLS обязателен, даже в «доверенной» локальной сети.
- Сервис, отдающий ответ браузеру, сам ставит `Strict-Transport-Security` (не менее года) и
  остальные заголовки безопасности (§14.3); дублирование на периметре допустимо, обязанность не
  снимает.

### 1.2. Учётные данные

- Учётные данные передаются заголовком `Authorization` (`Bearer <token>` или иная объявленная
  схема) и извлекаются только из него. Заголовок `Cookie` при этом не читается, не логируется и не
  пробрасывается дальше. Токен никогда не передаётся в URL (ни в пути, ни в query), см. §2.3.
- **Cookie-сессия допустима только для браузерного клиента, у которого нет возможности поставить
  заголовок** (страница, отдаваемая тем же сервером, `EventSource`, скачивание файла по ссылке), и
  только с полным набором условий: `HttpOnly`, `Secure` (кроме loopback), `SameSite=Strict`,
  ограниченный `Path`, срок жизни, обязательная проверка `Origin` на всех изменяющих операциях
  (§14.2). Cookie устанавливается ответом на `POST` с учётными данными в теле, а не переходом по
  ссылке с токеном. Один и тот же маршрут не принимает учётные данные двумя способами «на выбор»:
  либо заголовок, либо cookie, и это записано в контракте маршрута.
- Смена или отзыв токена немедленно обнуляет все сессии, выданные по нему.
- Проверка токена выполняется сервисом самостоятельно, даже если перед ним стоит шлюз, который
  тоже проверяет.

### 1.3. Ограничения на входе

Проверяются до разбора тела и до аутентификации, общей обвязкой (§16):

- предел размера тела (`413`), проверяется по `Content-Length` и по факту чтения;
- предел суммарного размера заголовков и длины одного заголовка (`400`);
- дублирующиеся `Host` или `Content-Length`, управляющие символы в заголовках: `400`, это признаки
  расщепления запроса, а не ошибки клиента, «чинить» их выбором первого значения нельзя;
- `Content-Type` тела не из списка контракта: `415`;
- таймауты чтения заголовков и тела; предел числа соединений с одного адреса.

## 2. Адресация

### 2.1. Схема пути

```
/api/v<major>/<resource>[/<id>[/<sub_resource>[/<id>]]]
/api/v<major>/<resource>/<id>/<action>          # доменное действие
/api/v<major>/<resource>/search                 # чтение с фильтрами, которым нельзя в URL
```

- Ресурсы во множественном числе, `snake_case`, латиница: `work_orders`, `issue_positions`.
- Вложенность пути не глубже двух ресурсов; глубже значит, что внутри спрятан самостоятельный
  ресурс со своим адресом.
- Доменное действие, смысл которого шире правки полей (`complete`, `cancel`, `approve`,
  `recalculate`), оформляется отдельным `POST` на подпуть глагола. У него своя схема запроса, свои
  права и своё имя в журнале; `PATCH` с «особым флагом» вместо действия запрещён.
- Версия `v<major>` в пути. Ломающее изменение (удаление или переименование поля, смена типа,
  смена семантики кода ошибки, ужесточение валидации, которое отвергает ранее допустимые
  запросы) выпускается новым major. Добавление необязательного поля, нового кода ошибки в
  объявленном списке, нового ресурса ломающим не является. Если у продукта нет потребителей,
  которых он не деплоит сам (клиент и сервер один артефакт), версию можно нести не в пути, а в
  заголовке и в служебном ответе; это записывается как отклонение (§19).

### 2.2. Методы

| метод | семантика | тело запроса | идемпотентен |
|---|---|---|---|
| `GET` | чтение, без побочных эффектов; параметры только в query (§2.3) | нет (тело у `GET` теряется по дороге) | да |
| `POST` | создание, доменное действие, поиск с параметрами, которым нельзя в URL | JSON | нет, кроме объявленной идемпотентности (§10) |
| `PUT` | полная замена ресурса | JSON, весь ресурс | да |
| `PATCH` | частичное изменение, JSON Merge Patch (RFC 7386) | JSON | да при `If-Match` |
| `DELETE` | удаление | нет | да |

`HEAD` и `OPTIONS` обрабатываются обвязкой. Иной метод на существующем пути: `405` с `Allow`.
Ветвление семантики по методу обязано соблюдаться: `GET`, меняющий состояние, и `POST`,
используемый для чтения без причины из §2.3, отвергаются на ревью.

### 2.3. Что запрещено в URL

Правило проверяемое и жёсткое:

- **Персональные данные** в любом сегменте пути и в любом параметре query: почта, телефон, ФИО,
  документы, адреса, логины, номера договоров и лицевых счетов, всё из реестра ПДн продукта
  (конвенция по БД §13.7).
- **Идентификаторы субъектов ПДн**: `person_id`, `employee_id`, `customer_id`, `user_id` и любые
  ключи, по которым запись однозначно связывается с человеком. Свои данные субъект читает через
  контекст токена (`/api/v1/me/...`), чужие, если право есть, через тело `POST .../search` или
  ссылку из уже полученного ресурса, где идентификатор нейтрален.
- **Учётные данные и секреты**: токены, ключи API, одноразовые коды, presigned-подписи.
- **Естественные ключи, которые что-то сообщают**: номер документа вида `ЗАЯВ-000123`, ИНН,
  табельный номер. Адресация только по непрозрачному идентификатору (UUID v7).

Что в URL допустимо: непрозрачные идентификаторы объектов (документов, заказов, устройств),
курсоры, лимиты, сортировка, фильтры по перечислениям, датам и идентификаторам объектов.
Идентификатор объекта в журнале говорит «кто-то читал объект X», и это принято как цена
ресурсной адресации ради кэша, условных запросов и стандартного инструментария. Продукт, для
которого и эта цена велика (объекты сами по себе чувствительны), переводит чтение таких ресурсов
на `POST .../search` и записывает это в §19 как отклонение с причиной.

Проверяемая форма: линтер контракта имеет список запрещённых имён параметров (`email`, `phone`,
`inn`, `passport`, `*_name`, `person_id`, `user_id`, `token`, `key`…) и валит сборку при их
появлении с `in: path` или `in: query`; тест на маршруты проверяет, что путь параметризован только
сегментами `{id}` с форматом UUID.

### 2.4. Фильтры, которым нельзя в URL

Чтение с фильтром по ПДн или по идентификатору субъекта делается операцией `POST
/<resource>/search` с телом той же формы, что запрос коллекции (§4.1): `cursor`, `limit`, `sort`,
`filter`, `expand`. Ответ идентичен `GET`-коллекции. `search` объявляется в контракте как чтение:
безопасен для повтора, не требует ключа идемпотентности, не продлевает сессию без пометки (§8.4),
кэшируется только в памяти процесса и только если ответ не содержит ПДн.

### 2.5. Query-параметры

- Закрытый список на операцию: неизвестный параметр даёт `400 invalid_parameter`, а не
  игнорируется. Клиент, у которого фильтр молча пропал, получает полную выборку и не замечает.
- Повторяющийся параметр (`status=a&status=b`) допустим только для параметров, объявленных
  массивами; иначе `400`.
- Значения кодируются по RFC 3986; даты и моменты в форматах §11.

## 3. Тело запроса и ответа

- JSON, UTF-8, `Content-Type: application/json; charset=utf-8` у запроса с телом и у успешного
  ответа; у ошибки `application/problem+json; charset=utf-8`. Кодировка указывается явно: текст
  в ответах не латиница.
- **Ключи `snake_case`**, латиница, те же имена, что в БД и в моделях. Слой переименования между
  колонкой и полем JSON это место, где имя однажды разойдётся.
- **Верхний уровень тела всегда объект**, и в запросе, и в ответе. В массив нельзя добавить поле;
  объект расширяется необязательным полем и не ломает никого. Массовая операция принимает
  `{ "items": [...] }`, а не массив.
- **Ресурс отдаётся без обёртки.** Никаких `data`, `result`, `success`. Признак успеха уже в коде
  состояния, диагностика в заголовках, метаданные коллекции в объекте страницы.
- **Объявленное поле присутствует всегда**, отсутствие значения передаётся явным `null`. Иначе
  клиент не отличит «значения нет» от «поле убрали» и от «сервис его не отдаёт».
- **Массивы именованные, пустой массив `[]`**, никогда не `null`.
- Вложенность объекта не глубже трёх уровней (корень первый, индекс массива уровнем не
  считается). Глубже значит, что внутри самостоятельный ресурс.
- Связанные сущности отдаются ссылкой (`counterparty_id`), встраивание только по полю `expand` с
  закрытым списком значений из контракта; значение вне списка `422`.
- Неограниченная коллекция внутри ресурса запрещена; она отдаётся отдельным пагинируемым
  подресурсом. Ограниченная по природе (размер записан в контракте) допустима.
- Операция без параметров всё равно принимает `{}`, а не отсутствующее тело: место для будущего
  необязательного поля.
- Имя идентификатора самого ресурса `id`; форма `<entity>_id` только для ссылок на другие
  сущности.

## 4. Коллекции

### 4.1. Запрос

`GET /api/v1/issues?cursor=…&limit=50&sort=-created_at&status=draft,in_progress&expand=counterparty`

| параметр | обязательность | смысл |
|---|---|---|
| `cursor` | нет | непрозрачный курсор предыдущей страницы; отсутствие или пусто: первая страница |
| `limit` | нет | размер страницы; умолчание и максимум зафиксированы в контракте операции; превышение `400`, не обрезание |
| `sort` | нет | список полей с префиксом `-` для убывания; допустимые поля перечислены в контракте |
| фильтры | нет | по одному параметру на поле, закрытый список, значения из перечислений и форматов §11 |
| `expand` | нет | закрытый список связей |

Максимумы `limit` задаются классами операций в контракте продукта, например: обычные списки 200
(умолчание 50), справочники 500 (100), списки с ПДн 100 (25). К какому классу относится операция, решает содержимое ответа: одно поле с ПДн переводит её в
нижний предел. Это вторая мера против массовой
выгрузки вместе с суточной квотой на выдачу ПДн.

### 4.2. Ответ

```json
{
  "items": [ { "id": "01903f2a-…", "status": "draft" } ],
  "next_cursor": "eyJpZCI6…",
  "has_more": true
}
```

- `items` всегда массив; `next_cursor` присутствует всегда, `null` в конце; `has_more` дублирует
  смысл курсора для интерфейса.
- **`total` в странице не отдаётся.** Счётчик это отдельное чтение таблицы на каждую страницу ради
  числа, которое устаревает к показу. Где число нужно, заводится `GET /<resource>/count` с теми же
  фильтрами, помеченный в контракте как дорогой; он вправе вернуть приблизительное значение с
  признаком `approximate: true`.
- Курсорная пагинация, не постраничная: при параллельных вставках страницы «съезжают», а
  `OFFSET` читает и выбрасывает всё, что перед ним. Курсор непрозрачен; разбор курсора клиентом
  запрещён; курсор, который не декодируется, `400`.
- **Выдача сужается правами вызывающего всегда**, и это не фильтр: субъекту без прав отвечают `200`
  с пустым `items`, а не `403`. Фильтр по идентификатору чужого объекта тоже даёт пустую
  страницу, иначе через список можно узнать, существует ли объект, хотя одиночное чтение это
  скрывает (§7.3). `count` считает по той же области.

## 5. Валидация

1. **Бэкенд проверяет всё заново**, независимо от клиента: до него доходят запросы из старых
   версий, очередей, интеграций и `curl`. Отсутствие проверки на клиенте дефект удобства,
   отсутствие на бэкенде уязвимость.
2. **Схема запроса закрыта.** Лишнее поле `422 extra_forbidden`, не игнорирование: опечатка в
   имени поля иначе превращается в документ без значения, найденный через месяц. Лишний
   query-параметр `400 invalid_parameter` (§2.5).
3. Для каждого поля проверяются тип, формат (UUID v7, ISO 8601 с `Z`, десятичная строка), диапазон,
   длина строки (у каждой строки есть максимум), принадлежность перечислению, взаимозависимости
   (`date_to >= date_from`).
4. **Один ответ `422` содержит все найденные нарушения** в `errors[]`; выдавать их по одному на
   каждую отправку формы запрещено.
5. Порядок обработки фиксирован: транспорт и заголовки, аутентификация и права, валидация схемы,
   бизнес-правила, работа с данными. Значение, не прошедшее схему, не попадает ни в бизнес-логику, ни в запрос к базе.
6. `400` против `422`: `400` «не смог разобрать или обратились неправильно» (битый JSON, битый
   курсор, лишний параметр query, `limit` сверх максимума, неверный формат обязательного
   заголовка); `422` «разобрал, но так нельзя» (схема, перечисление, лишнее поле, бизнес-правило).
   Клиент на `400` показывает общую ошибку, на `422` подсвечивает поля.
7. Текст ошибки не цитирует присланное значение целиком, не упоминает таблицы, классы и
   регулярные выражения схемы и не выдаёт, какие ещё значения существуют в системе.
8. Данные клиента не считаются безопасными после сохранения: экранирование при выводе в его
   контексте (HTML, SQL только параметрами, имя файла, строка лога без управляющих символов);
   клиентское значение не становится путём, заголовком, ключом объекта в хранилище или частью
   `type` ошибки.

## 6. Ошибки

Все ошибки во всех сервисах продукта отдаются в формате Problem Details (RFC 9457, преемник RFC
7807) с `Content-Type: application/problem+json; charset=utf-8`:

```json
{
  "type": "urn:<product>:problem:validation-error",
  "title": "Ошибка валидации",
  "status": 422,
  "detail": "Проверьте заполнение полей",
  "instance": "/api/v1/issues",
  "code": "validation_error",
  "request_id": "01903f2a-7c1e-7a3b-9f21-6d4e2b8c9a10",
  "errors": [
    { "field": "positions[0].quantity", "code": "greater_than", "message": "Должно быть больше 0" }
  ]
}
```

| поле | когда | смысл |
|---|---|---|
| `type` | всегда | URN `urn:<product>:problem:<code-с-дефисами>`; URN, а не URL, чтобы не публиковать страницы и не раскрывать внутренние домены |
| `title` | всегда | короткий заголовок для человека на языке продукта |
| `status` | всегда | тот же код состояния, что в строке ответа |
| `detail` | всегда | развёрнутый текст для человека, без технических подробностей |
| `instance` | всегда | **шаблон** пути операции (`/api/v1/issues/{id}`), не конкретный URL: конкретный путь мог бы содержать идентификатор, а тело ошибки показывается пользователю и уходит в поддержку |
| `code` | всегда | машинный код `snake_case` из закрытого каталога продукта; клиент ветвится только по нему |
| `request_id` | всегда | UUID v7 запроса, тот же, что в заголовке `X-Request-Id` |
| `errors[]` | только валидация | `field` полный путь до поля (`positions[0].quantity`, `filter.status`), `code` машинный, `message` человеческий |

- `type` и `code` одно значение в двух формах; преобразование механическое в обвязке.
- Ветвиться по `title` и `detail` запрещено: это тексты, их правят редакторы.
- `errors[]` единственное необязательное поле: у невалидационных ошибок его нет вовсе.
- Каталог кодов ведётся вместе с контрактом; новый код «по месту» в обработчике не заводится.
- **Запрещено в теле ошибки**: стеки, фрагменты кода, SQL и имена таблиц, тексты драйверов, имена
  хостов и портов, версии ПО, дампы запроса, ПДн, токены и подписи. Всё это пишется в лог под
  `request_id`.
- Любое необработанное исключение превращается обвязкой в корректный `500` с общим текстом и
  `request_id`; HTML-страница фреймворка или пустой ответ наружу не уходят.

## 7. Коды состояния

### 7.1. Успех

| код | когда | обязательно |
|---|---|---|
| `200` | чтение или изменение с телом | тело ресурса или страницы |
| `201` | создано | тело созданного ресурса с `id`; заголовок `Location` с его адресом |
| `202` | принято в асинхронную обработку | тело `{ "id", "state", "status_url" }` задачи и `Location` на ресурс задачи; `state` из `queued \| running \| succeeded \| failed \| cancelled` |
| `204` | успех без тела (`DELETE`, действие без результата) | тела нет; диагностические заголовки есть |
| `304` | условный `GET`, ресурс не менялся | тела нет; `ETag` |

**`2xx` только при реальном успехе.** `200` с `{ "success": false }` запрещён: мониторинг видит
ноль ошибок, повтор клиента не включается, пользователь узнаёт первым.

### 7.2. Ошибки клиента

| код | когда |
|---|---|
| `400` | битый JSON, битый курсор, неизвестный или неверный параметр query, `limit` сверх максимума, отсутствующее или не-JSON тело там, где оно нужно, неверный формат обязательного заголовка (`Idempotency-Key` не UUID v7), нарушения §1.3 |
| `401` | нет учётных данных, токен невалиден или просрочен, сессия закрыта; различаются `code` (§8.1) |
| `403` | учётные данные валидны, но нет права на класс операции (scope). Не на конкретный объект (§7.3) |
| `404` | ресурса нет **или** вызывающий не вправе его видеть |
| `405` | метод не поддерживается путём; `Allow` обязателен |
| `409` | конфликт состояния: уникальность, недопустимый переход, повтор `Idempotency-Key` с другим телом (`conflict`), повтор при идущей обработке (`idempotency_in_progress` + `Retry-After`) |
| `410` | ресурс удалён окончательно |
| `412` | условие `If-Match`/`If-Unmodified-Since` не выполнено: ресурс изменён с момента чтения |
| `413` | тело или файл больше предела |
| `415` | `Content-Type` не из контракта |
| `422` | нарушена схема или бизнес-правило; лишнее поле |
| `428` | операция требует `If-Match`, а его нет |
| `429` | превышен лимит частоты; `Retry-After` обязателен |

### 7.3. `404`, а не `403`, на чужой объект

`403` подтверждает существование объекта и часто его принадлежность. Перебирая идентификаторы,
чужой пользователь строит карту данных, к которым не имеет доступа. Поэтому отсутствие права на
конкретный объект отдаётся как `404`; `403` остаётся для отказа, который относится к вызывающему
целиком (нет scope на класс операций) и ничего не раскрывает. Списки при этом отдают пустую
страницу (§4.2).

### 7.4. Ошибки сервера

| код | когда |
|---|---|
| `500` | необработанное исключение; наружу общий текст и `request_id` |
| `502` | зависимость ответила некорректно; `Retry-After`, если срок известен |
| `503` | сервис или зависимость недоступны, перегрузка, старт; **`Retry-After` обязателен** |
| `504` | таймаут зависимости; `Retry-After`, если срок известен |

Нестандартные коды (`440`, `419`, `499`) не используются: их не понимают прокси, библиотеки и
панели мониторинга; различия передаются полем `code`.

## 8. Аутентификация, сессия, права

### 8.1. Коды отказа

| ситуация | статус | `code` | что делает клиент |
|---|---|---|---|
| токен просрочен, сессия жива | `401` | `token_expired` | молча обновляет токен и повторяет один раз |
| сессия закрыта (бездействие или предельный срок) | `401` | `session_expired` | показывает объяснение, ведёт на вход; токен не обновляет |
| учётных данных нет либо токен не прошёл проверку (подпись, издатель, отзыв) | `401` | `unauthenticated` | ведёт на вход |
| прав на класс операции нет | `403` | `forbidden` | показывает «нет прав»; на вход не ведёт и сессию не сбрасывает |

- Истечение по бездействию и по предельному сроку отдаётся одинаково: устройство таймеров
  клиенту не сообщается.
- В теле нет `login_url`, момента истечения, остатка времени, идентификатора сессии.
- `WWW-Authenticate` отдаётся только там, где схема аутентификации действительно `Bearer` по RFC
  6750 и клиент не браузерная страница с собственным потоком входа; иначе он включает
  браузерное окно, которое мешает.
- Если интерфейс отвечает формой входа на каждый отказ, пользователь привыкает вводить пароль по
  любому поводу, а именно эту привычку эксплуатирует фишинг.

### 8.2. Сессия по бездействию (если у продукта она есть)

- Отметку последнего действия ведёт сервер; утверждению клиента «пользователь активен» он не
  верит.
- **Умолчание закрытое**: сессию продлевают только изменяющие операции (всегда) и читающие,
  которые контракт пометил `on_marker`, и только при пометке клиента `X-<Product>-User-Action:
  true`. Всё остальное (фоновые опросы, обновление токена, кадры реалтайма, служебные пути,
  досылка очереди, автоперезапрос при возврате фокуса) сессию не двигает. Асимметрия ошибки:
  пропущенная пометка на пользовательском чтении завершает сессию раньше времени, и это замечают
  сразу; пропущенная пометка на фоновом опросе превращает сессию в вечную, и этого не замечает
  никто.
- Пометку ставит одно место в клиенте (api-клиент по источнику вызова), а не компоненты.
- Отдельной операции «состояние сессии» нет: она сама была бы фоновым запросом. Обратный отсчёт
  клиент считает от своей последней помеченной операции. При расхождении сервер главнее: получив
  `session_expired`, клиент подчиняется немедленно.
- Истечение сессии не равно выходу: локальные черновики и очереди клиент не очищает.

### 8.3. Права

Проверка прав в сервисе, а не только на шлюзе. Право на объект проверяется на каждом чтении и
изменении, в том числе на пути повтора по ключу идемпотентности (§10): область поиска
сохранённого ответа включает субъекта.

### 8.4. Чтение и продление

`GET`, `search` и `count` классифицируются как чтение: безопасны для повтора, не требуют ключа
идемпотентности, продлевают сессию только по пометке.

## 9. Заголовки ответа и кэширование

### 9.1. Обязательные заголовки каждого ответа

Включая `204`, ошибки и отдачу файлов:

| заголовок | содержимое |
|---|---|
| `X-Request-Id` | UUID v7 запроса |
| `Cache-Control` | явная политика (§9.3) |
| `Retry-After` | при `429` и `503` всегда; при `502`/`504`, если срок известен |

### 9.2. Обязательные, когда сервисов или экземпляров больше одного

| заголовок | содержимое |
|---|---|
| `traceparent` | W3C Trace Context, продолжается сквозь все вызовы |
| `X-<Product>-Module` | имя сервиса из конфигурации |
| `X-<Product>-Instance` | **непрозрачный** идентификатор экземпляра (UUID v7 при старте), без hostname, адреса и имени контейнера |
| `X-Processing-Time-Ms` | длительность обработки в middleware |

Рекомендуемые: `Server-Timing`, `X-Request-Received-At`/`X-Response-Sent-At` (ISO 8601 UTC с
миллисекундами). Продукт из одного процесса без распределённой трассировки записывает
отсутствие этого набора в §19 одной строкой.

Диагностика живёт в заголовках, а не в теле: тело ресурса задано контрактом, тело ошибки
форматом §6, а заголовки работают и для `204`, и для бинарных ответов.

### 9.3. Кэш и условные запросы

- `GET` на ресурс отдаёт `ETag` (сильный, от версии или хэша представления) и поддерживает
  `If-None-Match` с `304`. Это одна из причин, ради которых сохранена ресурсная адресация.
- `Cache-Control` явный на каждом ответе. Персонализированные ответы и ответы с ПДн:
  `private, no-store`. Публичные справочники: `public, max-age=<с>, must-revalidate`. Ответы под
  `Authorization` промежуточные кэши не сохраняют; полагаться на это молча нельзя, политика
  пишется явно.
- **Ответы с ПДн кэшируются только внутри процесса** и недолго. Внешний кэш (Redis, диск, шлюз)
  означал бы копию ПДн в хранилище, на которое не распространяются правила их защиты.

### 9.4. Оптимистическая блокировка

Ресурс, объявленный в контракте версионируемым, изменяется (`PUT`, `PATCH`, `DELETE`, доменные
действия) только с `If-Match: <etag>`: отсутствие `428 precondition_required`, несовпадение `412
precondition_failed` с актуальным представлением в теле, чтобы клиент мог показать, что
изменилось. Это защита от потерянного обновления двумя вкладками и одновременно естественная
идемпотентность `PUT` (§10.3).

### 9.5. Заголовки, которых в ответе нет

`Server`, `X-Powered-By`, `Via`, заголовки шлюза и любые, сообщающие фреймворк, версию, хост или
имя пода. Проверяется **конечный ответ у клиента**, потому что заголовок может добавить прокси
после приложения.

## 10. Идемпотентность

### 10.1. Что идемпотентно само

`GET`, `HEAD`, `PUT`, `DELETE`, `search`, `count`. Повтор `PUT` с `If-Match` после успеха получает
`412`: версия сменилась, второго применения нет. Повтор `DELETE` получает `404` или `410`. Этого
достаточно там, где клиент может перечитать ресурс при `412` и понять, применилось ли его
изменение.

### 10.2. Когда нужен `Idempotency-Key`

Изменяющие `POST` (создание, доменные действия), которые может повторить клиент, не получивший
ответа: офлайн-очереди, интеграции, автоматические повторы шлюза. Без ключа повтор создаёт второй
документ. Обязательность ключа объявляется контрактом каждой операции; из метода `POST` она не следует.

| ситуация | ответ |
|---|---|
| операция объявила ключ, он не передан | `400 invalid_parameter`, операция не выполняется |
| ключ не UUID v7 | `400 invalid_parameter` |
| ключ предъявлен операции, которая его не объявляла | `400 invalid_parameter`: молча выбросить значит отказаться от гарантии, не сказав клиенту |
| ключ встречается первый раз | штатная обработка; успешный ответ запоминается под этим ключом |
| повтор ключа с тем же телом | отдаётся запомненный ответ, добавляется `X-Idempotent-Replay: true` |
| повтор ключа с другим телом | `409 conflict` |
| повтор ключа, пока первый запрос не завершён | `409 idempotency_in_progress` + `Retry-After` |

Правила механизма (хранилище описано в конвенции по БД §11.2):

- область ключа: пара «субъект + ключ»; тот же ключ от другого субъекта это первая встреча, а не
  конфликт, потому что на пути повтора обработчик и его проверки прав не вызываются;
- «то же тело» это совпадение хэша от пути операции и сырых байт тела; JSON не нормализуется:
  очередь повторяет сохранённый запрос, а не собирает новый; ложный `409` громкий, ложное
  совпадение тихо отдаёт чужой ответ;
- сохраняются только `2xx`; ошибка снимает бронь ключа, иначе `422` из-за опечатки запирал бы
  ключ навсегда;
- тело запроса не хранится, только отпечаток: копия запроса с ПДн лежала бы дольше любого срока
  хранения;
- окно хранения больше максимального срока жизни элемента клиентской очереди с запасом; для
  клиентов без очередей достаточно 72 часов;
- ключ создаётся клиентом в момент постановки операции в очередь и сохраняется рядом с ней; при
  каждой отправке используется тот же ключ;
- реализация одна на продукт, в общей обвязке; своя таблица «по образцу» в модуле запрещена.

### 10.3. Идемпотентность через версию вместо ключа

Операция вправе объявить в контракте, что её идемпотентность обеспечена `If-Match` (замена
состояния, выпуск нового секрета, который сразу меняет версию ресурса). Тогда ключ не требуется, а
клиент при `412` обязан перечитать ресурс, чтобы понять, применилось ли изменение. Слабое место
этого способа записано честно: после обрыва связи клиент не отличает «моё применилось» от «кто-то
другой поменял» без перечитывания. Для очередей с накоплением операций этого недостаточно, там
нужен ключ.

## 11. Форматы значений

Канон в [конвенции по БД](database.md) (§1, §2, §3.3, §4, §5); здесь сводка, чтобы не держать два
файла открытыми:

| значение | форма | пример |
|---|---|---|
| момент времени, поля `_at` | ISO 8601 UTC, строго `Z`, без смещений | `"2026-09-06T18:10:00Z"` |
| календарная дата, поля `_on` | `YYYY-MM-DD` | `"2026-09-06"` |
| идентификатор | UUID v7 строкой | `"0192a7f0-3c4d-7e21-8a55-0b9c1d2e3f40"` |
| деньги | строка десятичного числа + `currency_code` ISO 4217 | `"amount": "1234.50", "currency_code": "RUB"` |
| количество, доля, процент с дробью | строка десятичного числа | `"quantity": "12.500"` |
| целые счётчики | число JSON | `"count": 42` |
| перечисление | латиница `snake_case` | `"in_progress"` |
| телефон | E.164 | `"+79991234567"` |
| длительность | целые секунды или миллисекунды с суффиксом в имени | `"timeout_sec": 30` |

Человекочитаемые подписи («2 дня 17 ч», «вчера») в API по умолчанию не отдаются: их формирует
интерфейс по локали. Продукт с несколькими интерфейсами, которым нужна одинаковая формулировка,
вправе отдавать готовые подписи в полях с суффиксом `_label` рядом с машинным значением, никогда
вместо него; это записывается в §19.

## 12. Потоки и события

- Server-Sent Events и WebSocket открываются `GET` на объявленном пути под тем же механизмом
  аутентификации, что и остальное API; токен в URL запрещён и здесь (§2.3), для `EventSource`
  используется cookie-сессия по правилам §1.2.
- Каждое событие несёт `id` (монотонный) и `event` из закрытого списка `snake_case`; `data` JSON
  по контракту события. Клиент присылает `Last-Event-ID`; сервер досылает пропущенное из буфера
  или, если буфер не покрывает разрыв, шлёт полное состояние первым событием.
- Первое событие после подключения: текущее состояние (snapshot), чтобы клиент не ждал первого
  изменения. Пустое соединение поддерживается `ping` не реже чем раз в 30 с.
- Лимит соединений на экземпляр и на субъекта; превышение `503` с `Retry-After`. Остановка
  сервера объявляется финальным событием (`bye`), а не обрывом.
- Кадры потока сессию не продлевают (§8.2).

## 13. Асинхронные операции

`202` с телом `{ "id", "state", "status_url" }` и `Location` на ресурс задачи `GET
/api/v1/tasks/{id}`; состояния из закрытого списка §7.1; результат задачи ссылкой на созданный
ресурс, а не встраиванием. Постановка задачи изменяющая операция, ключ идемпотентности по §10.
Сам ответ `202` укладывается в бюджет времени быстрого ответа продукта.

## 14. Безопасность на HTTP-границе

### 14.1. Скрытие деталей

- Версии ПО и версия сборки в обычных ответах не отдаются: ни заголовком, ни полем, ни в `detail`.
  Клиенту достаточно `/api/v<major>`; номер сборки читает эксплуатация на служебном пути
  внутреннего контура.
- Служебные пути (проверки работоспособности, метрики, спецификация) не публикуются наружу:
  спецификация это карта всех полей, метрики состав зависимостей. Наружу контракт публикуется из
  репозитория контрактов, а не живой спецификацией с боевого сервиса.
- Идентификатор экземпляра непрозрачен (§9.2). Абсолютные пути файловой системы, имена
  пользователей ОС, имена хостов в ответах не появляются даже в служебных полях, отдаваемых по
  сети; они допустимы только на loopback-интерфейсе локального инструмента.

### 14.2. Доверие входящим заголовкам

- Реальный адрес клиента вычисляется только если соединение пришло с адреса из списка доверенных
  прокси; тогда берётся крайний правый недоверенный адрес `X-Forwarded-For`. Если соединение пришло не
  от доверенного прокси, оба заголовка отбрасываются целиком и клиентом считается адрес
  соединения. Лимиты, блокировки, аудит и лог используют один и тот же вычисленный адрес. Пока список пуст, механизм работает в безопасном
  вырожденном режиме (адрес соединения) и лимиты не являются мерой против конкретного клиента.
- Значения из заголовков клиента (`X-Request-Id`, `Origin`, `User-Agent`) годятся для корреляции и
  проверки, но не для решений об идентичности и не для подстановки в SQL, пути и ключи.
- Дальше по цепочке пробрасывается закрытый список известных заголовков.
- `Origin` на изменяющих операциях: пришедший проверяется по списку разрешённых источников;
  отсутствующий отказ для браузерной сессии и допустим для межсервисного токена или ключа
  агента, у которых источника-браузера нет.

### 14.3. Заголовки безопасности для браузерных ответов

`Strict-Transport-Security` (§1.1), `Content-Security-Policy` без внешних источников, где это
возможно, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (чтобы URL с
идентификаторами объектов не уходил третьим сторонам), `X-Frame-Options: DENY` или
`frame-ancestors`. CORS включается только для объявленных источников; `*` под `Authorization`
запрещён.

### 14.4. Лимиты

Ограничение частоты по вычисленному адресу и по субъекту; неверные учётные данные считаются
отдельно (например, десять за минуту с одного адреса дают временный `429`); сравнение секретов
за константное время; суточная квота на объём выданных ПДн.

## 15. Журналирование

- Каждая строка лога несёт `request_id`, `trace_id` (если есть), сервис, экземпляр, метод, шаблон
  пути, субъекта, вычисленный адрес клиента. Контекст ставит обвязка один раз, руками поля не
  добавляются.
- **Тело запроса и ответа в лог не пишется** ни на каком уровне без согласования со службой ИБ: там
  ПДн и секреты. Прикладные идентификаторы, нужные для разбора, обработчик кладёт в контекст
  поимённо.
- Журнал доступа хранит URL целиком: по правилу §2.3 в нём нет ПДн и секретов, а идентификаторы
  объектов нужны разбору инцидентов. Появление ПДн в URL это инцидент, а не повод чистить лог.
  Query-строка на маршрутах, принимающих учётные данные (если такие остались как отклонение),
  вырезается на уровне обвязки.
- Уровень задаётся конфигурацией, не кодом; `DEBUG` в продуктиве только по согласованию.
- Строки с управляющими символами экранируются: `\n` в значении иначе подделывает соседнюю запись.

## 16. Что делает общая обвязка (middleware)

Правило, которое выполняют обработчики, выполняется только в тех, где о нём вспомнили. Поэтому
обвязка одна на продукт, подключается шаблоном сервиса, меняется в одном месте:

1. `request_id`: взять из `X-Request-Id`, если там валидный UUID, иначе создать UUID v7; вернуть
   заголовком и положить в контекст лога. Мусор в заголовке не причина отказать запросу.
2. `traceparent`: принять, продолжить, вернуть, пробросить в исходящие вызовы и события.
3. Тайминги и идентификация сервиса и экземпляра (§9.2).
4. Ограничения §1.3 и валидация заголовков, формат `Idempotency-Key`.
5. Извлечение учётных данных только из объявленного источника; проверка `Origin`; проверка
   живости сессии и классификация активности (§8.2).
6. Проверка адресации: неизвестный параметр query `400`, неверный метод `405` с `Allow`.
7. Валидация тела по закрытой схеме, сбор всех ошибок в один `422`, перевод сообщений
   валидатора на язык продукта.
8. Преобразование любого исключения в Problem Details (§6).
9. Удаление раскрывающих заголовков, установка обязательных (§9) и заголовков безопасности
   (§14.3).
10. Вычисление адреса клиента по доверенным прокси; лимиты.
11. Механизм идемпотентности (§10) целиком.

## 17. Повторы на стороне клиента

Единая политика для всех клиентов продукта, иначе при деградации они хором устраивают лавину:

- автоматически повторяются только чтения (`GET`, `search`, `count`) и изменяющие операции **с
  `Idempotency-Key`**; изменяющие без ключа автоматически не повторяются никогда;
- не более трёх попыток с задержкой 0,5 → 1 → 2 с и разбросом ±20 %; без разброса все
  клиенты, отказ которым пришёл одновременно, вернутся тоже одновременно и воспроизведут пик;
- `Retry-After` перекрывает расчёт безусловно;
- при `4xx`, кроме `429`, повтора нет: запрос неверен и останется неверным;
- при `session_expired` клиент приостанавливает очередь целиком, сохраняет её содержимое и
  продолжает после повторного входа;
- исчерпав попытки, клиент показывает ошибку с кнопкой повторить, не пустой экран и не вечный
  индикатор.

## 18. Контракт

- OpenAPI 3.x появляется до реализации или вместе с ней и живёт в репозитории контрактов;
  клиенты генерируются из него; расхождение спецификации с поведением дефект сервера.
- Для каждой операции: путь и метод, схема запроса с `additionalProperties: false`, схема
  успешного ответа со всеми полями, все возвращаемые коды, ссылка на общий компонент ошибки,
  обязательные заголовки, умолчание и максимум `limit`, закрытый список `expand`, требуется ли
  `Idempotency-Key` или `If-Match`, класс активности (`always`/`on_marker`), содержит ли ответ ПДн.
- Общие формы выносятся в компоненты и не копируются: `Problem`, `ValidationProblem`, `Page`,
  параметры пагинации, набор заголовков.
- Линтер контракта в CI проверяет: имена параметров пути и query по чёрному списку §2.3, формат
  `{id}` UUID, отсутствие `total` в страницах, наличие `Retry-After` у `429`/`503`, наличие всех
  обязательных заголовков, `snake_case` ключей и перечислений, отсутствие голых массивов на
  верхнем уровне, ссылку на общий `Problem` у каждого ответа `4xx`/`5xx`.
- Каталог `code` и `type` часть контракта; клиентский код ветвится только по значениям из него.

## 19. Отклонения

Отклонение от правила допустимо, если записано в документе продукта (раздел «Отклонения от
конвенции по API») таблицей: правило, что сделано иначе, почему, цена и условие, при котором
отклонение снимается. Типичные законные отклонения:

- версия API в заголовке вместо пути у продукта, где клиент и сервер один артефакт;
- cookie-сессия для страницы и `EventSource` по условиям §1.2;
- отсутствие набора §9.2 у одного процесса без распределённой трассировки;
- готовые подписи `_label` рядом с машинными значениями (§11);
- перевод чтения чувствительных ресурсов на `POST .../search` целиком (§2.3);
- отсутствие TLS на loopback-слушателе (§1.1).

Отклонение без записи блокер ревью.

## 20. Чек-лист перед изменением API

```markdown
- [ ] Путь /api/v<major>/<resources>[/{id}][/<action>], snake_case латиницей, вложенность ≤ 2 ресурсов
- [ ] В пути и query нет ПДн, идентификаторов субъектов, секретов, говорящих естественных ключей; {id} только UUID
- [ ] Фильтры по ПДн только через POST .../search
- [ ] Метод по семантике: GET без побочных эффектов и без тела; действия отдельным POST
- [ ] TLS везде, кроме loopback; учётные данные только заголовком; cookie только по условиям §1.2 с Origin-проверкой
- [ ] Неизвестный query-параметр 400; лишнее поле тела 422; все ошибки валидации в одном ответе с errors[] и полным field
- [ ] Ошибки RFC 9457: type URN, code, request_id, instance по шаблону; никаких стеков, SQL, хостов, версий, ПДн
- [ ] 2xx только при успехе; 201 с id и Location; 202 с задачей; 204 с заголовками; 404 вместо 403 на чужой объект
- [ ] X-Request-Id и явный Cache-Control в каждом ответе; Retry-After при 429/503; ETag на GET ресурса
- [ ] Версионируемый ресурс меняется только с If-Match: 428 без него, 412 при несовпадении
- [ ] Изменяющий POST, который клиент может повторить, объявил Idempotency-Key; правила таблицы §10.2 соблюдены
- [ ] Коллекция { items, next_cursor, has_more }, без total; limit с максимумом в контракте; выдача сужена правами
- [ ] Форматы по конвенции БД: _at с Z, _on, UUID v7, деньги и количества строкой, перечисления snake_case
- [ ] Вложенность ≤ 3, связи ссылками, expand закрытым списком, неограниченных встроенных списков нет
- [ ] Ответы с ПДн не кэшируются вне процесса; ПДн-списки под нижним максимумом limit
- [ ] Тело запроса не в логе; request_id в каждой строке; уровень логирования из конфигурации
- [ ] В конечном ответе нет Server, X-Powered-By, Via, версий; идентификатор экземпляра непрозрачен
- [ ] Клиентский IP по доверенным прокси; неизвестные входящие заголовки не пробрасываются
- [ ] Контракт обновлён: схемы, коды, заголовки, общие компоненты; линтер зелёный
- [ ] Каждое отклонение записано в таблице продукта с причиной, ценой и условием снятия
```
