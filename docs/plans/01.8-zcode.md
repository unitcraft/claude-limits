## Что известно (проверено живьём 2026-10-31)

- Логин: дом ZCode `~/.zcode` (`$ZCODE_HOME`); маркер содержимого — файл `v2/credentials.json`.
  Одна учётка на дом (как Codex).
- `credentials.json` — плоская карта; значения либо открытые, либо `enc:v1:IV.TAG.CT`
  (base64url): AES-256-GCM, IV 12 байт, тег 16. Ключ = `sha256(secret)`; secret — env
  `ZCODE_CREDENTIAL_SECRET`, если задан и непуст, иначе детерминированная строка
  `zcode-credential-fallback:{platform}:{homedir}:{username}` (значения как у node:
  `platform` = `win32|linux|darwin`, `homedir` = `os.homedir()`, `username` =
  `os.userInfo().username`; UTF-8 байты — на машине владельца homedir и username кириллические).
  Схема прочитана в установке ZCode (`zcode.cjs`: `createZCodeCredentialCipher`,
  `resolveCredentialSecret`) и подтверждена локальной расшифровкой (node, 2026-10-31).
- Читаются три значения: `zcodejwttoken` (JWT, поля `iat`/`sub`, БЕЗ `exp` — срок по файлу
  не узнать), `oauth:zai:access_token` (JWT), `oauth:zai:user_info` → `{user_id, email, name}`
  (идентичность карточки; e-mail — ключ учётки).
- **Потребление**: `GET https://zcode.z.ai/api/v1/mcp/usage` (origin по умолчанию; env
  `ZCODE_BASE_URL` переопределяет), заголовки `Authorization: Bearer <zcodejwttoken>` +
  `X-Bigmodel-Authorization: Bearer <oauth:zai:access_token>`. Ответ (схема — zod-схема самого
  ZCode): `{code, msg, data: {server_time, next_refresh_at, level, total_usage:
  {used, limit, remaining}}}`. Процент = `used/limit·100`; сброс = `next_refresh_at` (epoch
  сек). `code != 0` или HTTP 401 → учётка не отвечает.
- **План**: `GET https://zcode.z.ai/api/v1/zcode-plan/billing/current`, только
  `Authorization: Bearer <zcodejwttoken>`. Ответ: `data.plans[]` — берётся активный с
  наибольшим `priority`: `name`, `starts_at`, `ends_at`, `entitlements[]` (пока не показываются).
- Два запроса на цикл на учётку — в рамках правил опроса (минимум раз в минуту, общий
  429-backoff).
- **Токен не обновляем.** Refresh-токена в хранилище НЕТ; политика как у Codex — read-only.
  Отвергнутый логин показывается с советом запустить ZCode; расшифровка ничего не пишет.
- TLS: энвойнт за перехватывающим прокси владельца — работает системное хранилище корней
  (как у Claude-эндпоинта, README «Status»).

## Шифрование (чего не было в 01.7)

Токены лежат зашифрованными, поэтому чтение логина — это расшифровка AES-256-GCM на месте.
Выбор владельца 2026-10-31: чистые implementations в обоих — Python (stdlib, без внешних
модулей) и Nova (модуль `usage/zcode_cipher.nv`, без FFI). Оба проверяются одними NIST-векторами
(AES-256-GCM) и одним committed-блобом, выработанным node, — две реализации обязаны сойтись
на нём посимвольно. Секрет не печатается никогда; расшифрованное покидает модуль только как
`Secret` (Nova) / без печати (эталон). Направление encrypt в эталоне нужно только тестам
(раунд-трип); Nova — только decrypt.

Допущение (записано, не спрятано): `username` на Linux собирается из `USER`
(node берёт `getpwuid`); на машине владельца Windows, расхождение не наблюдалось. Проверяется
пробой при переносе на Linux.

## Строки

- «plan usage» — единственная квота-строка: процент `used/limit`, сброс `next_refresh_at`.
  Вид окна — новый `plan` (миграция 0004 расширяет и провайдера, и вид окна одной пересборкой).
- Строка плана (по слову владельца): ОТДЕЛЬНАЯ строка в обоих представлениях, как
  «extra usage balance» у Kimi. Терминал — текстовая строка после квот:
  `  plan: NAME, ends Nov 2 (2d 1h)`. Страница — своя строка `account-extra` под
  строками лимитов: `plan: NAME, ends 2026-11-02 03:00` (дата в поясе машины,
  `format.dateTimeIn`). На проводе — поле `plan: {name, ends_at_ms}` в аккаунте,
  отсутствует, когда `billing/current` не ответил; в слоте `org` плана НЕТ (уточнение
  владельца 2026-10-31: план и квота — разные строки). Смена неудавшегося чтения
  хранит предыдущий план, как хранит предыдущие строки. Значок сервиса `ZCode` — как
  `Kimi Code`/`Codex`.
- Серия истории `zcode:<адрес>|plan usage` пишется. ПРОГНОЗ ВКЛЮЧЁН (поправка 2026-10-31
  вечера, по вопросу владельца «почему нет прогнозных баров»): журнал приложения называет
  длину окна (`period_start..period_end`), она едет в `Window.span_sec` (0 = вид по
  умолчанию) через `live.limit_of` и `tick` (старт цикла в базе — от неё же), и
  `forecast_of` считает прогноз как у Codex по `window_seconds`. До поправки прогноз был
  выключен сознательно — API длины не называл; замер живьём: строка 66 %, окно 180988 с,
  прогноз «→ 363% at reset, ends ~17:37 (4h 26min)».

## Поправка 2026-10-31: настоящий расход — из лога приложения

Живая проверка показала: `mcp/usage`'s `total_usage` на start-плане ВСЕГДА 0 — это счётчик
MCP-инструментов, не плана. Настоящий расход — `billing/balance`
(`data.balances[]: used_units/total_units`, окно `period_start..period_end`, сброс
`expires_at`). Тот эндпоинт принимает свежий zcode-jwt, который приложение держит в памяти
и НЕ пишет в `credentials.json` (копия файла — от сентября; сервер отвечает
`parameter error`). Повторить запрос снаружи нельзя; но работающее приложение пишет КАЖДЫЙ
ответ в свой журнал целиком (`~/.zcode/v2/logs/<день>.log`, строки
`[usage-stats] billing/balance 请求完成 {json}`) — несколько раз в минуту. Эталон и бинарь
читают этот журнал: локально, без запросов, без токенов; опрос остаётся для живости учётки.
На проводе `plan`/окно `plan usage` отдаёт расход из журнала, когда он есть, иначе
показания mcp-опроса. Замечено живьём: журнал догоняет расход за секунды.

## Поправка 2026-10-31 (вторая): два тарифа — две группы строк

Скрин приложения («Usage remaining»: 5 hours / Weekly / ZCode MCP) — это КУПЛЕННЫЙ
индивидуальный тариф. Его окна: `GET api.z.ai/api/monitor/usage/quota/limit`, ОДИН bearer
— `oauth:zai:access_token` из файла (снаружи работает!), ответ `code: 200`,
`data.limits[]`: `unit` 3 → пятничное окно (`session`), 6 → неделя (`weekly_all`),
`percentage` — ИСПОЛЬЗОВАНО, `nextResetTime` — epoch мс. Акционный WEEKEND BUILD
остаётся из журнала (`plan usage`). Итог карточки: `session 5h` + `all 7d` (тариф) +
`plan usage` (акция) + строка плана. Замер живьём: 39% / 38% / 72%, прогноз акции
«→ 351% at reset, ends ~18:02»; прогнозы тариха появятся по мере истории
(сессии — минуты, недели — часы).
