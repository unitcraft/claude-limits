## 0. Решения

| № | решение | почему |
|---|---|---|
| 1 | **Два хранилища с разными ролями**: настройки — текстовый TOML, данные — DuckDB | настройки правит человек и кладёт в дотфайлы; данные — сотни тысяч замеров с запросами по времени |
| 2 | **Настройки — один файл `claude-limits.toml`**, источник истины; UI пишет в него атомарно | совместимо с эталонным скриптом; читается без программы; версионируется руками |
| 3 | **База — DuckDB**, один файл `claude-limits.duckdb`, расширения `core_functions` и `icu` прилинкованы статически | слово владельца 2026-09-06: настоящие типы (`TIMESTAMPTZ`, `BOOLEAN`, `ENUM`, `DECIMAL`), строгость на входе; спайк: линковка с Nova чистая, старт не страдает, цена — +36 МБ бинаря и полная сборка репозитория (§0а) |
| 4 | **Привязка — пакет `nova-duckdb`** (подплан 01.4), сборка из репозитория DuckDB по тегу, автозагрузка расширений выключена на уровне сборки и соединения | один бинарь без сети и без `~/.duckdb` |
| 5 | **Одно соединение, один владелец — файбер `store`**; все записи и чтения через него по `Chan`; `threads = 2` | решение 4 подплана 01.4 (`#thread_affine`); база не забирает ядра у виджета и сервера |
| 6 | **Запись тика — через Appender** во временные таблицы `stage_*` и один `INSERT … SELECT` в транзакции; точечные `UPDATE` — обычные | построчный `INSERT` в DuckDB ≈ 2 мс, Appender — микросекунды (спайк) |
| 7 | **Токены в базе не хранятся никогда**, ни в каком поле, ни в логе ошибок | README §Rules; база содержит почты и организации — файл `0600` на Linux |
| 8 | **Ретенция настраивается**: сырые замеры 30 дней, дневные свёртки 400 дней, занятость и блокировки — без срока; свёртки ≤ 30 дней считаются на лету | сырьё для графиков 24 ч / 7 д / 30 д; DuckDB агрегирует 138 тыс. строк за миллисекунды, хранить агрегат за текущий месяц незачем |
| 9 | **Инварианты, которых DuckDB не выражает** (каскады, частичные уникальные индексы), держит `store` и проверяют тесты | DuckDB поддерживает `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `CHECK`, `FOREIGN KEY` без `ON DELETE`-действий и без частичных индексов |
| 10 | **Миграции — пронумерованные SQL-файлы в бинаре**, версия и версия DuckDB в `schema_meta` | обычная практика; перед миграцией — бэкап (§5) |

## 0а. Спайк 2026-09-06: DuckDB статически в бинаре Nova (что решило выбор)

Полный вердикт — [`spikes/duckdb-static/VERDICT.md`](../../spikes/duckdb-static/VERDICT.md).

| что мерили | Windows | Linux (WSL) |
|---|---|---|
| компиляция амальгамации `duckdb.cpp` (655 k строк, `-O2`) | 11 мин, пик 3,5 ГБ RAM | 20 мин, пик 4,8 ГБ RAM |
| статическая библиотека | 119 МБ `.lib` | 62 МБ `.a` |
| бинарь C-теста / Nova-бинарь | 36,4 МБ / **36,8 МБ** (hello на Nova — 0,56 МБ) | 37,4 МБ полностью статический, 30 МБ после `strip` |
| конфликт CRT с рантаймом Nova (`/MT`) | **нет**: `nova build` слинковал, импорты только системные DLL | C-линковка `-static` прошла |
| холодный старт процесса | Nova-бинарь 660–870 мс первый запуск, далее 245–260 мс (hello — 215–270 мс) | — |
| открыть файл БД + соединение | 18–50 мс | 7–22 мс |
| 10 000 вставок по одной, prepared, одна транзакция | 19–21 с (≈2 мс/строка) | 26 с |
| 10 000 строк через Appender | 9–12 мс | 12 мс |
| выборка по диапазону с группировкой | 2 мс | 2–7 мс |
| строка в колонку `TIMESTAMP` | отвергнута ошибкой типа | отвергнута |

Вскрытое: амальгамация не содержит `core_functions` и `icu` (без них нет `date_trunc`,
`time_bucket`, `TIMESTAMPTZ`, а DuckDB при первом вызове идёт в интернет за расширением и держит
запрос 22 с) — отсюда решение собирать из репозитория со статическими расширениями (подплан 01.4);
построчная запись медленная — отсюда Appender; заголовки Windows требуют `WIN32_LEAN_AND_MEAN`;
`at` — зарезервированное слово.

## 1. Где лежат файлы

| что | Windows | Linux | переопределение |
|---|---|---|---|
| настройки `claude-limits.toml` | `%APPDATA%\claude-limits\` | `$XDG_CONFIG_HOME/claude-limits/` (по умолчанию `~/.config/claude-limits/`) | `--config PATH`; переменная `CLAUDE_LIMITS_CONFIG` |
| база `claude-limits.duckdb` (+ `claude-limits.duckdb.wal` во время записи) | `%LOCALAPPDATA%\claude-limits\` | `$XDG_DATA_HOME/claude-limits/` (`~/.local/share/claude-limits/`) | `--data-dir PATH`; `[storage] data_dir`; `CLAUDE_LIMITS_DATA` |
| временные файлы DuckDB `tmp/` | там же, подкаталог | там же | `SET temp_directory` ставит пакет при открытии; `~/.duckdb` не создаётся никогда |
| бэкапы `backup/claude-limits-YYYYMMDD-HHMM.duckdb` | там же, подкаталог | там же | `[storage] backups_keep = 5` |
| логи `claude-limits.log` | `%LOCALAPPDATA%\claude-limits\logs\` | `$XDG_STATE_HOME/claude-limits/` (`~/.local/state/claude-limits/`) | `--log PATH` |

В нормальной работе это один файл; в момент записи — два (`.wal` сливается в основной при
`CHECKPOINT` и корректном закрытии; после сбоя доигрывается при открытии). Переносить или копировать
базу — только вместе с `.wal` или после `CHECKPOINT`.

**Portable-режим**: если рядом с бинарём лежит `claude-limits.toml`, все каталоги — рядом с
бинарём (`./data/`, `./logs/`). Так работает эталонный скрипт, так удобно носить на флешке.

Права: на Linux каталоги `0700`, файлы `0600`. Каталоги Claude Code остаются **только для
чтения** (решение 6 плана 01): туда не пишется ничего, включая lock-файлы.

## 2. Настройки

### 2.1. Файл

Один TOML, все секции; поля с их значениями по умолчанию. Это **полный** список, планы 01, 01.1 и
01.3 ссылаются сюда:

```toml
# claude-limits.toml — settings. Written by the app on Save; comments below are regenerated.
schema = 1                                    # формат файла; бэкенд мигрирует старые

[[folders]]                                   # где искать логины Claude Code (план 01.1 §5.4)
path = "C:/accounts"          # тип (single/parent/empty) определяется содержимым

[[folders]]
path = "~/.claude"                            # ~, %VAR%, $VAR и UNC-пути WSL допустимы

[poll]
interval_sec = 300                            # пол 60 с — сервер отвечает 429 на частый опрос
min_interval_sec = 60                         # не редактируется из UI, защита от ошибки в файле
request_timeout_sec = 30

[thresholds]
warning = 70

[forecast]                                    # план 01.1 §2.7
enabled = true
work_days = ["mon", "tue", "wed", "thu", "fri"]
work_from = "09:00"
work_to = "19:00"
off_hours_rate = 0                            # % от рабочей скорости вне графика
rate_window_days = 3                          # по скольким последним рабочим дням считать скорость

[server]
bind = "127.0.0.1"
port = 7391
# access_token = "…"                          # обязателен при bind не на loopback
allow_lan = false                             # UI-тумблер; true требует access_token

[ui]                                          # общие для всех браузеров; личное — в localStorage
accounts_order = ["main@example.com", "work@example.org"]
hidden_accounts = []
hide_stale = false

[widget]

[history]
```

Что живёт **не здесь**: браузерные предпочтения (вид, стиль бара, период статистики, обратный
отсчёт) — в `localStorage` каждого браузера (план 01.1 §0); порядок учёток общий и потому здесь.

### 2.2. Чтение и запись

- **Чтение** при старте и при каждом тике опроса: если `mtime` файла изменился — перечитать,
  провалидировать, применить, событие `config` в SSE. Ошибка в файле — в лог и в шапку страницы
  (`config error: [poll] interval_sec must be a number`), продолжаем с предыдущими значениями.
- **Запись** из UI (`PUT /api/config`) и из меню виджета: бэкенд сливает изменения в текущий
  конфиг, валидирует, сериализует **канонически** (порядок секций как выше, комментарии
  регенерируются — пользовательские комментарии не сохраняются, это записано в шапке файла) и
  пишет `write_atomic` (`std/fs`: временный файл в том же каталоге, `fsync`, `rename`, `fsync`
  каталога; при обрыве оригинал цел). Перед записью прежний текст кладётся в `config_history`
  (§3.14).
- **Конфликт**: `PUT` несёт `If-Match: <хэш загруженного конфига>`; если файл менялся после того,
  как панель настроек его загрузила — `409`, панель предлагает перечитать.
- Валидация одна для старта и `PUT`; ошибки — `400 { field, message }` (тексты — план 01.1 §5).
- Секреты: `access_token` хранится в файле открытым текстом — это локальный файл `0600`, как
  `.credentials.json` у самого Claude Code. В логи и в `/api/config` он не попадает (в ответе —
  `access_token_set: true`).

## 3. База данных

### 3.1. Общее

- Файл `claude-limits.duckdb`, DuckDB v1.5.5 (тег сабмодуля пакета `nova-duckdb`), расширения
  `core_functions` и `icu` статически. При открытии пакет выставляет: `autoinstall_known_extensions
  = false`, `autoload_known_extensions = false`, `temp_directory = '<data_dir>/tmp'`,
  `TimeZone = 'UTC'`, `memory_limit`, `threads` из `[storage]`.
- **Дата и время — `TIMESTAMPTZ`** (микросекунды, UTC в сессии), в Nova — `Timestamp` (нс, пакет
  пересчитывает ×1000 без потери). Имена таких колонок заканчиваются на `_at`. Календарный день
  человека — `DATE`, вычисляется `(at AT TIME ZONE '<rollup_tz>')::DATE` через `icu`; пояс
  записан в `schema_meta.rollup_tz` (§3.13). Миллисекунды не нужны: точность опроса — минуты.
- **Типы**: `BOOLEAN`, `TINYINT`/`INTEGER`/`BIGINT`, `DECIMAL`, `ENUM` для закрытых списков,
  `VARCHAR`. Строгость — свойство DuckDB: строка в `TIMESTAMPTZ` или `200` в `TINYINT` — ошибка
  на входе (спайк). `CHECK` — для диапазонов и согласованности интервалов.
- **Ключи и связи**: `PRIMARY KEY`, `UNIQUE`, `FOREIGN KEY … REFERENCES` — есть и проверяются.
  **Нет** `ON DELETE CASCADE/SET NULL` и частичных уникальных индексов: удаление учётки — явная
  транзакция (§3.15), инвариант «одна открытая запись на каталог» держит `store` и проверяет тест.
  Индексы DuckDB (ART) нужны только для `UNIQUE`/`PK`; выборки по диапазону времени быстры за счёт
  зон-карт по колонкам, отдельные индексы по времени не создаются.
- **Идентификаторы** — `INTEGER`/`BIGINT` из `SEQUENCE` (`CREATE SEQUENCE … ; DEFAULT nextval(…)`).
- **Запись** — идемпотентная: справочники `INSERT … ON CONFLICT (…) DO UPDATE SET last_seen_at =
  excluded.last_seen_at, …`; факты — через Appender в `stage_*` и `INSERT INTO … SELECT … ON CONFLICT
  DO NOTHING`; почта нормализуется в нижний регистр до записи. Все запросы — `sql\`…\`` с параметрами.
- **`at` — зарезервированное слово** в DuckDB; колонка замера называется `sampled_at`.

### 3.4. `folder` — папки из конфига, как их видит обнаружение

```sql
CREATE SEQUENCE folder_id_seq;
CREATE TABLE folder (
  id            INTEGER PRIMARY KEY DEFAULT nextval('folder_id_seq'),
```

### 3.6. `account` — учётка (одна на почту)

```sql
CREATE SEQUENCE account_id_seq;
CREATE TABLE account (
  id                INTEGER PRIMARY KEY DEFAULT nextval('account_id_seq'),
  email             VARCHAR NOT NULL UNIQUE,
  org_name          VARCHAR,
  org_uuid          UUID,
  subscription_type VARCHAR,                      -- .credentials.json: subscriptionType
  rate_limit_tier   VARCHAR,                      -- .credentials.json: rateLimitTier
  color_slot        TINYINT NOT NULL,             -- закреплённый цвет серии (план 01.1 §8), не меняется
  first_seen_at     TIMESTAMPTZ NOT NULL,
  last_seen_at      TIMESTAMPTZ NOT NULL,
  CHECK (last_seen_at >= first_seen_at),
  CHECK (email = lower(email))                    -- нормализуется до записи
);
```

Токена, `refreshToken`, `expiresAt` здесь **нет**. Состояние токена — в `occupancy.token_state` и
`poll.outcome`; сам срок читается из файла в момент опроса и не хранится.

### 3.7. `occupancy` — кто сидел в каталоге когда (журнал занятости)

```sql
CREATE SEQUENCE occupancy_id_seq;
CREATE TABLE occupancy (
  id           BIGINT PRIMARY KEY DEFAULT nextval('occupancy_id_seq'),
  login_dir_id INTEGER NOT NULL REFERENCES login_dir(id),
  account_id   INTEGER REFERENCES account(id),   -- NULL = логина нет (файла нет или он пуст)
  token_state  token_state NOT NULL,
  started_at   TIMESTAMPTZ NOT NULL,
  ended_at     TIMESTAMPTZ,                       -- NULL = текущая запись
  CHECK (ended_at IS NULL OR ended_at >= started_at)
);
```

Инвариант «не больше одной строки с `ended_at IS NULL` на `login_dir_id`» держит `store`: закрытие
и открытие — в одной транзакции; тест §8 проверяет запросом `SELECT login_dir_id FROM occupancy
WHERE ended_at IS NULL GROUP BY 1 HAVING count(*) > 1` — пусто. Правило записи: при каждом
обнаружении для каталога читаются почта и состояние токена; если пара `(account_id, token_state)`
отличается от открытой записи — открытая закрывается `ended_at = now()`, открывается новая. Смена
`ok → expired` — тоже новая запись (серый хвост «токен протух» на полосе занятости, план 01.1 §7.3).

### 3.8. `poll` — журнал обращений к эндпоинту

```sql
CREATE SEQUENCE poll_id_seq;
CREATE TABLE poll (
  id              BIGINT PRIMARY KEY DEFAULT nextval('poll_id_seq'),
  account_id      INTEGER NOT NULL REFERENCES account(id),
  polled_at       TIMESTAMPTZ NOT NULL,
  outcome         poll_outcome NOT NULL,

```

### 3.9. `limit_window` — измерение «окно лимита учётки»

```sql
CREATE SEQUENCE limit_window_id_seq;
CREATE TABLE limit_window (
  id            INTEGER PRIMARY KEY DEFAULT nextval('limit_window_id_seq'),
  account_id    INTEGER NOT NULL REFERENCES account(id),
  kind          window_kind NOT NULL,
  model         VARCHAR,                          -- display_name модели для weekly_scoped, иначе NULL
  first_seen_at TIMESTAMPTZ NOT NULL,
  last_seen_at  TIMESTAMPTZ NOT NULL,             -- модель исчезла из ответа → перестаёт обновляться, история остаётся
  UNIQUE (account_id, kind, model),
  CHECK (last_seen_at >= first_seen_at),
  CHECK ((kind = 'weekly_scoped') = (model IS NOT NULL))
);
```

### 3.10. `window_cycle` — один проход окна (от сброса до сброса)

Сброс окна — факт, а не эвристика по перепаду процента: каждый `resets_at`, который эндпоинт
называет для окна, — отдельный цикл. Замеры ссылаются на цикл, границы окна хранятся один раз.

```sql
CREATE SEQUENCE window_cycle_id_seq;
CREATE TABLE window_cycle (
  id         BIGINT PRIMARY KEY DEFAULT nextval('window_cycle_id_seq'),
  window_id  INTEGER NOT NULL REFERENCES limit_window(id),
  starts_at  TIMESTAMPTZ NOT NULL,                -- resets_at − длина окна (5 ч / 7 сут)
  resets_at  TIMESTAMPTZ NOT NULL,
  UNIQUE (window_id, resets_at),
  CHECK (resets_at > starts_at)
);
```

Новый `resets_at` в ответе → `INSERT … ON CONFLICT DO NOTHING`; вертикали сбросов на графиках,
границы для скорости прогноза и число сбросов за день читаются отсюда.

### 3.11. `sample` — замер (история для графиков и прогноза)

Строка на окно на удачный опрос. При интервале 300 с — 288 строк в сутки на окно.

```sql
CREATE TABLE sample (
  window_id       INTEGER NOT NULL REFERENCES limit_window(id),
  sampled_at      TIMESTAMPTZ NOT NULL,            -- время опроса (poll.polled_at)
  cycle_id        BIGINT  NOT NULL REFERENCES window_cycle(id),
  percent         TINYINT NOT NULL CHECK (percent BETWEEN 0 AND 100),
  locked          BOOLEAN NOT NULL DEFAULT false,
  locked_reason   VARCHAR,
  server_severity VARCHAR,                         -- severity, как его назвал эндпоинт; наша — по порогам
  is_active       BOOLEAN,                         -- limits[].is_active: это окно сейчас ограничивает
  PRIMARY KEY (window_id, sampled_at)
);
```

Запись тика: Appender → `stage_sample` (та же структура, без ключей) → `INSERT INTO sample SELECT …
FROM stage_sample ON CONFLICT DO NOTHING; DELETE FROM stage_sample;` в той же транзакции.
Дедупликации по значению нет: сетка замеров регулярная, и пропуск строки означает «нет данных»,
что графику важно.

### 3.12. `lock_period` — интервалы блокировки

```sql
CREATE SEQUENCE lock_period_id_seq;
CREATE TABLE lock_period (
  id         BIGINT PRIMARY KEY DEFAULT nextval('lock_period_id_seq'),
  window_id  INTEGER NOT NULL REFERENCES limit_window(id),
  cycle_id   BIGINT  NOT NULL REFERENCES window_cycle(id),
  started_at TIMESTAMPTZ NOT NULL,                 -- первый замер с locked
  ended_at   TIMESTAMPTZ,                          -- первый замер без locked после; NULL = идёт сейчас
  reason     VARCHAR,                              -- locked_reason или 'percent_100'
  CHECK (ended_at IS NULL OR ended_at >= started_at)
);
```

Открывается и при `percent = 100` без `locked_reason` (`reason = 'percent_100'`): дизайн считает
100 % красной плашкой. Инвариант «один открытый период на окно» — как в §3.7, держит `store`.

### 3.13. `daily_rollup` — дневные свёртки старше `keep_days`

За последние `keep_days` агрегаты считаются на лету из `sample` (`time_bucket(INTERVAL 1 DAY,
sampled_at AT TIME ZONE rollup_tz)`, `max`, `avg`, `sum(locked)`); свёртка нужна только чтобы годовая
история переживала удаление сырья.

```sql
CREATE TABLE daily_rollup (
  window_id      INTEGER NOT NULL REFERENCES limit_window(id),
  day            DATE    NOT NULL,                 -- календарный день в поясе schema_meta.rollup_tz
  samples        INTEGER NOT NULL,
  peak_percent   TINYINT NOT NULL,
  avg_percent    DECIMAL(5,2) NOT NULL,
  minutes_locked INTEGER NOT NULL DEFAULT 0,
  resets         INTEGER NOT NULL DEFAULT 0,       -- сколько раз окно сбрасывалось за день
  PRIMARY KEY (window_id, day)
);
```

Пересчёт: перед удалением сырья за день — свёртка этого дня одним `INSERT … SELECT … ON CONFLICT DO
UPDATE`. Если пояс машины отличается от `schema_meta.rollup_tz`, при старте свёртки за ещё
хранящиеся дни пересчитываются, `rollup_tz` обновляется, более старые остаются как есть с
пометкой в логе.

### 3.14. `config_history` и `notification`

```sql
CREATE SEQUENCE config_history_id_seq;
CREATE TABLE config_history (

CREATE SEQUENCE notification_id_seq;                -- зарезервировано под Ф.5, до неё пусто
```

### 3.15. Удаление учётки (`claude-limits forget <email>`) — явная транзакция

DuckDB не каскадирует, порядок фиксирован в `storage/repo.nv` и проверяется тестом:

```sql
BEGIN;
UPDATE occupancy SET account_id = NULL WHERE account_id = $1;        -- история каталога остаётся
DELETE FROM notification WHERE account_id = $1 OR window_id IN (SELECT id FROM limit_window WHERE account_id = $1);
DELETE FROM daily_rollup  WHERE window_id IN (SELECT id FROM limit_window WHERE account_id = $1);
DELETE FROM lock_period   WHERE window_id IN (SELECT id FROM limit_window WHERE account_id = $1);
DELETE FROM sample        WHERE window_id IN (SELECT id FROM limit_window WHERE account_id = $1);
DELETE FROM window_cycle  WHERE window_id IN (SELECT id FROM limit_window WHERE account_id = $1);
DELETE FROM limit_window  WHERE account_id = $1;
DELETE FROM poll          WHERE account_id = $1;
DELETE FROM account       WHERE id = $1;
COMMIT;
```

Удаление папки из конфига учётку **не удаляет** — она нужна статистике по папкам.

### 3.16. Чего в базе нет и почему

- **Прогноз** — вычисляется по запросу из `sample` за окно скорости и кэшируется в памяти на тик.
- **Снимок «сейчас»** — в памяти файбера `store`; при старте восстанавливается из последних строк
  `sample` и `poll`, чтобы страница не была пустой до первого опроса (с пометкой давности).
- **Разрывы данных** — выводятся из `poll`/`sample` при запросе (`gap` = промежуток между соседними
  `sampled_at` больше `2 × interval_sec`).
- **Пользователи и сессии** — один токен доступа в конфиге (план 01 §9).
- **Настройки** — в TOML (§2), не в базе; база не должна становиться вторым источником истины.

### 3.17. Представления для отчётов и отладки

```sql
CREATE VIEW v_current_occupancy AS
  SELECT ld.path AS dir, ld.name, a.email, o.token_state, o.started_at
  FROM occupancy o JOIN login_dir ld ON ld.id = o.login_dir_id
  LEFT JOIN account a ON a.id = o.account_id
  WHERE o.ended_at IS NULL;

CREATE VIEW v_latest_sample AS
  SELECT s.* FROM sample s
  QUALIFY row_number() OVER (PARTITION BY window_id ORDER BY sampled_at DESC) = 1;

-- время в поясе машины для отладки в CLI duckdb (в приложении не используется)
CREATE VIEW v_sample_local AS
  SELECT a.email, w.kind, w.model, s.percent, s.locked,
         s.sampled_at AT TIME ZONE (SELECT value FROM schema_meta WHERE key = 'rollup_tz') AS sampled_local,
         c.resets_at  AT TIME ZONE (SELECT value FROM schema_meta WHERE key = 'rollup_tz') AS resets_local
  FROM sample s JOIN limit_window w ON w.id = s.window_id
  JOIN account a ON a.id = w.account_id JOIN window_cycle c ON c.id = s.cycle_id;
```

## 4. Запросы, которые обслуживает база

| потребитель | запрос | таблицы |
|---|---|---|
| `/api/snapshot` при старте | `v_latest_sample` + последний `poll` учётки | `sample`, `poll` |
| `/api/history?by=account` | `sample WHERE window_id IN (…) AND sampled_at BETWEEN $1 AND $2`, `step` — `time_bucket(INTERVAL '<step>', sampled_at)` с `last(percent ORDER BY sampled_at)`; `lock_period` за период; разрывы — из `poll` | `sample`, `lock_period`, `poll` |
| `/api/history?by=folder` | `occupancy` каталога за период → для каждого отрезка `sample` его учётки; при `30d` для сессии — дневные пики `time_bucket(INTERVAL 1 DAY, sampled_at AT TIME ZONE rollup_tz)` | `occupancy`, `sample` |
| прогноз (план 01.1 §2.7) | `sample` окна за `rate_window_days` рабочих дней внутри текущего `window_cycle` | `sample`, `window_cycle` |
| плитки статистики | `lock_period` за 7 д; `max(percent)` сессии; `avg` по живым; смены почты — `occupancy` за 30 д | `lock_period`, `sample`, `occupancy` |
| `--once` | ничего не пишет и не читает | — |
| `claude-limits export --range 30d --format csv\|json` | `COPY (SELECT …) TO '<file>' (FORMAT CSV)` / `(FORMAT JSON)` — встроенный экспорт DuckDB | `sample`, `occupancy`, `poll` |

Запись за один тик — одна транзакция: `poll` + Appender в `stage_sample` + перенос в `sample` +
переходы `lock_period` + при необходимости `occupancy`/`account`/`limit_window`/`window_cycle`.
Ожидаемо 20–60 мс на тик (десяток точечных `UPDATE`/`INSERT` по ~2 мс плюс Appender), раз в 5
минут — незаметно.

## 5. Обслуживание

- **Checkpoint** — `CHECKPOINT` после каждой транзакции тика: `.wal` сливается в файл, база на
  диске всегда целостна и копируема.
- **Ретенция** — раз в сутки после полуночи по `rollup_tz`: свёртка дня, уходящего за
  `keep_days`, затем `DELETE FROM sample WHERE sampled_at < now() − INTERVAL '<keep_days> days'`,
  то же для `poll`; `daily_rollup` старше `rollup_keep_days`; `config_history` сверх
  `config_versions_keep`; затем `CHECKPOINT`. Место внутри файла DuckDB переиспользует сама;
  отдельного `VACUUM` нет — при разрастании файла вдвое против данных делается `EXPORT DATABASE` →
  новый файл → `IMPORT DATABASE` (раз в год, если вообще понадобится).
- **Бэкап** — `CHECKPOINT` и копия файла в `backup/` перед каждой миграцией и раз в неделю;
  хранится `backups_keep` штук. Копия без `.wal` после `CHECKPOINT` целостна.
- **Целостность** — DuckDB проверяет заголовок и чексуммы блоков при открытии; ошибка открытия →
  файл переименовывается в `claude-limits.corrupt-<stamp>.duckdb`, поднимается последний бэкап,
  строка в лог и в шапку страницы. История без бэкапа теряется, настройки — нет: они в TOML.
- **Миграции** — `migrations/0001_init.sql`, `0002_….sql` из `embed_dir("migrations")`; по одной в
  транзакции с обновлением `schema_meta.schema_version`; бинарь со старой схемой, открывший новую
  базу, отказывается стартовать с понятным текстом. Смена версии DuckDB в пакете → запись
  `duckdb_version`; формат файла DuckDB стабилен между минорными версиями с 1.0, при мажорной —
  `EXPORT`/`IMPORT` через бэкап.
- **Размер** — при `keep_days = 30` и 4 учётках ≈ 10–15 МБ; в `/api/health` есть `db_size_bytes`,
  страница показывает его в настройках.

## 6. Приватность и безопасность данных

- В базе: почты, названия организаций, `subscription_type`, `rate_limit_tier`, пути каталогов,
  проценты, времена. **Нет**: токенов, `refreshToken`, `expiresAt`, содержимого `.claude.json`
  сверх названных полей, заголовков HTTP.
- `poll.error` и логи обрезаются до 200 символов и проходят фильтр: строка, похожая на
  bearer-токен (`sk-ant-…`, JWT-подобная), заменяется на `***` до записи.
- `config_history.toml` хранится с замаскированным `access_token`.
- Шифрования на диске нет — сознательно: в базе нет ничего, чего нет в `.claude.json` рядом;
  шифрование DuckDB (`ATTACH … ENCRYPTION_KEY`) добавило бы ключ, который негде хранить.
- Файлы `0600`; каталог данных не индексируется поисковиками (Windows —
  `FILE_ATTRIBUTE_NOT_CONTENT_INDEXED`).
- База никогда не ходит в сеть: автозагрузка расширений выключена на уровне сборки и соединения
  (подплан 01.4), тест держит мок `Net` с нулём вызовов.

## 8. Приёмка (часть Ф.1 и Ф.2 плана 01)

1. Конфиг: путь по §1 на обеих ОС; portable-режим включается файлом рядом с бинарём; `--config` и
   переменная окружения переопределяют. Файл с ошибкой не роняет процесс, ошибка видна в логе и в
   шапке.
2. Запись конфига: `PUT` даёт байт-в-байт канонический TOML; повторный `PUT` без изменений — тот
   же файл; `If-Match` устаревший → `409`; перед записью строка в `config_history` с `***` вместо
   токена; `write_atomic` — при убитом процессе посреди записи старый файл цел (тест с моком `Fs`).
3. Схема: `0001_init.sql` создаёт типы, последовательности, таблицы §3; строка в `TIMESTAMPTZ`,
   `200` в `TINYINT`, `ended_at < started_at`, почта с заглавной буквой — ошибка типа или `CHECK`;
   `forget <email>` (§3.15) оставляет `occupancy` с `account_id = NULL` и удаляет всё остальное;
   `EXPLAIN` запросов §4 читает только нужные колонки (колоночные срезы, без полного скана строк).
4. Запись тика: одна транзакция; при инъекции ошибки на переносе из `stage_sample` не остаётся
   `poll` без пары; после тика `.wal` пуст (был `CHECKPOINT`).
5. Занятость: смена почты в `.claude.json` фикстуры → закрытая и новая запись; `ok → expired` →
   новая запись; запрос из §3.7 на «две открытые» пуст.
6. Блокировки: последовательность замеров `0,100,100,0` даёт один `lock_period`; `percent = 100`
   без `locked_reason` — период с `reason = 'percent_100'`.
7. Свёртки и ретенция: фикстура на 35 дней → после обслуживания `sample` содержит 30 дней,
   `daily_rollup` — 5 дней, `peak_percent` совпадает с `max` по удалённым замерам (снимается до
   удаления); смена пояса машины между запусками пересчитывает свёртки и обновляет `rollup_tz`.
8. Целостность: испорченный файл базы → переименован, поднят бэкап, строка в логе; без бэкапа —
   пустая база, настройки целы.
9. Приватность: `grep` по файлу базы и логам на подстроки токенов из фикстур — ноль совпадений
   (обратная проба: нарочно записать токен в `poll.error` → тест краснеет); за прогон тестов ни
   одного сетевого вызова из базы; `~/.duckdb` не появляется.
10. Производительность: тик с 4 учётками (≈16 замеров) — ≤ 100 мс; `/api/history?range=30d` —
    ≤ 50 мс на 138 000 строк; файл на 30 дней синтетики ≤ 15 МБ.
