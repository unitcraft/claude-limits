Факты сверены 2026-09-06: спайк [`spikes/duckdb-static/`](../../spikes/duckdb-static/VERDICT.md);
атомарная запись файла — `std/src/fs/fs.nv:674 write_atomic`; TOML — `std/src/encoding/toml.nv`;

std — `Timestamp` (нс), `Date`, `TimeZone`, `Duration`; `int128` — `std/src/math/int128.nv`.

## 0. Решения

| № | решение | почему |
|---|---|---|
| 1 | **Два хранилища с разными ролями**: настройки — текстовый TOML, данные — DuckDB | настройки правит человек и кладёт в дотфайлы; данные — сотни тысяч замеров с запросами по времени |
| 2 | **Настройки — один файл `claude-limits.toml`**, источник истины; UI пишет в него атомарно | совместимо с эталонным скриптом; читается без программы; версионируется руками |
| 3 | **База — DuckDB**, один файл `claude-limits.duckdb`, расширения `core_functions` и `icu` прилинкованы статически | слово владельца 2026-09-06: настоящие типы (`TIMESTAMPTZ`, `BOOLEAN`, `DATE`, `DECIMAL`, `UUID`; перечисления — `VARCHAR` + `CHECK` по конвенции §4), строгость на входе; спайк: линковка с Nova чистая, старт не страдает, цена — +36 МБ бинаря и полная сборка репозитория (§0а) |
| 4 | **Привязка — пакет `nova-duckdb`** (подплан 01.4), сборка из репозитория DuckDB по тегу, автозагрузка расширений выключена на уровне сборки и соединения | один бинарь без сети и без `~/.duckdb` |
| 5 | **Одно соединение, один владелец — файбер `store`**; все записи и чтения через него по `Chan`; `threads = 2` | решение 4 подплана 01.4 (`#thread_affine`); база не забирает ядра у виджета и сервера |
| 6 | **Запись тика — через Appender** во временные таблицы `stage_*` и один `INSERT … SELECT` в транзакции; точечные `UPDATE` — обычные | построчный `INSERT` в DuckDB ≈ 2 мс, Appender — микросекунды (спайк) |
| 7 | **Ключи — UUID v7 из `Uuid.v7()`**, единый служебный набор колонок у всех таблиц предметной области, автор — идентичность экземпляра приложения | конвенция §3 и §6: не угадывать на старте, будет ли второй источник записей или второй автор; сегодня оба — один процесс, завтра — агент на другой машине (Docker-сценарий плана 01 §9) |
| 8 | **Токены в базе не хранятся никогда**, ни в каком поле, ни в логе ошибок; почты и пути каталогов — ПДн, ведётся реестр (§10) | README §Rules; конвенция §13 |
| 9 | **Ретенция настраивается**: сырые замеры 30 дней, дневные свёртки 400 дней, занятость и блокировки — без срока; свёртки ≤ 30 дней считаются на лету | сырьё для графиков 24 ч / 7 д / 30 д; DuckDB агрегирует 138 тыс. строк за миллисекунды |
| 10 | **Инварианты, которых DuckDB не выражает** (каскады, частичные уникальные индексы), держит `store` и проверяют тесты | DuckDB поддерживает `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `CHECK`, `FOREIGN KEY` без `ON DELETE`-действий и без частичных индексов; записано в §9 |
| 11 | **Миграции — пронумерованные SQL-файлы в бинаре**, версия схемы и версия DuckDB в `schema_meta` | конвенция §15; перед миграцией — бэкап (§5) |

## 0а. Спайк 2026-09-06: DuckDB статически в бинаре Nova (что решило выбор)

Полный вердикт — [`spikes/duckdb-static/VERDICT.md`](../../spikes/duckdb-static/VERDICT.md).

| что мерили | Windows | Linux (WSL) |
|---|---|---|
| компиляция амальгамации `duckdb.cpp` (655 k строк, `-O2`) | 11 мин, пик 3,5 ГБ RAM | 20 мин, пик 4,8 ГБ RAM |
| статическая библиотека | 119 МБ `.lib` | 62 МБ `.a` |
| бинарь C-теста / Nova-бинарь | 36,4 МБ / **36,8 МБ** (hello на Nova — 0,56 МБ) | 37,4 МБ полностью статический, 30 МБ после `strip` |
| конфликт CRT с рантаймом Nova (`/MT`) | **нет**: `nova build` слинковал, импорты только системные DLL | C-линковка `-static` прошла |
| холодный старт процесса | Nova-бинарь 660–870 мс первый запуск, далее 245–260 мс (hello — 215–270 мс) | — |
| открыть файл БД + соединение | 18–50 мс | 7–22 мс |
| 10 000 вставок по одной, prepared, одна транзакция | 19–21 с (≈2 мс/строка) | 26 с |
| 10 000 строк через Appender | 9–12 мс | 12 мс |
| выборка по диапазону с группировкой | 2 мс | 2–7 мс |
| строка в колонку `TIMESTAMP` | отвергнута ошибкой типа | отвергнута |

Вскрытое: амальгамация не содержит `core_functions` и `icu` (без них нет `date_trunc`,
`time_bucket`, `TIMESTAMPTZ`, а DuckDB при первом вызове идёт в интернет за расширением и держит
запрос 22 с) — отсюда решение собирать из репозитория со статическими расширениями (подплан 01.4);
построчная запись медленная — отсюда Appender; заголовки Windows требуют `WIN32_LEAN_AND_MEAN`;
`at` — зарезервированное слово.

## 1. Где лежат файлы

| что | Windows | Linux | переопределение |
|---|---|---|---|
| настройки `claude-limits.toml` | `%APPDATA%\claude-limits\` | `$XDG_CONFIG_HOME/claude-limits/` (по умолчанию `~/.config/claude-limits/`) | `--config PATH`; переменная `CLAUDE_LIMITS_CONFIG` |
| база `claude-limits.duckdb` (+ `claude-limits.duckdb.wal` во время записи) | `%LOCALAPPDATA%\claude-limits\` | `$XDG_DATA_HOME/claude-limits/` (`~/.local/share/claude-limits/`) | `--data-dir PATH`; `[storage] data_dir`; `CLAUDE_LIMITS_DATA` |
| временные файлы DuckDB `tmp/` | там же, подкаталог | там же | `SET temp_directory` ставит пакет при открытии; `~/.duckdb` не создаётся никогда |
| бэкапы `backup/claude-limits-YYYYMMDD-HHMM.duckdb` | там же, подкаталог | там же | `[storage] backups_keep = 5` |
| логи `claude-limits.log` | `%LOCALAPPDATA%\claude-limits\logs\` | `$XDG_STATE_HOME/claude-limits/` (`~/.local/state/claude-limits/`) | `--log PATH` |

В нормальной работе это один файл; в момент записи — два (`.wal` сливается в основной при
`CHECKPOINT` и корректном закрытии; после сбоя доигрывается при открытии). Переносить или копировать
базу — только вместе с `.wal` или после `CHECKPOINT`.

**Portable-режим**: если рядом с бинарём лежит `claude-limits.toml`, все каталоги — рядом с
бинарём (`./data/`, `./logs/`). Так работает эталонный скрипт, так удобно носить на флешке.

Права: на Linux каталоги `0700`, файлы `0600`. Каталоги Claude Code остаются **только для
чтения** (решение 6 плана 01): туда не пишется ничего, включая lock-файлы.

## 2. Настройки

### 2.1. Файл

Один TOML, все секции; поля с их значениями по умолчанию. Это **полный** список, планы 01, 01.1 и
01.3 ссылаются сюда:

```toml
# claude-limits.toml — settings. Written by the app on Save; comments below are regenerated.
schema = 1                                    # формат файла; бэкенд мигрирует старые

[[folders]]                                   # где искать логины Claude Code (план 01.1 §5.4)
path = "C:/accounts"          # тип (single/parent/empty) определяется содержимым

[[folders]]
path = "~/.claude"                            # ~, %VAR%, $VAR и UNC-пути WSL допустимы

[poll]
interval_sec = 300                            # пол 60 с — сервер отвечает 429 на частый опрос
min_interval_sec = 60                         # не редактируется из UI, защита от ошибки в файле
request_timeout_sec = 30

[thresholds]
warning = 70

[forecast]                                    # план 01.1 §2.7
enabled = true
work_days = ["mon", "tue", "wed", "thu", "fri"]
work_from = "09:00"
work_to = "19:00"
off_hours_rate = 0                            # % от рабочей скорости вне графика
rate_window_days = 3                          # по скольким последним рабочим дням считать скорость

[server]
bind = "127.0.0.1"

# access_token = "…"                          # обязателен при bind не на loopback
allow_lan = false                             # UI-тумблер; true требует access_token

[ui]                                          # общие для всех браузеров; личное — в localStorage
accounts_order = ["main@example.com", "work@example.org"]
hidden_accounts = []
hide_stale = false

[widget]

[history]
```

отсчёт) — в `localStorage` каждого браузера (план 01.1 §0); порядок учёток общий и потому здесь.

### 2.2. Чтение и запись

- **Чтение** при старте и при каждом тике опроса: если `mtime` файла изменился — перечитать,
  провалидировать, применить, событие `config` в SSE. Ошибка в файле — в лог и в шапку страницы
  (`config error: [poll] interval_sec must be a number`), продолжаем с предыдущими значениями.
- **Запись** из UI (`PUT /api/config`) и из меню виджета: бэкенд сливает изменения в текущий
  конфиг, валидирует, сериализует **канонически** (порядок секций как выше, комментарии
  регенерируются — пользовательские комментарии не сохраняются, это записано в шапке файла) и
  пишет `write_atomic` (`std/fs`: временный файл в том же каталоге, `fsync`, `rename`, `fsync`
  каталога; при обрыве оригинал цел). Перед записью прежний текст кладётся в `config_history`
  (§3.14).
- **Конфликт**: `PUT` несёт `If-Match: <хэш загруженного конфига>`; если файл менялся после того,
  как панель настроек его загрузила — `409`, панель предлагает перечитать.
- Валидация одна для старта и `PUT`; ошибки — `400 { field, message }` (тексты — план 01.1 §5).
- Секреты: `access_token` хранится в файле открытым текстом — это локальный файл `0600`, как
  `.credentials.json` у самого Claude Code. В логи и в `/api/config` он не попадает (в ответе —
  `access_token_set: true`).

## 3. База данных

### 3.1. Общее

- Файл `claude-limits.duckdb`, DuckDB v1.5.5 (тег сабмодуля пакета `nova-duckdb`), расширения
  `core_functions` и `icu` статически. При открытии пакет выставляет: `autoinstall_known_extensions
  = false`, `autoload_known_extensions = false`, `temp_directory = '<data_dir>/tmp'`,
  `TimeZone = 'UTC'`, `memory_limit`, `threads` из `[storage]`.
- **Дата и время — `TIMESTAMPTZ`** (микросекунды, UTC в сессии), в Nova — `Timestamp` (нс, пакет
  пересчитывает ×1000 без потери). Имена колонок моментов — `_at`. Календарный день человека —
  `DATE` с суффиксом `_on`, вычисляется `(… AT TIME ZONE '<rollup_tz>')::DATE` через `icu`; пояс
  записан в `schema_meta.rollup_tz` (§3.13). В API — ISO 8601 с `Z` (подплан 01.3 §0).
- **Ключи.** Первичный ключ каждой таблицы предметной области — `id UUID` **версии 7**, значение
  создаёт приложение вызовом `Uuid.v7()` (`std/identifiers/uuid.nv`); серверного `DEFAULT` у `id`
  нет. Естественная уникальность — отдельным `UNIQUE` с нормализацией в `CHECK`. Ключей внешних
  систем в схеме нет: почта учётки и путь каталога — свойства самих сущностей, а не идентификаторы
  чужих записей, поэтому таблица `external_ref` не заводится (конвенция §3.2).
- **Служебный набор** у каждой таблицы предметной области (конвенция §6): `id`, `created_at`,
  `updated_at`, `deleted_at` (где применимо мягкое удаление), `created_by`, `updated_by`. Автор —
  **идентичность экземпляра приложения**: UUID v7, создаваемый при первом старте и хранимый в
  `schema_meta.app_instance_id`; при появлении второго автора (агент с другой машины, правка из UI
  под учётной записью) значение станет его идентичностью без смены схемы. `updated_at`/`updated_by`
  выставляет слой `storage/repo.nv` в той же операции, что и данные. В DDL ниже набор помечен
  комментарием `служебный набор (конвенция §6)`; в `0001_init.sql` он выписан полностью.
- **Типы**: `BOOLEAN`, `TINYINT`/`INTEGER`/`BIGINT`, `DECIMAL`, `VARCHAR`, `UUID`; перечисления —
  **`VARCHAR(32)` с `CHECK (… IN (…))`**, не `ENUM` (конвенция §4). Строгость — свойство DuckDB:
  строка в `TIMESTAMPTZ` или `200` в `TINYINT` — ошибка на входе (спайк).
- **Связи**: `FOREIGN KEY … REFERENCES` есть и проверяются; **нет** `ON DELETE`-действий и частичных
  уникальных индексов (§9): удаление учётки — явная транзакция (§3.15), инвариант «одна открытая
  запись» держит `store` и проверяет тест. Отдельные индексы по времени не создаются: колоночный
  движок читает диапазон по зон-картам.
- **Запись** — идемпотентная (конвенция §11.1): справочники `INSERT … ON CONFLICT (<естественный
  UNIQUE>) DO UPDATE SET last_seen_at = excluded.last_seen_at, updated_at = excluded.updated_at,
  updated_by = excluded.updated_by`; факты — через Appender в `stage_*` и `INSERT INTO … SELECT … ON
  CONFLICT (window_id, sampled_at) DO NOTHING`, журнал опросов — `ON CONFLICT (account_id,
  polled_at) DO NOTHING`; почта нормализуется в нижний регистр до записи. Все
  запросы — `sql\`…\`` с параметрами.
- **Имена ограничений** — по конвенции §9: `<таблица>_<колонки>_uq|ck|fk`. В DDL ниже `UNIQUE` и
  содержательные `CHECK` выписаны с именами; `NOT NULL` и `REFERENCES` даны короткой формой, имена
  `<таблица>_<колонка>_fk` им присваивает `0001_init.sql`. Флаги — прилагательное или причастие без
  `is_` (`locked`, `active`); `is_active` эндпоинта отображается в колонку `active`.
- **Зарезервированные слова** DuckDB в именах не используются: `at` → `sampled_at`; `sample`,
  `percent`, `locked`, `source`, `key`, `value` в DuckDB нерезервированные (проверено по списку
  ключевых слов грамматики v1.5.5) и допустимы без кавычек.

```sql

  key   VARCHAR PRIMARY KEY,
  value VARCHAR NOT NULL
);
-- ключи: schema_version, created_at, app_version, duckdb_version, extensions ('core_functions,icu'),
--        app_instance_id (UUID v7 экземпляра — автор записей), last_checkpoint_at, last_rollup_day,

```

Служебные таблицы механизмов, не соблюдающие набор §6: `schema_meta`, `stage_sample`. Список закрыт.

### 3.4. `folder` — папки из конфига, как их видит обнаружение

```sql
CREATE TABLE folder (
  id             UUID PRIMARY KEY,               -- v7 из приложения
  created_at     TIMESTAMPTZ NOT NULL,           -- служебный набор (конвенция §6)
  updated_at     TIMESTAMPTZ NOT NULL,
  deleted_at     TIMESTAMPTZ,                    -- убрана из конфига или пропала с диска; строка остаётся ради истории
  deleted_reason VARCHAR(32) CHECK (deleted_reason IN ('removed_from_config','not_found','forgotten')),
  created_by     UUID NOT NULL,
  updated_by     UUID NOT NULL,
  path           VARCHAR NOT NULL,               -- нормализованный абсолютный путь: прямые слэши, без хвостового, после раскрытия ~ и переменных
  kind           VARCHAR(32) NOT NULL CHECK (kind IN ('single','parent','empty','missing')),
  source         VARCHAR(32) NOT NULL CHECK (source IN ('config','default','env')),
  first_seen_at  TIMESTAMPTZ NOT NULL,           -- доменные моменты поверх набора: когда впервые/последний раз наблюдали
  last_seen_at   TIMESTAMPTZ NOT NULL,
  CONSTRAINT folder_path_uq UNIQUE (path),
  CONSTRAINT folder_path_ck CHECK (path = trim(path) AND right(path, 1) NOT IN ('/', '\')),
  CONSTRAINT folder_seen_ck CHECK (last_seen_at >= first_seen_at),
  CONSTRAINT folder_deleted_ck CHECK ((deleted_at IS NULL) = (deleted_reason IS NULL))
);
```

`folder_path_uq` у мягко удаляемой таблицы по конвенции должен быть частичным (`WHERE deleted_at IS
NULL`); DuckDB частичных индексов не даёт, поэтому папка, вернувшаяся в конфиг, **восстанавливается**
(`deleted_at = NULL`) той же строкой, а не создаётся заново — это и есть желаемое поведение (§9).

### 3.5. `login_dir` — каталог с `.credentials.json`

```sql
CREATE TABLE login_dir (
  id             UUID PRIMARY KEY,
```

### 3.7. `occupancy` — кто сидел в каталоге когда (журнал занятости)

```sql
CREATE TABLE occupancy (
  id           UUID PRIMARY KEY,
  created_at   TIMESTAMPTZ NOT NULL,             -- служебный набор (конвенция §6); deleted_at не применим — журнал
  updated_at   TIMESTAMPTZ NOT NULL,
  created_by   UUID NOT NULL,
  updated_by   UUID NOT NULL,
  login_dir_id UUID NOT NULL REFERENCES login_dir(id),
  account_id   UUID REFERENCES account(id),      -- NULL = логина нет, либо учётка забыта (§3.15)
  token_state  VARCHAR(32) NOT NULL CHECK (token_state IN ('ok','expired','rejected','none')),
  started_at   TIMESTAMPTZ NOT NULL,
  ended_at     TIMESTAMPTZ,                      -- NULL = текущая запись
  CONSTRAINT occupancy_ended_ck CHECK (ended_at IS NULL OR ended_at >= started_at)
);
```

Инвариант «не больше одной строки с `ended_at IS NULL` на `login_dir_id`» держит `store`: закрытие
и открытие — в одной транзакции; тест §8 проверяет запросом `SELECT login_dir_id FROM occupancy
WHERE ended_at IS NULL GROUP BY 1 HAVING count(*) > 1` — пусто. Правило записи: при каждом
обнаружении для каталога читаются почта и состояние токена; если пара `(account_id, token_state)`
отличается от открытой записи — открытая закрывается `ended_at = now()`, открывается новая. Смена
`ok → expired` — тоже новая запись (серый хвост «токен протух» на полосе занятости, план 01.1 §7.3).

### 3.10. `window_cycle` — один проход окна (от сброса до сброса)

Сброс окна — факт, а не эвристика по перепаду процента: каждый `resets_at`, который эндпоинт
называет для окна, — отдельный цикл. Замеры ссылаются на цикл, границы окна хранятся один раз.

```sql
CREATE TABLE window_cycle (
  id         UUID PRIMARY KEY,
  created_at TIMESTAMPTZ NOT NULL,               -- служебный набор (конвенция §6); deleted_at не применим
  updated_at TIMESTAMPTZ NOT NULL,
  created_by UUID NOT NULL,
  updated_by UUID NOT NULL,
  window_id  UUID NOT NULL REFERENCES limit_window(id),
  starts_at  TIMESTAMPTZ NOT NULL,               -- resets_at − длина окна (5 ч / 7 сут)
  resets_at  TIMESTAMPTZ NOT NULL,
  CONSTRAINT window_cycle_window_resets_uq UNIQUE (window_id, resets_at),
  CONSTRAINT window_cycle_order_ck CHECK (resets_at > starts_at)
);
```

Новый `resets_at` в ответе → `INSERT … ON CONFLICT DO NOTHING`; вертикали сбросов на графиках,
границы для скорости прогноза и число сбросов за день читаются отсюда.

### 3.11. `sample` — замер (история для графиков и прогноза)

Строка на окно на удачный опрос. При интервале 300 с — 288 строк в сутки на окно.

```sql
CREATE TABLE sample (
  id              UUID PRIMARY KEY,              -- v7 (конвенция §3.1: единый вид ключа и у фактов)
  created_at      TIMESTAMPTZ NOT NULL,          -- служебный набор (конвенция §6); deleted_at не применим — факт
  updated_at      TIMESTAMPTZ NOT NULL,
  created_by      UUID NOT NULL,
  updated_by      UUID NOT NULL,
  window_id       UUID NOT NULL REFERENCES limit_window(id),
  sampled_at      TIMESTAMPTZ NOT NULL,          -- время опроса (poll.polled_at)
  cycle_id        UUID NOT NULL REFERENCES window_cycle(id),
  percent         TINYINT NOT NULL,
  locked          BOOLEAN NOT NULL DEFAULT false,
  locked_reason   VARCHAR,
  server_severity VARCHAR,                       -- severity, как его назвал эндпоинт; наша — по порогам
  active          BOOLEAN,                       -- limits[].is_active эндпоинта: это окно сейчас ограничивает; без is_ (конвенция §9)
  CONSTRAINT sample_window_sampled_uq UNIQUE (window_id, sampled_at),  -- естественный ключ факта; по нему идут идемпотентные вставки
  CONSTRAINT sample_percent_ck CHECK (percent BETWEEN 0 AND 100)
);
```

Служебные колонки у 138 тысяч строк почти ничего не стоят в DuckDB: `created_by`/`updated_by` —
константа на экземпляр, `created_at ≈ sampled_at`, оба сжимаются словарём и дельтой (проверка — §8
п. 10). Запись тика: Appender → `stage_sample` (те же колонки, без ключей) → `INSERT INTO sample
SELECT … FROM stage_sample ON CONFLICT (window_id, sampled_at) DO NOTHING; DELETE FROM stage_sample;`
в той же транзакции. Дедупликации по значению нет: сетка замеров регулярная, пропуск строки означает
«нет данных», что графику важно.

### 3.13. `daily_rollup` — дневные свёртки старше `keep_days`

За последние `keep_days` агрегаты считаются на лету из `sample` (`time_bucket(INTERVAL 1 DAY,
sampled_at AT TIME ZONE rollup_tz)`, `max`, `avg`, `sum(locked)`); свёртка нужна только чтобы годовая
история переживала удаление сырья.

```sql
CREATE TABLE daily_rollup (
  id             UUID PRIMARY KEY,
  created_at     TIMESTAMPTZ NOT NULL,           -- служебный набор (конвенция §6); deleted_at не применим
  updated_at     TIMESTAMPTZ NOT NULL,
  created_by     UUID NOT NULL,
  updated_by     UUID NOT NULL,
  window_id      UUID NOT NULL REFERENCES limit_window(id),
  day_on         DATE NOT NULL,                  -- календарный день в поясе schema_meta.rollup_tz
  samples        INTEGER NOT NULL,
  peak_percent   TINYINT NOT NULL,
  avg_percent    DECIMAL(5,2) NOT NULL,
  minutes_locked INTEGER NOT NULL DEFAULT 0,
  resets         INTEGER NOT NULL DEFAULT 0,     -- сколько раз окно сбрасывалось за день
  CONSTRAINT daily_rollup_window_day_uq UNIQUE (window_id, day_on),
  CONSTRAINT daily_rollup_percent_ck CHECK (peak_percent BETWEEN 0 AND 100 AND avg_percent BETWEEN 0 AND 100)
);
```

Пересчёт: перед удалением сырья за день — свёртка этого дня одним `INSERT … SELECT … ON CONFLICT
(window_id, day_on) DO UPDATE`. Если пояс машины отличается от `schema_meta.rollup_tz`, при старте
свёртки за ещё хранящиеся дни пересчитываются, `rollup_tz` обновляется, более старые остаются как
есть с пометкой в логе.

### 3.15. Удаление учётки (`claude-limits forget <email>`) — явная транзакция

Право на удаление данных о человеке (конвенция §13.6). DuckDB не каскадирует, порядок фиксирован в
`storage/repo.nv` и проверяется тестом:

```sql
BEGIN;
UPDATE occupancy SET account_id = NULL, updated_at = now(), updated_by = $app WHERE account_id = $1;  -- история каталога остаётся
DELETE FROM notification WHERE account_id = $1 OR subject_id = $1 OR window_id IN (SELECT id FROM limit_window WHERE account_id = $1)
                          OR subject_id IN (SELECT id FROM limit_window WHERE account_id = $1);
DELETE FROM daily_rollup  WHERE window_id IN (SELECT id FROM limit_window WHERE account_id = $1);
DELETE FROM lock_period   WHERE window_id IN (SELECT id FROM limit_window WHERE account_id = $1);
DELETE FROM sample        WHERE window_id IN (SELECT id FROM limit_window WHERE account_id = $1);
DELETE FROM window_cycle  WHERE window_id IN (SELECT id FROM limit_window WHERE account_id = $1);
DELETE FROM limit_window  WHERE account_id = $1;
DELETE FROM poll          WHERE account_id = $1;
DELETE FROM account       WHERE id = $1;                                                            -- физически: ПДн
UPDATE config_history SET toml = <toml с почтой, заменённой на '***'> WHERE toml LIKE '%' || $email || '%';
COMMIT;
```

Удаление папки из конфига учётку **не удаляет** — она нужна статистике по папкам; мягкое удаление
(`deleted_at`) на учётку не применяется, кроме как внутри `forget` до физического удаления в той же
транзакции. После `forget` тест ищет почту по файлу базы, логам и последнему бэкапу — ноль совпадений
(обратная проба: нарочно оставить почту в `config_history` → тест краснеет).

### 3.16. Чего в базе нет и почему

- **Прогноз** — вычисляется по запросу из `sample` за окно скорости и кэшируется в памяти на тик.
- **Снимок «сейчас»** — в памяти файбера `store`; при старте восстанавливается из последних строк
  `sample` и `poll`, чтобы страница не была пустой до первого опроса (с пометкой давности).
- **Разрывы данных** — выводятся из `poll`/`sample` при запросе (`gap` = промежуток между соседними
  `sampled_at` больше `2 × interval_sec`).
- **Ключи идемпотентности, outbox, обработанные события** (конвенция §11.2–11.4) — не нужны:
  входящих изменяющих команд извне у бэкенда нет (`PUT /api/config` идемпотентен по `If-Match`,
  `POST /api/refresh` — по полу 60 с), событий наружу он не публикует. Появится агент, шлющий замеры
  на центральный сервер (Docker-сценарий) — таблицы добавляются миграцией по форме конвенции.
- **`external_ref`** — нет ключей внешних систем (§3.1).
- **Пользователи и сессии** — один токен доступа в конфиге (план 01 §9).
- **Настройки** — в TOML (§2), не в базе.

### 3.17. Представления для отчётов и отладки

```sql
CREATE VIEW v_current_occupancy AS
  SELECT ld.path AS dir, ld.name, a.email, o.token_state, o.started_at
  FROM occupancy o JOIN login_dir ld ON ld.id = o.login_dir_id
  LEFT JOIN account a ON a.id = o.account_id
  WHERE o.ended_at IS NULL AND ld.deleted_at IS NULL;

CREATE VIEW v_latest_sample AS
  SELECT s.* FROM sample s
  QUALIFY row_number() OVER (PARTITION BY window_id ORDER BY sampled_at DESC) = 1;

-- время в поясе машины для отладки в CLI duckdb (в приложении не используется)
CREATE VIEW v_sample_local AS
  SELECT a.email, w.kind, w.model, s.percent, s.locked,
         s.sampled_at AT TIME ZONE (SELECT value FROM schema_meta WHERE key = 'rollup_tz') AS sampled_local,
         c.resets_at  AT TIME ZONE (SELECT value FROM schema_meta WHERE key = 'rollup_tz') AS resets_local
  FROM sample s JOIN limit_window w ON w.id = s.window_id
  JOIN account a ON a.id = w.account_id JOIN window_cycle c ON c.id = s.cycle_id;
```

Все выборки текущего состояния в `storage/repo.nv` содержат `deleted_at IS NULL` для `folder`,
`login_dir`, `limit_window`, `notification` (конвенция §8).

## 4. Запросы, которые обслуживает база

| потребитель | запрос | таблицы |
|---|---|---|
| `/api/snapshot` при старте | `v_latest_sample` + последний `poll` учётки | `sample`, `poll` |
| `/api/history?by=account` | `sample WHERE window_id IN (…) AND sampled_at BETWEEN $1 AND $2`, `step` — `time_bucket(INTERVAL '<step>', sampled_at)` с `last(percent ORDER BY sampled_at)`; `lock_period` за период; разрывы — из `poll` | `sample`, `lock_period`, `poll` |
| `/api/history?by=folder` | `occupancy` каталога за период → для каждого отрезка `sample` его учётки; при `30d` для сессии — дневные пики | `occupancy`, `sample` |
| прогноз (план 01.1 §2.7) | `sample` окна за `rate_window_days` рабочих дней внутри текущего `window_cycle` | `sample`, `window_cycle` |
| плитки статистики | `lock_period` за 7 д; `max(percent)` сессии; `avg` по живым; смены почты — `occupancy` за 30 д | `lock_period`, `sample`, `occupancy` |
| `--once` | ничего не пишет и не читает | — |
| `claude-limits export --range 30d --format csv\|json` | `COPY (SELECT …) TO '<file>' (FORMAT CSV)` / `(FORMAT JSON)`; почты по умолчанию маскируются (§10) | `sample`, `occupancy`, `poll` |

Запись за один тик — одна транзакция: `poll` + Appender в `stage_sample` + перенос в `sample` +
переходы `lock_period` + при необходимости `occupancy`/`account`/`limit_window`/`window_cycle`, всё с
`created_by = updated_by = app_instance_id`. Ожидаемо 20–60 мс на тик.

## 5. Обслуживание

- **Checkpoint** — `CHECKPOINT` после каждой транзакции тика: `.wal` сливается в файл, база на
  диске всегда целостна и копируема.
- **Ретенция** — раз в сутки после полуночи по `rollup_tz`: свёртка дня, уходящего за
  `keep_days`, затем `DELETE FROM sample WHERE sampled_at < now() − INTERVAL '<keep_days> days'`,
  то же для `poll`; `daily_rollup` старше `rollup_keep_days`; `config_history` сверх
  `config_versions_keep`; затем `CHECKPOINT`. Отдельного `VACUUM` нет — при разрастании файла вдвое
  против данных делается `EXPORT DATABASE` → новый файл → `IMPORT DATABASE`.
- **Бэкап** — `CHECKPOINT` и копия файла в `backup/` перед каждой миграцией и раз в неделю;
  хранится `backups_keep` штук; бэкап содержит ПДн и защищён теми же правами файла (§10).
- **Целостность** — DuckDB проверяет заголовок и чексуммы блоков при открытии; ошибка открытия →
  файл переименовывается в `claude-limits.corrupt-<stamp>.duckdb`, поднимается последний бэкап,
  строка в лог и в шапку страницы. Настройки при этом целы: они в TOML.
- **Миграции** — `migrations/0001_init.sql`, `0002_….sql` из `embed_dir("migrations")`; по одной в
  транзакции с обновлением `schema_meta.schema_version`; бинарь со старой схемой, открывший новую
  базу, отказывается стартовать с понятным текстом; ломающие изменения — двухшаговые; обратный ход —
  восстановление бэкапа (записано как объяснение по конвенции §15).
- **Размер** — при `keep_days = 30` и 4 учётках ≈ 12–15 МБ; в `/api/health` есть `db_size_bytes`.

## 6. Безопасность данных вне ПДн

- В базе **нет** токенов, `refreshToken`, `expiresAt`, содержимого `.claude.json` сверх названных
  полей, заголовков HTTP.
- `poll.error` и логи обрезаются до 200 символов и проходят фильтр: строка, похожая на
  bearer-токен (`sk-ant-…`, JWT-подобная), заменяется на `***` до записи.
- `config_history.toml` хранится с замаскированным `access_token`.
- База никогда не ходит в сеть: автозагрузка расширений выключена на уровне сборки и соединения
  (подплан 01.4), тест держит мок `Net` с нулём вызовов.
- Файлы `0600`; каталог данных не индексируется поисковиками (Windows —
  `FILE_ATTRIBUTE_NOT_CONTENT_INDEXED`); бэкапы проверяются восстановлением в тесте Ф.2.

## 7. Пакет привязки

`nova-duckdb` — подплан [01.4](01.4-nova-duckdb.md): сборка из репозитория DuckDB со статическими
`core_functions` и `icu`, шим, фасад, отображение типов (`TIMESTAMPTZ` ↔ `Timestamp`, `DATE` ↔ `Date`,
`UUID` ↔ `Uuid`, `DECIMAL` ↔ `int128`+масштаб), Appender, тесты, ступени S0–S3. Приложение зависит от
него тегом `v0.1.0`; спайк Ф.0 п.5 плана 01 — его ступень S0.

## 9. Отклонения от конвенции по БД

Конвенция — [`docs/conventions/database.md`](../conventions/database.md), §16 требует записывать
каждое отклонение с причиной и ценой.

| правило | отклонение | почему | цена |
|---|---|---|---|
| частичный уникальный индекс на открытую запись (§7) и на мягко удаляемые `UNIQUE` (§8) | инвариант держит `store` + проверочный запрос в тестах; удалённая папка восстанавливается той же строкой | DuckDB не поддерживает частичные индексы | ошибка в коде `store` ловится тестом, не базой |
| каскадное удаление (§8) | явная транзакция `forget` (§3.15) | DuckDB не поддерживает `ON DELETE` | порядок удаления поддерживается руками при добавлении таблиц |
| индекс по колонке времени для диапазонов | индексов нет | колоночный движок читает диапазон по зон-картам | при смене движка на строчный — добавить индексы по `_at` |
| ПДн в отдельной схеме/файле `pdn` с шифрованием в приложении (§13.2–13.3) | один файл базы с правами `0600` в профиле владельца данных, без прикладного шифрования | приложение одного пользователя на его машине; ПДн здесь — его собственные почты и организации, лежащие рядом в `.claude.json` открытым текстом вместе с токенами; шифровать почты сильнее, чем Claude Code хранит токены, защиты не добавляет | при появлении центрального сервера с данными многих людей отклонение снимается: схема `pdn`, шифрование ключом из хранилища секретов, роль и аудит — обязательны |
| таблицы `idempotency_key`, `processed_event`, `outbox` (§11.2–11.4) | не заводятся | нет входящих изменяющих команд извне и исходящих событий (§3.16) | при появлении агента — добавить миграцией по форме конвенции |

## 10. Реестр ПДн (конвенция §13.7)

Классы данных — словарь конвенции: `none`, `pii`, `subject_id`, `secret`. Колонка «куда попадает»
— карта потоков для линтера контракта и для сверки при изменении состава ПДн (конвенция по API
§14.5).

| колонка | класс | категория | функция | основание | срок | защита | удаление | куда попадает |
|---|---|---|---|---|---|---|---|---|
| `account.email` | `pii` | контакт, идентификатор человека | ключ учётки, подпись строки, группировка каталогов | законный интерес владельца данных: это его собственные учётки на его машине | пока учётка наблюдается + до `forget` | файл `0600`, нет в логах/URL, экспорт с маской по умолчанию | `forget` физически (§3.15) | тела `snapshot`, `history`, `config` (`accounts_order`), `probe`, события SSE `snapshot`/`config`, экспорт (маска), `config_history.toml` |
| `account.id` | `subject_id` | ключ учётки | адресация в API вместо почты | то же | то же | `forget` | query `history`/`export`, тела всех ответов; допустим в URL: непрозрачный UUID v7, вне базы с человеком не связан |
| `account.org_name` | `pii` | принадлежность к организации | подпись строки | то же | то же | то же | `forget` | тела `snapshot`, `probe`, события `snapshot` |
| `login_dir.path` | `pii` | технический след (имя пользователя ОС в пути) | обнаружение кредов, подпись каталога | то же | пока каталог наблюдается; `deleted_at` при исчезновении | в логах — только `name`; в LAN-режиме поле отдаётся `null` | остаётся (история каталога), при `forget` учётки не трогается: путь — свойство машины, не человека | тела `snapshot`, `config`, `probe`, `history?by=folder` только на loopback; `config_history.toml` |
| `config_history.toml` | `pii` | почты в `accounts_order`, пути папок | откат настроек | то же | `config_versions_keep` версий | маска токена; при `forget` почта заменяется на `***` | ретенция + `forget` | никуда: только чтение из CLI на машине владельца |
| `[server] access_token`, сессии | `secret` | учётные данные | доступ из LAN | — | файл `0600`; в ответах только `access_token_set`; показ один раз при генерации | смена токена обнуляет сессии | тело `POST /api/config/token` один раз; cookie `cl_session` (случайный идентификатор, не токен) |
| `v_sample_local`, экспорт CSV/JSON | `pii` | почта в выборке | отладка, выгрузка | то же | не хранится | экспорт маскирует почту, полный — `unmasked` только с loopback с записью в лог | — | файл экспорта у владельца |

Аналитика (`sample`, `poll`, `lock_period`, `daily_rollup`) ссылается на человека только `account_id`
(конвенция §13.2); `notification.payload` содержит только идентификаторы.

## 8. Приёмка (часть Ф.1 и Ф.2 плана 01)

1. Конфиг: путь по §1 на обеих ОС; portable-режим включается файлом рядом с бинарём; `--config` и
   переменная окружения переопределяют. Файл с ошибкой не роняет процесс, ошибка видна в логе и в
   шапке.
2. Запись конфига: `PUT` даёт байт-в-байт канонический TOML; повторный `PUT` без изменений — тот
   же файл; `If-Match` устаревший → `409`; перед записью строка в `config_history` с `***` вместо
   токена; `write_atomic` — при убитом процессе посреди записи старый файл цел (тест с моком `Fs`).
3. Схема: `0001_init.sql` создаёт таблицы §3 со служебным набором у каждой таблицы предметной
   области (проверка по `information_schema.columns`); имена ограничений из `duckdb_constraints()`
   соответствуют шаблону `<таблица>_<колонки>_uq|ck|fk`, ни одной колонки с префиксом `is_`; `id` — UUID v7 (старшие 48 бит — время
   создания, тест сравнивает с `created_at` ± 1 с); списки `CHECK` совпадают с §3.2 и с кодом; строка в
   `TIMESTAMPTZ`, `200` в `TINYINT`, `ended_at < started_at`, почта с заглавной буквой — ошибка;
   `EXPLAIN` запросов §4 читает только нужные колонки.
4. Запись тика: одна транзакция; при инъекции ошибки на переносе из `stage_sample` не остаётся
   `poll` без пары; `created_by = updated_by = app_instance_id`; после тика `.wal` пуст.
   **Два раза подряд** (конвенция §11.5): повторный перенос того же `stage_sample`, повторная
   вставка того же `poll`, повторное обнаружение тех же папок и учёток не меняют ни одного счётчика
   строк и не трогают `updated_at` фактов; у справочников `updated_at` сдвигается, `id` тот же.
5. Занятость: смена почты в `.claude.json` фикстуры → закрытая и новая запись; `ok → expired` →
   новая запись; запрос из §3.7 на «две открытые» пуст; папка, убранная из конфига и возвращённая, —
   та же строка с `deleted_at` → `NULL`.
6. Блокировки: последовательность замеров `0,100,100,0` даёт один `lock_period`; `percent = 100`
   без `locked_reason` — период с `reason = 'percent_100'`.
7. Свёртки и ретенция: фикстура на 35 дней → после обслуживания `sample` содержит 30 дней,
   `daily_rollup` — 5 дней, `peak_percent` совпадает с `max` по удалённым замерам; смена пояса машины
   пересчитывает свёртки и обновляет `rollup_tz`.
8. Целостность: испорченный файл базы → переименован, поднят бэкап, строка в логе; без бэкапа —
   пустая база, настройки целы; бэкап восстанавливается и открывается.
9. Приватность и ПДн: фикстуры не содержат настоящих ПДн (почты `@example.com`, пути с
   пользователем `me`); `grep` по файлу базы и логам на подстроки токенов из фикстур — ноль (обратная
   проба: токен в `poll.error` → тест краснеет); после `forget <email>` почта не находится ни в базе,
   ни в логах, ни в свежем бэкапе (обратная проба: оставить почту в `config_history` → красный);
   экспорт без флага маскирует почты; в логах нет `login_dir.path`; ни одного сетевого вызова из
   базы; `~/.duckdb` не появляется.
10. Производительность и объём: тик с 4 учётками — ≤ 100 мс; `/api/history?range=30d` — ≤ 50 мс на
    138 000 строк; файл на 30 дней синтетики ≤ 15 МБ со служебными колонками.
