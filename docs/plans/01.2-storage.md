## 0. Решения

| № | решение | почему |
|---|---|---|
| 1 | **Два хранилища с разными ролями**: настройки — текстовый TOML, данные — SQLite | настройки правит человек и кладёт в дотфайлы; данные — сотни тысяч строк с запросами по времени, это работа для БД, не для файла |
| 2 | **Настройки — один файл `claude-limits.toml`**, источник истины; UI пишет в него атомарно | совместимо с эталонным скриптом; читается без программы; версионируется руками |
| 3 | **База — SQLite**, один файл `claude-limits.db`, WAL | встраиваемая, нулевое администрирование, открывается любым инструментом; амальгамация `sqlite3.c` собирается через `vendor_src_dirs` как mbedTLS; пример привязки уже в кукбуке |
| 4 | **Привязка — отдельный пакет `nova-sqlite`** (сиблинг-репо, как `nova-tls`), тонкий `.nv`-фасад над амальгамацией; виджет и бэкенд тянут его по тегу | канон спутниковых пакетов; SQLite пригодится другим проектам на Nova |
| 5 | **Одно соединение, один владелец — файбер `store`**; все записи и чтения идут через него по `Chan` | снимает вопросы потокобезопасности SQLite и файберов (план 01 §3.1); чтения дёшевы, конкуренции нет |
| 6 | **Токены в базе не хранятся никогда**, ни в каком поле, ни в логе ошибок | README §Rules; база содержит почты и организации — файл с правами `0600` на Linux |
| 7 | **Ретенция настраивается**, по умолчанию сырые замеры 30 дней, дневные свёртки 400 дней, занятость и блокировки — без срока | сырьё нужно для графиков 24 ч / 7 д / 30 д; для годовой картины хватает дневных агрегатов |
| 8 | **Миграции — пронумерованные SQL-файлы, встроенные в бинарь**, версия в `schema_meta` | обычная практика; откат — из бэкапа, который делается перед миграцией |

## 0а. Альтернатива — DuckDB: результаты спайка 2026-09-06

Владелец недоволен слабой типизацией SQLite (нет типа даты, `STRICT` даёт лишь пять типов).
Проверена встраиваемая альтернатива с настоящими типами — DuckDB v1.5.5, статически, на этой
машине (Windows 11, clang 22 + MSVC 14.44; WSL Ubuntu, clang 21). Исходники, команды и полный
вердикт — [`spikes/duckdb-static/VERDICT.md`](../../spikes/duckdb-static/VERDICT.md).

| что мерили | Windows | Linux (WSL) |
|---|---|---|
| компиляция амальгамации `duckdb.cpp` (655 k строк, `-O2`) | 11 мин, пик 3,5 ГБ RAM | 20 мин, пик 4,8 ГБ RAM |
| статическая библиотека | 119 МБ `.lib` | 62 МБ `.a` |
| бинарь C-теста / Nova-бинарь | 36,4 МБ / **36,8 МБ** (hello на Nova — 0,56 МБ) | 37,4 МБ полностью статический, 30 МБ после `strip` |
| конфликт CRT с рантаймом Nova (`/MT`) | **нет**: `nova build` слинковал, импорты только системные DLL, ни одной CRT-DLL | C-линковка `-static` прошла; Nova в WSL не собирали |
| холодный старт процесса | Nova-бинарь 660–870 мс первый запуск, далее 245–260 мс (hello — 215–270 мс) | — |
| открыть файл БД + соединение | 18–50 мс (первый раз 277 мс) | 7–22 мс |
| 10 000 вставок **по одной** prepared statement в одной транзакции | **19–21 с** (≈2 мс/строка) | **26 с** |
| 10 000 строк через **Appender** | 9–12 мс | 12 мс |
| выборка по диапазону с группировкой, 10 000 строк | 2 мс | 2–7 мс |
| строка в колонку `TIMESTAMP` | отвергнута ошибкой типа | отвергнута |

Что спайк вскрыл сверх размера и CRT:

1. **Амальгамация — это не весь DuckDB.** С версии 1.2 `make_timestamp`, `date_trunc`,
   `time_bucket`, `epoch_ms` и десятки функций вынесены в расширение `core_functions`, а
   арифметика и функции `TIMESTAMPTZ` — в расширение `icu`. В `libduckdb-src.zip` их **нет**,
   а при первом вызове DuckDB пытается **скачать расширение из интернета** и держит запрос
   22 секунды. Для одного статического бинаря без сети это неприемлемо; лечится только полной
   CMake-сборкой из репозитория с `-DBUILD_EXTENSIONS="core_functions;icu"` и статической
   линковкой расширений — это тяжелее амальгамации (репозиторий, CMake, около часа сборки), и
   `autoinstall_known_extensions=false` в каждом соединении.
2. **Построчная запись медленная.** DuckDB — колоночная аналитическая база; `INSERT` по строке
   стоит ~2 мс, у SQLite — микросекунды. Наш тик пишет десятки строк, это 50–100 мс на тик,
   терпимо, но каждая точечная запись (`UPDATE` открытого интервала, `last_seen_at`) идёт по
   той же цене. Appender спасает только массовые вставки.
3. **Бинарь +36 МБ** к 0,5 МБ и 11–20 минут к чистой сборке на CI на каждой ОС.

**Вывод спайка:** типы у DuckDB настоящие, линковка с Nova чистая, старт не страдает, но цена —
36 МБ бинаря, полная сборка из репозитория ради базовых функций дат и медленные точечные записи.
Решение о смене хранилища — за владельцем; до него подплан описывает SQLite. Если выбор падёт
на DuckDB: `TIMESTAMP` в UTC вместо `TIMESTAMPTZ` (без ICU), запись тика через Appender во
временную таблицу и `INSERT … SELECT`, `daily_rollup` не нужен (агрегаты считаются на лету),
`ON DELETE CASCADE` заменяется явными `DELETE` в транзакции, пакет `nova-duckdb` собирается по
образцу `nova-sdl` (CMake, build-and-cache), спайк Ф.0 п.5 меняет предмет.

## 0б. Если DuckDB — сборка из исходников с расширениями (решение владельца 2026-09-06)

Владелец: расширения собирать **сразу из исходников вместе с ядром**, статически, никаких
скачиваний в рантайме. Это меняет предмет пакета: не амальгамация, а полный репозиторий.

### Что входит в бинарь

| расширение | зачем нам | без него |
|---|---|---|
| `core_functions` | `make_timestamp`, `date_trunc`, `time_bucket`, `epoch_ms`, `strftime`, оконные и строковые функции — почти весь SQL подпланов 01.1 и 01.3 | запросы падают с «exists in the core_functions extension» (спайк, §0а) |
| `icu` | `TIMESTAMPTZ`, часовые пояса, календарный день человека для свёрток без своего кода | только `TIMESTAMP` в UTC, пояс считает Nova |
| `json` | `payload` в `notification`, `/api/export?format=json` прямо из SQL | сериализация на стороне Nova (у нас она и так есть) — **не берём**, лишние 3–5 МБ |
| `parquet`, `httpfs`, `autocomplete`, `tpch`… | не нужны | выключены явно |

Итого ядро + `core_functions` + `icu`. Ожидаемый размер бинаря — 45–55 МБ против 37 МБ у голого
ядра (ICU несёт таблицы локалей); точную цифру даёт спайк Ф.0 п.5.

### Пакет `nova-duckdb`

```
nova-duckdb/                        сиблинг-репо, раскладка как у nova-sdl (CMake-сборка, build-and-cache)
├── nova.toml                       [package] name="duckdb"; [ffi] c_shims, include_dirs, libs = ["duckdb_static", "core_functions_extension", "icu_extension", "duckdb_re2", "duckdb_fmt", …], lib_dirs = ["native/lib"]
├── duckdb.nv                       Database.open(path, opts), Connection { query(Sql), prepare, appender(table) }, Appender { row(...), flush }, Result { rows, col typed accessors }
├── ffi.nv                          extern "C" #thread_affine — duckdb_open_ext, connect, query, prepare/bind_*/execute, appender_*, value_*, destroy_*
├── native/
│   ├── duckdb_shim.c / .h          плоские сигнатуры; #define DUCKDB_STATIC_BUILD до заголовка; #pragma comment(lib, "rstrtmgr") и "ws2_32", "bcrypt" на Windows
│   └── duckdb/                     git-сабмодуль репозитория duckdb/duckdb, закреплённый тег (v1.5.5 на 2026-09-06)
├── scripts/build-duckdb.ps1 / .sh  CMake из сабмодуля → native/lib; no-op по хешу коммита сабмодуля и набора флагов
└── duckdb_test.nv                  in-memory: типы, upsert, appender, date_trunc и time_bucket (доказывает, что расширения прилинкованы), отказ автозагрузки
```

Скрипт сборки (флаги сверяет спайк; названия по CMake DuckDB 1.5):

```sh
cmake -S native/duckdb -B native/build -G Ninja   -DCMAKE_BUILD_TYPE=Release   -DBUILD_EXTENSIONS="core_functions;icu" \        # статически, регистрируются при старте
  -DENABLE_EXTENSION_AUTOLOADING=0 -DENABLE_EXTENSION_AUTOINSTALL=0   -DBUILD_SHELL=0 -DBUILD_UNITTESTS=0 -DBUILD_BENCHMARKS=0   -DDUCKDB_EXPLICIT_PLATFORM=<windows_amd64|linux_amd64>   -DCMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded          # Windows: /MT, как рантайм Nova (спайк: конфликта нет)
cmake --build native/build --target duckdb_static -j
```

Выход — набор статических библиотек (ядро и по одной на расширение и вендоренную зависимость:
re2, fmt, utf8proc, hyperloglog, fastpforlib, mbedtls-часть, …); их имена скрипт собирает в
`native/lib` и они перечислены в `[ffi] libs` в порядке от зависимого к зависимости. Порядок и
полный список — из вывода первой сборки, закрепляются в `nova.toml`.

### Что это стоит и как живёт на CI

- Полная сборка из репозитория — порядка 40–60 минут на 16 ядрах и до 8 ГБ RAM (спайк на
  амальгамации: 11 мин Windows, 20 мин Linux при одном TU; репозиторий параллелится, но объём
  больше). Сабмодуль репозитория DuckDB — ~200 МБ клона.
- **Кэш обязателен**: GitHub Actions `actions/cache` по ключу `duckdb-<тег>-<ОС>-<хеш флагов>`
  на `native/lib`; при попадании сборка не запускается. Локально — тот же no-op по хешу.
- Обновление DuckDB — смена тега сабмодуля и одна пересборка; тег и набор расширений
  фиксируются в `nova.toml` пакета и в `schema_meta.duckdb_version` базы.

### Настройки соединения (в `duckdb.nv`, не в конфиге пользователя)

При каждом `open`: `SET autoinstall_known_extensions=false; SET autoload_known_extensions=false;
SET temp_directory='<data_dir>/tmp'; SET memory_limit='512MB'; SET threads=2;
SET TimeZone='UTC'`. Так база никогда не создаёт `~/.duckdb`, не ходит в сеть, не разбрасывает
временные файлы и не забирает у машины все ядра ради запроса на 138 тысяч строк.

### Что меняется в схеме §3 при переходе на DuckDB

- все `*_at INTEGER` → `TIMESTAMPTZ` (с `icu`) или `TIMESTAMP` в UTC; `day TEXT` → `DATE`;
  `locked INTEGER 0/1` → `BOOLEAN`; перечисления `TEXT CHECK (…)` → `ENUM`; `rate` → `DECIMAL`;
- `STRICT`/`WITHOUT ROWID` — понятия SQLite, убираются; типы строгие по умолчанию;
- `ON DELETE CASCADE / SET NULL` DuckDB не поддерживает — `forget <email>` становится явной
  транзакцией из `DELETE` по таблицам-фактам в правильном порядке (§3.14 дополняется);
- частичные уникальные индексы (`WHERE ended_at IS NULL`) не поддерживаются — инвариант «одна
  открытая запись на каталог» держит код `store` плюс проверочный запрос в тестах;
- запись тика: Appender во временные таблицы `stage_*` в одной транзакции, затем
  `INSERT … SELECT` с `ON CONFLICT DO UPDATE`; точечные `UPDATE` открытых интервалов остаются
  обычными и стоят ~2 мс каждый (спайк) — на тик их единицы;
- `daily_rollup` не нужен: `time_bucket(INTERVAL 1 DAY, at AT TIME ZONE tz)` по `sample` за
  30 дней считается за миллисекунды; ретенция сырья сверх 30 дней — `DELETE`, для годовой
  истории — `daily_rollup` остаётся как экспорт-агрегат (решить по замеру);
- `VACUUM INTO` → `CHECKPOINT` + копия файла, либо `EXPORT DATABASE '<dir>'` (Parquet/CSV) для
  бэкапа; `PRAGMA quick_check` → `PRAGMA database_size` + `CHECKPOINT`, целостность файла
  DuckDB проверяет при открытии сама.

Спайк Ф.0 п.5 плана 01 переформулирован: **полная сборка DuckDB с `core_functions` и `icu` из
сабмодуля на Windows и Linux**; вердикт — время сборки на CI с кэшем и без, размер бинаря Nova,
`date_trunc` и `TIMESTAMPTZ` работают без сети, `~/.duckdb` не появляется.

## 1. Где лежат файлы

| что | Windows | Linux | переопределение |
|---|---|---|---|
| настройки `claude-limits.toml` | `%APPDATA%\claude-limits\` | `$XDG_CONFIG_HOME/claude-limits/` (по умолчанию `~/.config/claude-limits/`) | `--config PATH`; переменная `CLAUDE_LIMITS_CONFIG` |
| база `claude-limits.db` (+ `-wal`, `-shm`) | `%LOCALAPPDATA%\claude-limits\` | `$XDG_DATA_HOME/claude-limits/` (`~/.local/share/claude-limits/`) | `--data-dir PATH`; `[storage] data_dir` в конфиге; `CLAUDE_LIMITS_DATA` |
| бэкапы `backup/claude-limits-YYYYMMDD-HHMM.db` | там же, подкаталог | там же | `[storage] backups_keep = 5` |
| логи `claude-limits.log` | `%LOCALAPPDATA%\claude-limits\logs\` | `$XDG_STATE_HOME/claude-limits/` (`~/.local/state/claude-limits/`) | `--log PATH` |

**Portable-режим**: если рядом с бинарём лежит `claude-limits.toml`, все три каталога — рядом с
бинарём (`./data/`, `./logs/`). Так работает эталонный скрипт (конфиг в корне репозитория),
так удобно носить на флешке. Режим выбирается при старте и пишется в лог одной строкой.

Права: на Linux каталоги `0700`, файлы `0600`. На Windows — наследуются от профиля.
Каталоги Claude Code остаются **только для чтения** (решение 6 плана 01): туда не пишется
ничего, включая lock-файлы.

### 2.1. Файл

Один TOML, все секции; поля с их значениями по умолчанию. Это **полный** список, планы 01 и
01.1 ссылаются сюда:

```toml
# claude-limits.toml — settings. Written by the app on Save; comments below are regenerated.

[[folders]]                                   # где искать логины Claude Code (план 01.1 §5.4)

[poll]

[ui]                                          # общие для всех браузеров; личное — в localStorage
```

Что живёт **не здесь**: браузерные предпочтения (вид, стиль бара, период статистики,
обратный отсчёт) — в `localStorage` каждого браузера (план 01.1 §0); порядок учёток общий и
потому здесь.

### 2.2. Чтение и запись

- **Чтение** при старте и при каждом тике опроса: если `mtime` файла изменился — перечитать,
  провалидировать, применить, событие `config` в SSE. Ошибка в файле — в лог и в шапку страницы
  (`config error: [poll] interval_sec must be a number`), продолжаем с предыдущими значениями.
- **Запись** из UI (`PUT /api/config`) и из меню виджета: бэкенд сливает изменения в текущий
  конфиг, валидирует, сериализует **канонически** (порядок секций как выше, комментарии
  регенерируются — пользовательские комментарии не сохраняются, это записано в шапке файла) и
  пишет `write_atomic` (временный файл + переименование). Перед записью прежний текст кладётся в
  `config_history` (§3.12).
- **Конфликт**: `PUT` несёт `If-Match: <mtime или хэш загруженного конфига>`; если файл менялся
  после того, как панель настроек его загрузила — `409`, панель предлагает перечитать.
- Валидация одна для старта и `PUT`; ошибки — `400 { field, message }` (тексты — план 01.1 §5).
- Секреты: `access_token` хранится в файле открытым текстом — это локальный файл `0600`, как
  `.credentials.json` у самого Claude Code. В логи и в `/api/config` он не попадает (в ответе —
  `access_token_set: true`).

## 3. База данных

### 3.1. Общее

- Файл `claude-limits.db`, SQLite ≥ 3.45 (амальгамация закреплена сабмодулем в `nova-sqlite`),
  прагмы при открытии: `journal_mode = WAL`, `synchronous = NORMAL`, `foreign_keys = ON`,
  `busy_timeout = 5000`, `temp_store = MEMORY`, `auto_vacuum = INCREMENTAL`.
- **Дата и время.** У SQLite нет типа даты, а в `STRICT`-таблицах допустимы только `INTEGER`,
  `REAL`, `TEXT`, `BLOB`, `ANY`. Поэтому все моменты времени — **`INTEGER`, секунды Unix UTC**,
  имена таких колонок заканчиваются на `_at` (`started_at`, `resets_at`, `at`). Это канонический
  выбор для SQLite: 8 байт, индексируется, диапазоны и свёртки — целочисленная арифметика,
  переход на летнее время не ломает порядок. Читаемость для человека дают представления §3.16
  (`datetime(at, 'unixepoch', 'localtime')`) и CLI `claude-limits export`. Единственное
  исключение — `day TEXT 'YYYY-MM-DD'` в дневных свёртках: это **календарный день человека** в
  локальном поясе бэкенда; пояс записывается в `schema_meta.rollup_tz`, при его смене свёртки
  пересчитываются из `sample` (§3.12). Миллисекунды не хранятся: точность опроса — минуты.
- **`STRICT`** (SQLite ≥ 3.37): колонка принимает только объявленный тип, попытка записать строку
  в `INTEGER` — ошибка, а не тихое приведение, как в обычных таблицах SQLite. Это и есть
  «типы как в других СУБД»; цена — набор типов ограничен пятью выше.
- **Целостность интервалов** — `CHECK (ended_at IS NULL OR ended_at >= started_at)` и
  `CHECK (last_seen_at >= first_seen_at)` везде, где есть пары; БД не примет перевёрнутый интервал.
- **Внешние ключи с явным поведением при удалении**: факты каскадируют за своим справочником
  (`ON DELETE CASCADE`), история занятости теряет ссылку, но не строку (`ON DELETE SET NULL`),
  структурные связи запрещают удаление с потомками (`ON DELETE RESTRICT`). Так `claude-limits
  forget <email>` — одна команда `DELETE FROM account`, остальное делает схема.
- **Запись — идемпотентными upsert-ами**: справочники — `INSERT … ON CONFLICT (…) DO UPDATE SET
  last_seen_at = excluded.last_seen_at, …`; почта нормализуется в нижний регистр до записи
  (`COLLATE NOCASE` — страховка, не механизм); замеры — `INSERT OR IGNORE` (повторный опрос в ту
  же секунду не ошибка). Все запросы — `sql\`…\`` с параметрами.
- Булевы — `INTEGER 0/1` с `CHECK`. Перечисления — `TEXT` с `CHECK (… IN (…))`: читается в
  любом клиенте, индексы по ним не нужны.
- Все таблицы `STRICT` (типы проверяются SQLite). Таблицы с составным естественным ключом —
  `WITHOUT ROWID`.
- Записи и чтения — через `sql\`…\`` с параметрами (`std/data/sql.nv`); конкатенации SQL нет.

### 3.3. `folder` — папки из конфига, как их видит обнаружение

Источник истины — `[[folders]]` в конфиге; таблица нужна, чтобы у каталогов логинов и занятости
был стабильный ключ и история «когда папка появилась/исчезла».

```sql
CREATE TABLE folder (
  id            INTEGER PRIMARY KEY,
  path          TEXT    NOT NULL UNIQUE,          -- нормализованный абсолютный путь, как в конфиге после раскрытия ~ и переменных
  kind          TEXT    NOT NULL CHECK (kind IN ('single','parent','empty','missing')),
  source        TEXT    NOT NULL CHECK (source IN ('config','default','env')),  -- откуда взялась: [[folders]], ~/.claude, CLAUDE_CONFIG_DIR
  first_seen_at INTEGER NOT NULL,
  last_seen_at  INTEGER NOT NULL,
  removed_at    INTEGER,                          -- убрана из конфига; строка остаётся ради истории
  CHECK (last_seen_at >= first_seen_at)
) STRICT;
CREATE INDEX folder_active_idx ON folder (removed_at) WHERE removed_at IS NULL;
```

### 3.4. `login_dir` — каталог с `.credentials.json`

Для `single` — сам путь папки; для `parent` — каждый дочерний каталог с логином.

```sql
CREATE TABLE login_dir (
  id            INTEGER PRIMARY KEY,
  folder_id     INTEGER NOT NULL REFERENCES folder(id) ON DELETE RESTRICT,
  path          TEXT    NOT NULL UNIQUE,
  name          TEXT    NOT NULL,                 -- короткое имя для подписи: nv-lang, dev, dev-wsl
  layout        TEXT    NOT NULL CHECK (layout IN ('default','config_dir')),  -- .claude.json РЯДОМ или ВНУТРИ (README §Accounts)
  first_seen_at INTEGER NOT NULL,
  last_seen_at  INTEGER NOT NULL,
  removed_at    INTEGER,
  CHECK (last_seen_at >= first_seen_at)
) STRICT;
CREATE INDEX login_dir_folder_idx ON login_dir (folder_id, removed_at);
```

### 3.5. `account` — учётка (одна на почту)

```sql
CREATE TABLE account (
  id                INTEGER PRIMARY KEY,
  email             TEXT    NOT NULL UNIQUE COLLATE NOCASE,
  org_name          TEXT,
  org_uuid          TEXT,                        -- oauthAccount.organizationUuid, если есть
  subscription_type TEXT,                        -- .credentials.json: subscriptionType (напр. max)
  rate_limit_tier   TEXT,                        -- .credentials.json: rateLimitTier
  color_slot        INTEGER NOT NULL,            -- 0..N: закреплённый цвет серии для статистики (план 01.1 §8), не меняется
  first_seen_at     INTEGER NOT NULL,
  last_seen_at      INTEGER NOT NULL,
  CHECK (last_seen_at >= first_seen_at),
  CHECK (email = lower(email))                   -- нормализуется до записи
) STRICT;
```

Токена, `refreshToken`, `expiresAt` здесь **нет**. Состояние токена — в `occupancy.token_state`
(§3.6) и в `poll.outcome` (§3.7); сам срок `expiresAt` не хранится: он нужен только в момент
опроса и читается из файла.

### 3.6. `occupancy` — кто сидел в каталоге когда (журнал занятости)

Основа статистики «по папкам» (план 01.1 §7). Одна открытая запись на каталог.

```sql
CREATE TABLE occupancy (
  id           INTEGER PRIMARY KEY,
  login_dir_id INTEGER NOT NULL REFERENCES login_dir(id) ON DELETE CASCADE,
  account_id   INTEGER REFERENCES account(id) ON DELETE SET NULL,  -- NULL = логина нет; при forget — ссылка снимается, строка остаётся
  token_state  TEXT    NOT NULL CHECK (token_state IN ('ok','expired','rejected','none')),
  started_at   INTEGER NOT NULL,
  ended_at     INTEGER,                          -- NULL = текущая запись
  CHECK (ended_at IS NULL OR ended_at >= started_at)
) STRICT;
CREATE INDEX occupancy_dir_time_idx ON occupancy (login_dir_id, started_at);
CREATE INDEX occupancy_account_time_idx ON occupancy (account_id, started_at);
CREATE UNIQUE INDEX occupancy_open_uidx ON occupancy (login_dir_id) WHERE ended_at IS NULL;
```

Правило записи (файбер `store`, при каждом обнаружении — старт, тик, `PUT /api/config`):
для каталога читаются почта и состояние токена; если пара `(account_id, token_state)`
отличается от открытой записи — открытая закрывается `ended_at = now`, открывается новая.
Смена `ok → expired` — тоже новая запись: так на полосе занятости виден серый хвост «токен
протух» (план 01.1 §7.3).

### 3.7. `poll` — журнал обращений к эндпоинту

Каждая попытка, удачная и нет. Нужен для полос «нет данных» на графиках, для диагностики 429
и для плитки «Days without a login».

```sql
CREATE TABLE poll (
  id              INTEGER PRIMARY KEY,
  account_id      INTEGER NOT NULL REFERENCES account(id) ON DELETE CASCADE,
  at              INTEGER NOT NULL,
  outcome         TEXT    NOT NULL CHECK (outcome IN ('ok','http_401','http_429','http_5xx','http_other','network','parse','skipped_expired','skipped_backoff')),
  http_status     INTEGER,
  retry_after_sec INTEGER,                       -- из Retry-After при 429
  latency_ms      INTEGER,
  error           TEXT                           -- короткий текст без токенов и заголовков
) STRICT;
CREATE INDEX poll_account_at_idx ON poll (account_id, at);
CREATE INDEX poll_at_idx ON poll (at);           -- ретенция и «последний опрос машины»
```

### 3.8. `limit_window` — измерение «окно лимита учётки»

Чтобы `sample` не повторял в каждой строке почту, вид окна и имя модели.

```sql
CREATE TABLE limit_window (
  id         INTEGER PRIMARY KEY,
  account_id INTEGER NOT NULL REFERENCES account(id) ON DELETE CASCADE,
  kind       TEXT    NOT NULL CHECK (kind IN ('session','weekly_all','weekly_scoped')),
  model      TEXT,                                -- display_name модели для weekly_scoped, иначе NULL
  first_seen_at INTEGER NOT NULL,
  last_seen_at  INTEGER NOT NULL,                 -- модель исчезла из ответа → перестаёт обновляться, строки истории остаются
  UNIQUE (account_id, kind, model),
  CHECK (last_seen_at >= first_seen_at),
  CHECK ((kind = 'weekly_scoped') = (model IS NOT NULL))
) STRICT;
```

### 3.8а. `window_cycle` — один проход окна (от сброса до сброса)

Сброс окна — факт, а не эвристика по перепаду процента: каждый `resets_at`, который эндпоинт
называет для окна, — отдельный цикл. Замеры ссылаются на цикл, границы окна хранятся один раз.

```sql
CREATE TABLE window_cycle (
  id         INTEGER PRIMARY KEY,
  window_id  INTEGER NOT NULL REFERENCES limit_window(id) ON DELETE CASCADE,
  starts_at  INTEGER NOT NULL,                    -- resets_at − длина окна (5 ч / 7 сут)
  resets_at  INTEGER NOT NULL,
  UNIQUE (window_id, resets_at),
  CHECK (resets_at > starts_at)
) STRICT;
CREATE INDEX window_cycle_window_idx ON window_cycle (window_id, starts_at);
```

Новый `resets_at` в ответе → `INSERT OR IGNORE` цикла; вертикали сбросов на графиках, границы
для скорости прогноза и `daily_rollup.resets` читаются отсюда, без сканирования замеров.

### 3.9. `sample` — замер (история для графиков и прогноза)

Строка на окно на удачный опрос. При интервале 300 с — 288 строк в сутки на окно.

```sql
CREATE TABLE sample (
  window_id       INTEGER NOT NULL REFERENCES limit_window(id) ON DELETE CASCADE,
  at              INTEGER NOT NULL,               -- время опроса (poll.at)
  cycle_id        INTEGER NOT NULL REFERENCES window_cycle(id) ON DELETE CASCADE,  -- границы окна — там
  percent         INTEGER NOT NULL CHECK (percent BETWEEN 0 AND 100),
  locked          INTEGER NOT NULL DEFAULT 0 CHECK (locked IN (0,1)),
  locked_reason   TEXT,
  server_severity TEXT,                           -- severity, как его назвал эндпоинт; наша считается по порогам
  is_active       INTEGER CHECK (is_active IN (0,1)),  -- limits[].is_active: это окно сейчас ограничивает
  PRIMARY KEY (window_id, at)
) STRICT, WITHOUT ROWID;
CREATE INDEX sample_at_idx ON sample (at);       -- ретенция, срезы «все окна в момент t»
CREATE INDEX sample_cycle_idx ON sample (cycle_id, at);  -- замеры одного прохода окна (прогноз)
```

Ключ `(window_id, at)` покрывает основной запрос графика (`WHERE window_id = ? AND at BETWEEN ?
AND ? ORDER BY at`) без отдельного индекса. Дедупликации нет: сетка замеров регулярная, и
пропуск строки означает «нет данных», что графику важно. Запись — `INSERT OR IGNORE`.

### 3.10. `lock_period` — интервалы блокировки

Выводимы из `sample.locked`, но хранятся явно: плитки «Locked this week» и красные полосы
графиков тогда не сканируют замеры.

```sql
CREATE TABLE lock_period (
  id         INTEGER PRIMARY KEY,
  window_id  INTEGER NOT NULL REFERENCES limit_window(id) ON DELETE CASCADE,
  cycle_id   INTEGER NOT NULL REFERENCES window_cycle(id) ON DELETE CASCADE,
  started_at INTEGER NOT NULL,                    -- первый замер с locked = 1
  ended_at   INTEGER,                             -- первый замер с locked = 0 после; NULL = идёт сейчас
  reason     TEXT,
  CHECK (ended_at IS NULL OR ended_at >= started_at)
) STRICT;
CREATE INDEX lock_period_window_idx ON lock_period (window_id, started_at);
CREATE UNIQUE INDEX lock_period_open_uidx ON lock_period (window_id) WHERE ended_at IS NULL;
```

Дополнительно к `locked` открывается период и при `percent = 100` без `locked_reason` (дизайн
считает 100 % красной плашкой), `reason = 'percent_100'`.

### 3.11. `daily_rollup` — дневные свёртки

Для периода 30 д в колонке сессии (дневные пики, план 01.1 §7.3) и для хранения дольше
`keep_days`.

```sql
CREATE TABLE daily_rollup (
  window_id      INTEGER NOT NULL REFERENCES limit_window(id) ON DELETE CASCADE,
  day            TEXT    NOT NULL,                -- 'YYYY-MM-DD' в поясе schema_meta.rollup_tz
  samples        INTEGER NOT NULL,
  peak_percent   INTEGER NOT NULL,
  avg_percent    REAL    NOT NULL,
  minutes_locked INTEGER NOT NULL DEFAULT 0,
  resets         INTEGER NOT NULL DEFAULT 0,      -- сколько раз окно сбрасывалось за день
  PRIMARY KEY (window_id, day)
) STRICT, WITHOUT ROWID;
CREATE INDEX daily_rollup_day_idx ON daily_rollup (day);
```

Пересчёт: при смене локального дня — за вчера; при старте — за все дни между
`schema_meta.last_rollup_day` и вчера; за сегодня — на лету из `sample`. Если пояс машины
отличается от `schema_meta.rollup_tz`, при старте таблица пересчитывается целиком из ещё
хранящихся `sample` (за пределами `keep_days` свёртки остаются как есть с пометкой в логе), и
`rollup_tz` обновляется.

### 3.14. Чего в базе нет и почему

- **Прогноз** — вычисляется по запросу из `sample` за окно скорости и кэшируется в памяти
  на один тик; хранить нечего.
- **Снимок «сейчас»** — в памяти файбера `store`; при старте восстанавливается из последних
  строк `sample` и `poll`, чтобы страница не была пустой до первого опроса (с пометкой
  давности).
- **Разрывы данных** — выводятся из `poll`/`sample` при запросе (`gap` = промежуток между
  соседними `sample.at` больше `2 × interval_sec`); таблицы нет.
- **Пользователи и сессии** — один токен доступа в конфиге, многопользовательского режима
  нет (план 01 §9).
- **Настройки** — в TOML (§2), не в базе; база не должна становиться вторым источником истины.

### 3.15. Представления для отчётов и отладки

```sql
CREATE VIEW v_current_occupancy AS
  SELECT ld.path AS dir, ld.name, a.email, o.token_state, o.started_at
  FROM occupancy o JOIN login_dir ld ON ld.id = o.login_dir_id
  LEFT JOIN account a ON a.id = o.account_id
  WHERE o.ended_at IS NULL;

CREATE VIEW v_latest_sample AS
  SELECT s.* FROM sample s
  JOIN (SELECT window_id, MAX(at) AS at FROM sample GROUP BY window_id) m
    ON m.window_id = s.window_id AND m.at = s.at;

-- человекочитаемое время для отладки в любом SQLite-клиенте (в приложении не используется)
CREATE VIEW v_sample_local AS
  SELECT a.email, w.kind, w.model, s.percent, s.locked,
         datetime(s.at, 'unixepoch', 'localtime')        AS at_local,
         datetime(c.resets_at, 'unixepoch', 'localtime') AS resets_local
  FROM sample s JOIN limit_window w ON w.id = s.window_id
  JOIN account a ON a.id = w.account_id JOIN window_cycle c ON c.id = s.cycle_id;
```

### 3.16. Индексы — сводка и объём

| таблица | ключ / индексы | оценка строк (4 учётки, 30 дней) |
|---|---|---|
| `sample` | PK `(window_id, at)`; `sample_at_idx`; `sample_cycle_idx (cycle_id, at)` | 4 учётки × ~4 окна × 288 × 30 ≈ 138 000 строк, ~6 МБ с индексом |
| `poll` | `(account_id, at)`, `(at)` | 4 × 288 × 30 ≈ 35 000 |
| `occupancy` | `(login_dir_id, started_at)`, `(account_id, started_at)`, частичный уникальный на открытую | десятки |
| `lock_period` | `(window_id, started_at)`, частичный уникальный на открытый | десятки–сотни |
| `window_cycle` | `UNIQUE (window_id, resets_at)`, `(window_id, starts_at)` | 4 учётки × 4 окна × (6 сессий/день × 30 + 4 недели) ≈ 3 000 |
| `daily_rollup` | PK `(window_id, day)`, `(day)` | 16 × 400 ≈ 6 400 |
| остальные | PK, `UNIQUE` по естественному ключу | единицы–десятки |

Все запросы страницы (план 01.1 §6.5, §7.4) — по диапазону `at` внутри одного `window_id`
или `account_id`; каждый закрыт индексом слева. Полных сканов нет, кроме ретенции по
`sample_at_idx`/`poll_at_idx`.

## 4. Запросы, которые обслуживает база

| потребитель | запрос | таблицы |
|---|---|---|
| `/api/snapshot` при старте | последние замеры каждого окна + последний `poll` учётки | `v_latest_sample`, `poll` |
| `/api/history?by=account` | `sample WHERE window_id IN (...) AND at BETWEEN ? AND ?`; `lock_period` за период; разрывы — из `poll` | `sample`, `lock_period`, `poll` |
| `/api/history?by=folder` | `occupancy` каталога за период → для каждого отрезка `sample` его учётки; при `30d` для сессии — `daily_rollup.peak_percent` | `occupancy`, `sample`, `daily_rollup` |
| прогноз (план 01.1 §2.7) | `sample` окна за `rate_window_days` рабочих дней, не раньше `resets_at − window` | `sample` |
| плитки статистики | `lock_period` за 7 д; `MAX(percent)` сессии за период; `AVG` по живым; смены почты — `occupancy` за 30 д | `lock_period`, `sample`, `occupancy` |
| `--once` | ничего не пишет и не читает: режим дифференциала с эталоном | — |
| `claude-limits export --range 30d --format csv\|json` | те же выборки в файл | `sample`, `occupancy`, `poll` |

Запись за один тик опроса — одна транзакция: `poll` + `sample` по окнам + переходы
`lock_period` + при необходимости `occupancy`/`account`/`limit_window`. Это один `fsync` в WAL
на тик, раз в 5 минут.

## 5. Обслуживание

- **Ретенция** — раз в сутки после свёртки: `DELETE FROM sample WHERE at < now − keep_days`,
  то же для `poll`; `daily_rollup` старше `rollup_keep_days`; `config_history` сверх
  `config_versions_keep`. Затем `PRAGMA incremental_vacuum`.
- **VACUUM** полный — раз в `vacuum_every_days`, при старте, если пора, и если база больше
  50 МБ; перед ним — бэкап.
- **Бэкап** — `VACUUM INTO 'backup/claude-limits-<stamp>.db'` перед каждой миграцией и раз в
  неделю; хранится `backups_keep` штук. Это целостная копия без остановки записи.
- **Целостность** — `PRAGMA quick_check` при старте; провал — база переименовывается в
  `claude-limits.corrupt-<stamp>.db`, поднимается последний бэкап, в лог и в шапку страницы —
  строка об этом. История без бэкапа теряется, настройки — нет: они в TOML.
- **Миграции** — `migrations/0001_init.sql`, `0002_….sql` из `embed_dir("migrations")`;
  применяются по одной в транзакции с обновлением `schema_meta.schema_version`; бинарь со
  старой схемой, открывший новую базу (`schema_version` больше, чем он знает), отказывается
  стартовать с понятным текстом.
- **Статистика планировщика** — `PRAGMA optimize` при закрытии соединения и раз в сутки после
  ретенции (SQLite сам решает, каким индексам нужен `ANALYZE`).
- **Размер** — при `keep_days = 30` и 4 учётках ≈ 10 МБ; при 20 учётках ≈ 50 МБ. Предел не
  ставится, но в `/api/health` есть `db_size_bytes`, и страница показывает его в настройках.

## 6. Приватность и безопасность данных

- В базе: почты, названия организаций, `subscription_type`, `rate_limit_tier`, пути каталогов,
  проценты, времена. **Нет**: токенов, `refreshToken`, `expiresAt`, содержимого `.claude.json`
  сверх названных полей, заголовков HTTP.
- `poll.error` и логи обрезаются до 200 символов и проходят фильтр: любая строка, похожая на
  bearer-токен (`sk-ant-…`, JWT-подобная), заменяется на `***` до записи.
- `config_history.toml` хранится с замаскированным `access_token`.
- Шифрования на диске нет — сознательно: в базе нет ничего, чего нет в `.claude.json` рядом
  (почты, организации), а SQLCipher добавил бы зависимость и ключ, который негде хранить.
- Файлы `0600`; каталог данных не индексируется поисковиками (на Windows атрибут
  `FILE_ATTRIBUTE_NOT_CONTENT_INDEXED`, на Linux — ничего не требуется).
- Удаление учётки из конфига (папка убрана) **не удаляет** её историю — она нужна статистике
  по папкам; явное стирание — `claude-limits forget <email>` удаляет `account` каскадом
  (`occupancy.account_id → NULL`, `sample`/`poll`/`lock_period`/`limit_window` — удаляются).

## 7. Пакет `nova-sqlite`

```
nova-sqlite/                       сиблинг-репо, раскладка как у nova-tls
├── nova.toml                      [package] name="sqlite"; [ffi] vendor_src_dirs = ["native/sqlite"]
├── sqlite.nv                      Connection { open(path, flags), exec(sql), prepare(sql) -> Statement, close },
│                                  Statement { bind([]SqlValue), step() -> Row?, reset, finalize }, Row { int(i), text(i), real(i), blob(i), is_null(i) }
├── ffi.nv                         extern "C" — sqlite3_open_v2, close_v2, prepare_v2, bind_*, step, column_*, finalize, exec, errmsg, changes, last_insert_rowid, busy_timeout
├── native/
│   ├── sqlite/sqlite3.c, sqlite3.h   амальгамация, закреплённая версия; флаги -DSQLITE_THREADSAFE=1 -DSQLITE_DEFAULT_WAL_SYNCHRONOUS=1 -DSQLITE_OMIT_DEPRECATED -DSQLITE_ENABLE_STAT4
│   └── sqlite_shim.c / .h         плоские сигнатуры: результат + код ошибки указателем (ffi-cookbook «Layered FFI»)
└── sqlite_test.nv                 in-memory база: create, insert, select с параметрами, транзакция, ошибка синтаксиса
```

Интеграция с `std/data/sql.nv`: `Connection.query(q Sql)` принимает результат `sql\`…\``-tag
и биндит `args` по порядку; ручных `?` в коде приложения нет. Соединение объявляется
`#thread_affine` (D172): компилятор не даст позвать его из другого файбера, что и закрепляет
решение 5. Спайк Ф.0 плана 01 получает пятый пункт: **SQLite из Nova** — сборка амальгамации
через `vendor_src_dirs` на Windows и Linux, WAL на реальном файле, 10 000 вставок в транзакции
и выборка по диапазону; вердикт — время и размер бинаря.

## 8. Приёмка (часть Ф.1 и Ф.2 плана 01)

1. Конфиг: путь выбирается по §1 на обеих ОС; portable-режим включается файлом рядом с бинарём;
   `--config` и переменная окружения переопределяют. Файл с ошибкой не роняет процесс, ошибка
   видна в логе и в шапке.
2. Запись конфига: `PUT` даёт байт-в-байт канонический TOML; повторный `PUT` без изменений —
   тот же файл; `If-Match` устаревший → `409`; перед записью строка в `config_history` с
   `***` вместо токена; `write_atomic` — при убитом процессе посреди записи старый файл цел
   (тест с моком `Fs`).
3. Схема: `0001_init.sql` создаёт все таблицы §3 со `STRICT`; `PRAGMA foreign_key_check`
   пуст; `EXPLAIN QUERY PLAN` для запросов §4 не содержит `SCAN` кроме ретенции; вставка
   `ended_at < started_at`, `email` с заглавной буквой или строки в `INTEGER`-колонку — ошибка
   `CHECK`/`STRICT`; `DELETE FROM account` уносит окна, циклы, замеры, опросы и уведомления, а
   `occupancy.account_id` становится `NULL`.
4. Запись тика: одна транзакция; при провале вставки `sample` не остаётся `poll` без пары
   (проверка на моке с инъекцией ошибки).
5. Занятость: смена почты в `.claude.json` фикстуры → закрытая и новая запись; `ok → expired`
   → новая запись; открытых на каталог — ровно одна (уникальный индекс держит).
6. Блокировки: последовательность замеров `0,100,100,0` даёт один `lock_period` с
   правильными границами; `percent = 100` без `locked_reason` — период с `reason =
   'percent_100'`.
7. Свёртки и ретенция: фикстура на 35 дней → после обслуживания `sample` содержит 30, свёртки
   — 35 дней, `daily_rollup.peak_percent` совпадает с `MAX` по удалённым замерам (проверка до
   удаления).
8. Целостность: испорченный файл базы → переименован, поднят бэкап, строка в логе; без бэкапа
   — пустая база, настройки целы.
9. Приватность: `grep` по файлу базы и логам на подстроки токенов из фикстур — ноль
   совпадений (обратная проба: нарочно записать токен в `poll.error` → тест краснеет).
10. Размер: 30 дней синтетики на 4 учётки — файл ≤ 12 МБ.
11. Циклы: смена `resets_at` в ответе даёт новую строку `window_cycle`, повтор — нет; замер
    ссылается на цикл, в который попадает его `at`; смена пояса машины между запусками
    пересчитывает `daily_rollup` и обновляет `rollup_tz`.
