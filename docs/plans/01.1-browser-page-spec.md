# План 01.1 — страница в браузере: каждый элемент дизайна и как он работает

**Статус:** ПРЕДЛОЖЕН 2026-09-06. **Подплан** плана [01-widget-on-nova.md](01-widget-on-nova.md):
детализирует его §0 и §3.3 и реализуется его фазой Ф.2, отдельных фаз и сроков у подплана
нет. Приёмка Ф.2 плана 01 = §11 здесь. Дизайн утверждён владельцем 2026-09-06:
[docs/design/browser-page](../design/browser-page/README.md), артборды `*.dc.html` там —
эталон разметки. Здесь — что каждый элемент значит, откуда берёт данные, как ведёт себя и
как считается. Это вход для Ф.2 (бэкенд и страница) плана 01; приёмка Ф.2 проверяется по
этому документу построчно.

Все примеры времени — в поясе машины, где работает бэкенд (план 01 §3.4). В макетах
«сейчас» = Сб 19:47.

## 0. Общие правила

- **Одна страница `web/index.html`**, встроенная в бинарь (`embed_dir("web")`).
  **Файлы: `index.html`, `app.css` и ES-модули JS** — все из того же `embed_dir`, плюс
  шрифты `.woff2` и `icon.svg`. Никаких сборок и никаких ВНЕШНИХ ресурсов.

  **Поправка 2026-09-08 (T2.20–T2.22): здесь стояло «три файла», а модулей JS уже
  четыре** — `app.js` (транспорт, виды, живые обновления), `format.js` (чистая
  арифметика), `render.js` (снимок → DOM), `reorder.js` (перетаскивание). Разделение
  сделано не для красоты: под node тестируется только то, что импортируется, и пока
  рендер жил внутри `app.js`, тест носил ЕГО КОПИЮ — то есть проходил бы на коде,
  которого никто не поставляет. Правило пункта — «ни сборки, ни сети, тот же origin»
  — модулями выполняется полностью: браузер грузит их сам по `import`, `<script
  type="module">` в разметке ровно один. Число файлов правилом не было и не будет:
  считать надо внешние ресурсы (их ноль) и шаги сборки (их ноль).

  **Поправка 2026-09-07, при написании каркаса (T2.19): здесь стояло «один `<style>`,
  один `<script>`», и по этому правилу страница вышла бы ПУСТОЙ.** Подплан 01.3 §1
  задаёт заголовок `Content-Security-Policy: default-src 'none'; script-src 'self';
  style-src 'self'; …` — без `'unsafe-inline'`, то есть встроенные `<style>` и
  `<script>` браузер выполнять не станет. Два подплана требовали несовместимого, и
  сломался бы тот, кто пишет страницу.
  **Разрешено в пользу CSP, и вот почему.** Смысл этого пункта — «ни сборки, ни сети», а
  не буквально один файл: §0 сам уже кладёт шрифты отдельными файлами из того же
  `embed_dir`. Раздельные файлы того же origin это условие выполняют полностью, а
  ослаблять CSP до `'unsafe-inline'` значило бы снять ровно ту защиту, ради которой
  заголовок и написан — на странице, показывающей почты и организации. Альтернатива с
  хешами отвергнута как хрупкая: хеш меняется от каждой правки стиля.
- **Состояние страницы** = последний снимок `/api/snapshot` + история (по запросу) +
  настройки `/api/config` (контракт всех маршрутов — подплан [01.3](01.3-api.md)). Страница ничего не считает из «сырого» ответа эндпоинта Anthropic:
  все производные (severity, доля времени, прогноз, подписи сброса) приходят из бэкенда
  готовыми, чтобы виджет SDL показывал те же числа (план 01, `model/format.nv`).
- **Локальные предпочтения браузера** (выбранный вид, стиль бара, период статистики) — в
  `localStorage`; **настройки приложения** (папки, порядок, интервал, пороги, график) — в
  конфиге через `PUT /api/config` (файл, пути, правила записи — подплан [01.2](01.2-storage.md) §2). Различие: первое — «как я смотрю в этом браузере», второе
  — «как работает бэкенд для всех».
- **Цвета** — CSS-переменные из README дизайна; никаких цветов в разметке, кроме
  вычисляемых ширин. Severity красит только заливку бара, число процента и плашку при 100 %.
- **Единицы**: проценты — целые; длительности — две старшие единицы (`2d 17h`, `1h 02m`,
  `45m`), минуты с ведущим нулём только после часов; время — `HH:MM`, день — `Tue`, дата
  вне недели — `5 Sep`.

## 1. Каркас страницы (общий для всех видов)

### 1.1. Шапка

| элемент | смысл | поведение |

| `19:47 · 15 s ago` | время последнего успешного опроса эндпоинта (`snapshot.fetched_at`) и давность | давность пересчитывается локально раз в секунду; после 90 с без событий SSE страница сама дёргает `/api/snapshot`; если `fetched_at` старше `2 × interval_sec`, текст становится янтарным — бэкенд жив, но данных нет |

## 2. Строка лимита — атом всех видов

Одна строка = одно окно лимита одной учётки. Сетка `100px · бар · 44px · 170px`, зазор
12 px, выравнивание по центру строки.

### 2.1. Название окна (100 px)

`session 5h` · `all 7d` · `<Model> 7d` (`Fable 7d`, `Opus 7d`). Источник:
`limits[].kind` → `session` / `weekly_all` / `weekly_scoped` + `scope.model.display_name`.
Порядок строк фиксирован: сессия, все модели, затем модели по алфавиту. Модель, которой
нет в ответе, не рисуется (у учётки может быть две строки). Цвет текста `--fg-soft`.

### 2.2. Бар расхода (гибкая колонка)

Стек из двух элементов, зазор 3 px:

**Основной бар** (10 px, скруглён 3 px, подложка `--track`):

- **заливка** — `percent` окна, цвет по severity: `normal` бирюзовый, `warning` янтарный,
  `critical` красный; `locked_reason` непустой → красный при любом проценте. Severity
  считает бэкенд по порогам конфига (`warning = 70`, `critical = 90`), не по `severity`
  эндпоинта: у эндпоинта свои пороги, наши — пользовательские; поле `severity` ответа
  сохраняется в JSON как `server_severity` для отладки;
- **штрихованный «призрак» прогноза** — от `percent` до `forecast.percent_at_reset`
  (обрезан по 100), тот же цвет, диагональная штриховка 2/5 px, прозрачность 0,75;
  рисуется только если прогноз включён (§5.3), доступен (§2.7) и больше текущего процента;
- **стиль «кубики»** (§5.1): вместо сплошной заливки и подложки — `repeating-linear-gradient`
  с шагом 10 px (8 px ячейка + 2 px зазор), цвет зазора = цвет ячейки, затемнённый на 12 %
  (`color-mix(in oklab, var(--c) 88%, black)`). **Ячейка либо полная, либо пустая**: JS при
  первом рендере и при `ResizeObserver` берёт ширину колонки, `N = floor((w + 2) / 10)`,
  ставит бару ширину `N × 10 − 2` (выравнивание по левому краю), заливке —
  `round(percent / 100 × N) × 10 − 2` (при `N` ячейках — полная ширина), призраку — от
  `filled × 10` до `round(forecast / 100 × N) × 10 − 2` через `mask` той же штриховкой.
  Тултип бара: `74% · 25 of 34 cells`. Скруглены только внешние края бара (контейнер
  `overflow: hidden`).

**Полоса времени** (3 px, скруглена 2 px, подложка `--track`), включается тумблером §5.2:

- заливка `--time-fill` (приглушённый фиолетовый `#7a6fa0`, вне палитры severity) —
  **доля окна, которая уже истекла**: `elapsed = window − (resets_at − now)`, доля
  `elapsed / window`, `window` = 5 ч для `session`, 7 сут для недельных. Пересчитывается
  локально раз в минуту без запроса к бэкенду (нужны только `resets_at` и `kind`);
- штриховка от истёкшей доли до `forecast.runs_out_at`, переведённого в долю окна
  (`(runs_out_at − window_start) / window`), если прогноз «не хватит» (§2.7); та же штриховка,
  что в основном баре, но цветом `--time-fill`;
- тултип: `time elapsed 61% · 4d 07h of 7d`; при штриховке добавляется
  `· at the current rate the limit runs out at 99% of the window`.

Чтение вместе: заливка расхода **левее** конца полосы времени — темп ниже, чем даёт окно;
**правее** — выше. Это единственное, что полоса призвана показать; числа не дублируются.

### 2.3. Процент (44 px)

`percent` целым, JetBrains Mono 600, прижат вправо, без переноса. Цвет — как у заливки
при `warning`/`critical`/locked, иначе `--fg`. У приглушённых строк (§3.3, 429) —
`--fg-muted`.

### 2.4. Время сброса (170 px)

Две строки, прижаты вправо, без переноса, JetBrains Mono:

- **строка 1**, 11 px, `--fg-muted`: `Tue 13:00 (2d 17h)` — момент сброса
  (`resets_at`, локальное время; день недели, если не сегодня; `5 Sep 13:00`, если дальше
  6 суток) и время до него в скобках. У сессии без дня: `20:50 (1h 02m)`. У locked
  строка та же, а слово `unlocks` не пишется — замок и «locked until» стоят в шапке
  учётки (§3.2). Остаток пересчитывается локально раз в минуту;
- **строка 2**, 10 px — **прогноз** (§2.7), только при включённом прогнозе:
  - хватает: `→ 31% at reset`, цвет `--fg-subtle`;
  - не хватает: `ends Tue ~12:30 (2d 17h)`, цвет `--warning` (янтарный): момент
    исчерпания и время до него от «сейчас». Тильда — признак оценки. Обе строки
    заканчиваются скобками одинаковой длины и потому выровнены; тултип строки 2:
    `at the current working-hours rate the limit hits 100% in 2d 17h — Tue ~12:30, 30 m
    before the Tue 13:00 reset`;
  - прогноз недоступен (§2.7) — строки 2 нет, высота строки лимита меньше; это нормально.

### 2.5. Наведение и клик

Наведение на строку подсвечивает её подложкой `--surface-hover`. Клик по строке в списке
или плашках открывает статистику (§6) с этой учёткой, прокрученной наверх, и периодом
`7 d` (или `24 h` для сессии). Клик по названию учётки — то же.

### 2.6. Доля времени — формула

```
window        = kind == session ? 5h : 7d
window_end    = resets_at
window_start  = resets_at − window
elapsed_share = clamp((now − window_start) / window, 0, 1)
```

Считает страница (и виджет) из `resets_at`; бэкенд ничего не шлёт.

### 2.7. Прогноз — формула (бэкенд, `model/forecast.nv`)

**ВОПРОС ВЛАДЕЛЬЦУ, поднят 2026-09-08 при реализации T2.16: три числа приёмочного
вектора не сходятся между собой.** §11 п. 5 задаёт вектор «36 рабочих часов истории,
74 %, 14 рабочих часов до сброса» и требует от него И `103 %` при сбросе, И
`runs_out_at` = сброс − 30 мин ± 5. По формуле выше из этого вектора выходит:

- ставка `74 / 36 ч = 2,0556 %/ч` — совпадает с `rate_per_hour: 2.06` на артборде;
- `percent_at_reset = 74 + 2,0556 × 14 = 102,8` — совпадает со `103 %`;
- `runs_out`: до 100 % остаётся 26 %, это `26 / 2,0556 = 12,65` рабочего часа, то есть
  **81 рабочая минута до сброса**, а не 30.

Чтобы получить 30 минут, нужна ставка `26 / 13,5 ч = 1,93 %/ч`, а она даёт при сбросе
`101 %`, а не 103. **Одновременно все три числа не выполняются ни при какой ставке.**
Умолчание, пока молчат: реализация следует ФОРМУЛЕ этого раздела, тест
`src/model/forecast_test.nv` закрепляет 81 минуту и объясняет расхождение в
комментарии; подгонять код под артборд я не стал. Что изменит ответ: если верны 30
минут, значит в формуле не хватает правила (например, последние минуты перед сбросом
считаются иначе), и его надо записать здесь.

Вход: история замеров учётки за окно (`/api/history`, шаг 5 мин), рабочий график из
конфига (§5.3), `now`, `resets_at`, `percent`.

```
work(t0, t1)   = рабочие минуты между t0 и t1 по графику (дни недели × часы),
                 вне графика минуты идут с весом off_hours_rate (0 по умолчанию)
rate_window    = session: 60 календарных минут; weekly: последние 3 рабочих дня,
                 но не раньше window_start
used_in_window = percent(now) − percent(начало rate_window)   [по истории; если
                 внутри был сброс — с момента сброса]
rate           = used_in_window / work(начало rate_window, now)   [% за рабочую минуту;
                 для session — за календарную минуту]
remaining_work = work(now, resets_at)
percent_at_reset = percent + rate × remaining_work
runs_out_at    = момент t ≥ now, когда percent + rate × work(now, t) достигает 100
                 (обратный ход по графику; если t > resets_at — «хватает»)
```

Правила:

- `rate ≤ 0` (за окно расчёта расход не рос) → прогноз `percent_at_reset = percent`,
  «хватает»; призрак не рисуется, строка 2 показывает `→ 74% at reset`;
- истории меньше 30 минут (бэкенд только запустился) → прогноз **недоступен**, поле
  `forecast: null`, строки 2 и штриховок нет, тултип процента: `forecast after 30 min of
  history`;
- `locked` → прогноз недоступен (уже 100 %);
- `stale`/`unknown`/`error` учётка → недоступен;
- сессия (5 ч) считается по календарным минутам: график к ней не применяется;
- ответ бэкенда: `forecast { percent_at_reset, runs_out_at | null, rate_per_hour,
  basis: "working-hours" | "clock", sample_minutes }`; страница только форматирует.

Почему график: расход идёт в рабочее время, а окно тикает круглосуточно; без графика
прогноз в пятницу вечером всегда «не хватит». В макете: Fable 74 % при 36 рабочих часах →
2,06 %/ч; до сброса 14 рабочих часов → 103 %, исчерпание за полчаса до сброса. Календарный
расчёт дал бы 121 % и понедельник.

## 3. Вид «Список» (`Main.dc.html`, по умолчанию)

Одна плашка `--surface`, граница `--border`, радиус 12 px. Внутри — блоки учёток,
разделённые линиями `--border`, без зазоров.

### 3.1. Блок учётки

Шапка блока: **почта** (600) · организация · каталоги через ` · ` (`Tech Center · nv-lang`,
`Personal · dev, dev-wsl`), всё в одну строку, каталоги — `--fg-muted`. Ниже — строки
лимитов §2 с зазором 6 px. Порядок учёток — из конфига (`accounts_order`, §4.2), новые
учётки — в конец.

### 3.2. Состояния учётки

| состояние | когда | как выглядит |
|---|---|---|
| `ok` | последний опрос удался | обычный блок |
| `ok` + **любое окно на 100 %** или `locked_reason` | | блок на **красноватой плашке**: фон `--surface-critical`, границы `--border-critical`, подложки баров `--track-critical`; в шапке справа замок и `locked until 21:10` (из `resets_at` заблокированного окна) красным; при 100 % без `locked_reason` — тот же вид, подпись `at 100% until 21:10` |
| `stale` | токен истёк по `expiresAt`, запрос не делался | блок в одну строку: почта и организация `--fg-muted`, каталоги `--fg-subtle`; справа текст `token expired 5 Sep 18:02 · start Claude Code under this login`; баров нет; фон `--surface-alt`, граница пунктирная |
| `unknown` | сеть или 429 | шапка обычная, справа янтарный бейдж `429 · retry 19:49 · data 19:41` (или `network error · retry 19:52`); строки лимитов — **последний удачный снимок**, вся группа строк с `opacity: 0.5`; полосы времени и прогноз для приглушённых строк не рисуются |
| `error` | 401 при живом по `expiresAt` токене, невалидный JSON | как `stale`, текст причины: `token rejected (401) · start Claude Code under this login` / `unexpected response · see log` |
| `hidden` | пользователь скрыл (§5.4) | не показывается ни в одном виде; в подвале `· 1 hidden` |

Порядок внутри блока и переходы между состояниями анимируются 150 мс по `opacity`; при
приходе события SSE меняются только тексты и ширины, DOM не пересоздаётся (ключ — почта).

## 4. Вид «Плашки» (`CardsView.dc.html`)

Те же блоки, но каждая учётка — отдельная плашка с зазором 10 px и **ручкой** слева
(6 точек, 22 px, `--fg-subtle`, `cursor: grab`).

### 4.1. Перетаскивание

- HTML5 drag-and-drop с fallback на pointer events (для тач-экранов);
- при захвате плашка поднимается: тень `0 14px 34px rgba(0,0,0,.55)`, поворот −0,6°,
  сдвиг 10 px, `cursor: grabbing`; на её месте остаётся пустой контур;
- между плашками, куда упадёт, рисуется линия 3 px `--normal` (бирюзовая) с отступами 6 px;
- отпускание → новый порядок сразу в DOM, затем `PUT /api/config { accounts_order: [emails] }`;
  ошибка → откат порядка и тост «could not save order»;
- порядок общий для списка, плашек и статистики; в панели настроек тот же список с ручками;
- клавиатура: ручка фокусируема, `Space` берёт, стрелки двигают, `Space` кладёт, `Esc` отменяет.

### 4.2. Конфиг

```toml
[ui]
accounts_order = ["main@example.com", "work@example.org", "qa@example.org"]
hidden_accounts = ["ops@example.org"]
```

Ключ — почта (одна учётка на все каталоги). Почты, которых нет в списке, идут после
перечисленных в порядке обнаружения.

## 5. Панель настроек (`SettingsPanel.dc.html`)

Поповер 400 px под шестерёнкой, заголовок, секции, футер `Cancel` / `Save`. Открытие —
`GET /api/config`; `Save` — один `PUT /api/config` со всеми полями; бэкенд валидирует как при
старте и отвечает `200` с применённым конфигом или `400 { field, message }` — поле
подсвечивается, текст под ним. Изменения вступают в силу без перезапуска: интервал и график
— со следующего тика, папки — немедленным переобнаружением, порт и `bind` — переоткрытием
слушателя (страница после `Save` переподключается по новому адресу и предупреждает, что
ссылка сменилась).

### 5.1. View

| контрол | тип | ключ | действие |
|---|---|---|---|
| Layout `List / Cards` | сегмент | `localStorage.view` (браузер) | то же, что переключатель в шапке |
| Bar style `Rounded / Blocks` | сегмент с превью | `localStorage.bar_style` (браузер) | §2.2; превью — миниатюра бара соответствующего стиля |
| Reset time · show countdown | тумблер | `localStorage.countdown` | выкл. — в строке 1 §2.4 только момент `Tue 13:00`, без скобок |
| Hide logins with an expired token | тумблер | `[ui] hide_stale = false` (конфиг) | `stale`/`error` учётки не показываются; счётчик в подвале |

### 5.2. Time elapsed bar

Тумблер `[ui] time_bar = true`. Выкл. — полос времени нет, строка лимита ниже на 6 px.

### 5.3. Forecast

| контрол | ключ | значение по умолчанию |
|---|---|---|
| Show forecast at reset | `[forecast] enabled` | `true` |
| Working days `Mo … Su` (кнопки-переключатели) | `[forecast] work_days` | `["mon","tue","wed","thu","fri"]` |
| Working hours `09:00 – 19:00` | `[forecast] work_from`, `work_to` | `"09:00"`, `"19:00"`; допускается через полночь |
| Usage outside working hours `0%` of the working rate | `[forecast] off_hours_rate` | `0` (0–100) |

Подпись под секцией объясняет формулу §2.7 одной строкой. Пустой набор дней → `400`
«pick at least one working day».

### 5.4. Login folders

Список папок из конфига — **источник учёток**. Строка: иконка папки, путь (моно, обрезается
с многоточием, полный — в тултипе), под ним что найдено, крестик удалить.

| текст под путём | когда |
|---|---|
| `parent folder · 3 logins found: nv-lang, dev, qa` | `accounts_parent`-запись; перечислены дочерние каталоги с `.credentials.json` |
| `single login · main@example.com` | каталог с логином; почта из `.claude.json` |
| `single login · work@example.org (same login as dev)` | почта совпадает с другим каталогом — будет одна учётка |
| `no .credentials.json here` (янтарно, иконка янтарная, фон `--surface-alt`) | путь есть, логина нет — запись остаётся, учётки не даёт |
| `folder not found` (красно) | пути нет |

Добавление: поле пути (`~`, переменные окружения и UNC-пути WSL допустимы), кнопка
`Browse…` (в браузере недоступна — открывает подсказку «type the path»; в виджете SDL —
системный диалог), кнопка `Add`. Тип записи бэкенд определяет сам: если внутри есть
`.credentials.json` — `single`, иначе если есть дочерние каталоги с ним — `parent`, иначе
`empty`. Удаление — немедленно из списка, применяется по `Save`. Папки по умолчанию
(`~/.claude`, `CLAUDE_CONFIG_DIR`) показываются как обычные строки с пометкой `default`,
их можно удалить.

Конфиг: `accounts_parent` и `accounts` из плана 01 §4 сливаются в один список:

```toml
[[folders]]
path = "C:/accounts"      # parent — определяется содержимым

[[folders]]
path = "~/.claude"
```

Секция **Accounts** ниже — производная: учётки, найденные в папках, с ручками порядка
(§4.1) и чекбоксом «показывать» (`hidden_accounts`). Подпись `found in the folders above ·
drag to reorder`.

### 5.5. Polling

`Interval` — число секунд, `[poll] interval_sec = 300`; меньше 60 → `400` «minimum is 60 s
(the server rate-limits eager polling)»; подпись под полем повторяет это.

### 5.6. Thresholds

`Warning 70%`, `Critical 90%` — `[thresholds] warning`, `critical`; `0 < warning < critical ≤
100`, иначе `400`. Квадраты цветов рядом — просто легенда.

### 5.7. Server

`Listening on 127.0.0.1:7391` — текст из `/api/health`. Тумблер `Allow access from the local
network · needs a token and a certificate` → `[server] bind = "0.0.0.0"`; при включении появляются
поле `access_token` (генерируется кнопкой, показывается один раз) и поля `tls_cert`/`tls_key`
(пути к PEM, подсказка с командой `openssl`/`mkcert` из README); без токена или сертификата `Save`
даёт `422` с подсветкой поля (подплан 01.3 §3.8). До фазы Ф.6 плана 01 тумблер неактивен с подсказкой
`LAN access arrives in a later version`, остальное в этом абзаце — контракт Ф.6. Смена `bind`/`port`/`tls_*`
применяется переоткрытием слушателя; страница показывает новый адрес `https://…`, отпечаток
сертификата и QR-код для телефона (SVG, без библиотек). На телефоне первая страница — `/login`
с полем токена; токен в адресной строке не появляется. Сетевые запросы страницы следуют
политике повторов подплана 01.3 §5: автоматически повторяются только `GET`, до трёх раз, с
`Retry-After` в приоритете.

### 5.8. Desktop widget

`Show the widget` → `[widget] enabled`; `Always on top` → `[widget] always_on_top`. В
браузере без запущенного виджета тумблеры меняют только конфиг; виджет подхватывает их на
следующем тике (план 01, решение 3).

## 6. Вид «Статистика» по учёткам (`StatsView.dc.html`)

### 6.1. Строка фильтров

- период `24 h / 7 d / 30 d` — `localStorage.stats_range`; запрос
  `GET /api/history?range=…&by=account`;
- группировка `Accounts / Folders` — переключает §6 и §7;
- справа — легенда помодельного графика (`Fable`, `Opus`) с квадратами цветов моделей;
  цвета моделей фиксированы по имени в порядке появления (палитра §8), не по рангу.

### 6.2. Плитки

Четыре плитки, каждая — подпись, число (моно 20 px), пояснение:

| плитка | формула | цвет числа |
|---|---|---|
| Locked this week | сумма интервалов `locked` по всем учёткам за 7 сут; пояснение — кто и когда | красный, если > 0 |
| Peak session | максимум `session.percent` за период; кто и сколько раз достигал 100 % | `--fg`; красный при 100 |
| Avg session window | среднее `session.percent` по живым учёткам по замерам за период | `--fg` |
| Pace · working hours | максимальный `rate_per_hour` среди недельных окон; пояснение — кто и когда кончится (`Fable ends Tue ~12:30, 30 m before reset`) | янтарный, если есть «не хватит» |

Плитки не кликабельны. При отсутствии данных — `—` и пояснение «no history yet».

### 6.3. Карточка учётки

Сетка `190px · 3 колонки`. Слева: почта, организация, каталоги, строка итога
(`peak 62% · never locked` / `locked 2h 10m this week` красным / `no data since 5 Sep
18:02 · token expired` / `gap since 19:41 · HTTP 429` янтарным). Красноватая плашка — по
тому же правилу, что в списке (§3.2). Три колонки = три окна:

| колонка | ось X | серия | подпись справа |
|---|---|---|---|
| `session · 24 h` | всегда последние 24 ч независимо от периода (при `30 d` — дневные пики, §7.3) | `session.percent` | `now 9%` |
| `all models · 7 d` | период | `weekly_all.percent` | `now 22%` |
| `per model · 7 d` | период | по линии на модель, цвета моделей | `Fable 74% · Opus 12%`; у учётки без помодельного лимита — плоский пунктир и `no per-model limit on this plan` |

### 6.4. График

SVG 280×84, `viewBox` фиксированный, растягивается по ширине колонки. Элементы:

- сетка: три горизонтали 0/50/100 % `--border`, без подписей оси Y (100 % = верх области);
- подписи оси X снизу, моно 10 px `--fg-subtle`: `20:00 · 02:00 · 08:00 · 14:00 · now`
  для 24 ч; `Sat · Mon · Wed · Fri · now` для 7 д; `Aug 7 · Aug 15 · Aug 22 · Aug 30 ·
  now` для 30 д;
- **линия** 2 px одного цвета (бирюзовый для одиночных серий), заливка под ней 12 %
  прозрачности; помодельная колонка — линии без заливки;
- **пунктирные вертикали** `--fg-subtle` 2/3 px — моменты сброса окна (перепад
  `percent` вниз более чем на 30 п.п. между соседними замерами или известный `resets_at`);
- **красная полоса** (`--critical`, 18 %) — интервалы `locked`;
- **янтарная полоса** (`--warning`, 15 %) — интервалы без замеров (429, сеть) длиннее
  одного интервала опроса; линия в них не рисуется (разрыв);
- **наведение**: вертикаль `--fg-muted` 1 px по всей высоте, точка 4 px на линии с обводкой
  цветом плашки, тултип над точкой `13:12 · 57%` (моно 10,5 px, подложка `--track`);
  в помодельной колонке тултип перечисляет все серии; наведение на одну колонку
  двигает вертикаль во всех трёх колонках карточки (общая ось времени);
- значения — из `/api/history` без интерполяции, точка на ближайший замер; между замерами
  линия прямая.

### 6.5. Данные

`GET /api/history?range=7d&by=account` →
`{ range { from, to, step_sec }, accounts[] { id, email, color_slot, summary }, series[] { account_id,
kind, model, points[] { at, percent, resets_at, locked }, resets[], locks[] { from, to, reason },
gaps[] { from, to, cause } }, tiles }` — серии плоские, страница группирует их по `account_id`
(подплан 01.3 §3.6); фильтр по учётке — `POST /api/history/search` с `account_id` в теле.
Бэкенд хранит замеры в DuckDB (подплан [01.2](01.2-storage.md) §3.11 `sample`, §3.12 `lock_period`;
разрывы выводятся из §3.8 `poll`); перезапуск историю не теряет. Замер пишется при
каждом удачном опросе; при интервале больше 5 мин точки реже — график это переживает.

## 7. Вид «Статистика» по папкам (`StatsFolders.dc.html`)

Папка = место человека; в ней со временем сменяются учётки. Показывает **историю
каталога**, склеенную из историй сидевших в нём учёток.

### 7.1. Строка фильтров и легенда

Период тот же; группировка `Folders`. Справа — легенда **учёток** (квадраты цветов
`main@…`, `work@…`, `qa@…`, серый `no login`) и `- - Opus` (пунктир = вторая модель).
Цвет учётки закрепляется за почтой при первом появлении в порядке конфига и не меняется
при фильтрах (палитра §8).

### 7.2. Плитки

| плитка | формула |
|---|---|
| Login switches · 30 d | число смен почты в каталогах за период; пояснение — цепочка самой активной папки `dev: main → work → main → qa` |
| Locked while in a folder | сумма `locked` тех учёток, что сидели в папке, за время их присутствия; кто |
| Folder with most logins | папка с наибольшим числом разных почт |
| Days without a login | дни, когда в папке не было валидного логина (`stale`/пусто); какая папка, почему |

### 7.3. Карточка папки

Слева: имя каталога (иконка папки), полный путь, строка «сейчас»:
`now: qa@example.org · since Sep 3` / `no login since Sep 2 · token expired`.

**Полоса занятости** над графиками (22 px, на всю ширину трёх колонок): отрезки по
времени, кто был залогинен; цвет учётки на 35 %, подпись `main@` внутри, если отрезок шире
46 px; `no login` — серый 25 %. Источник — журнал занятости (§7.4). Наведение на отрезок —
тултип `work@example.org · Aug 16 09:12 → Aug 29 18:40 · 13 d`.

Три графика — те же окна, что в §6.3, с отличиями:

- при `30 d` колонка сессии показывает **дневные пики** (максимум `session.percent` за
  календарный день, точка на полдень) — иначе 24 ч × 30 сливаются в шум;
- **линия окрашена цветом учётки**, которая сидела в папке в этот момент, и **обрывается
  на смене** (разрыв 0,15 сут): скачок уровня после разрыва — это другая учётка, а не расход;
- фон под линией — те же отрезки занятости 10 % прозрачности; серые отрезки «нет логина» —
  18 %;
- помодельный график: сплошная — первая модель учётки, пунктирная — вторая; цвет — учётки.

### 7.4. Журнал занятости и ограничение

Бэкенд при каждом обнаружении (старт, `PUT /api/config`, раз в `interval_sec`) фиксирует
для каждого каталога почту из `.claude.json` и состояние токена; изменение почты или
переход `ok ↔ stale` пишет запись в таблицу `occupancy` (подплан [01.2](01.2-storage.md) §3.6): закрывает открытую запись каталога и открывает новую.

**Поправка 2026-09-08 (T2.24): форма ответа — по 01.3 §3.6, а не по наброску, что
стоял здесь.** Здесь было написано, что `GET /api/history?by=folder` отдаёт
`folders[] { path, name, occupancy[] …, points[] … }`, то есть занятость и точки
ВЛОЖЕНЫ в папку. Подплан 01.3 §3.6 задаёт другое: `folders[]`, ПЛОСКИЙ `occupancy[]`
и ПЛОСКИЙ `series[]`, все со склейкой по `login_dir_id`, причём серия — отрезок ОДНОЙ
учётки со своими `from`/`to`. Два подплана требовали несовместимого, и сломался бы
тот, кто пишет страницу.
**Разрешено в пользу 01.3, и не монеткой:** (1) этот же документ в §6.5 для
`by=account` уже прямо отсылает форму к 01.3 («серии плоские, страница группирует их
по `account_id`») — здесь тот же случай, и разнобой был бы случайным; (2) плоские
серии-отрезки дают ровно то, чего требует §7.3, — линия рвётся на смене учётки,
потому что после смены это ДРУГАЯ серия, а не другой участок той же; при вложенных
`points[]` разрыв пришлось бы вычислять по журналу и синхронизировать с ним вручную.
Цена ошибки измерена ранее в этом же плане: рендер списка предполагал вложенные
`limits` и против живого бэкенда рисовал бы каждую учётку пустой.

**Ограничение, которое страница называет прямо** (подпись под фильтрами): эндпоинт
считает лимиты на логин. Две папки под одной почтой одновременно показывают одну и ту же
кривую; разделить расход между ними нельзя. Статистика «по людям» честна, когда у каждого
человека свой логин.

## 9. Живые обновления

- `EventSource('/api/events')`: событие `snapshot` (тело = `/api/snapshot`) после каждого
  опроса и после `POST /api/snapshot/refresh`; событие `config` после `PUT /api/config` (любой
  вкладкой) — страница перечитывает конфиг и перерисовывает; `ping` раз в 30 с;
- страница применяет снимок точечно: по почте находит блок, обновляет тексты, ширины,
  классы состояния; новая учётка — блок добавляется на своё место по порядку; исчезнувшая
  (папку удалили) — блок уходит с анимацией;
- статистика при открытом виде дозапрашивает `/api/history` при каждом `snapshot`, но не
  чаще раза в минуту; при закрытом — не запрашивает;
- локальные таймеры (давность, остатки времени, доля времени) — раз в секунду для
  давности, раз в минуту для остального; вкладка в фоне (`document.hidden`) таймеры
  останавливает и догоняет при возврате.

## 10. Доступность и клавиатура

- все интерактивные элементы — настоящие `<button>`/`[role=tab]`, фокус видим
  (`outline` 2 px `--fg-muted`);
- бары имеют `role="meter"`, `aria-valuenow`, `aria-valuetext="74%, Fable, 7 days, resets
  Tue 13:00"`; полоса времени и призрак — `aria-hidden`, их смысл дублируется в
  `aria-valuetext` («61% of the window elapsed; forecast 103% at reset»);
- графики — `role="img"` с `aria-label` вида `session usage over 24 hours, now 9%, peak
  62%`, плюс скрытая таблица значений по кнопке «table» в углу карточки (для чтения с
  экрана и копирования);
- цвет никогда единственный носитель смысла: locked — замок и текст, «не хватит» — текст
  `ends …`, состояния — текст в шапке блока.
