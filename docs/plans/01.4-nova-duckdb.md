# План 01.4 — пакет `nova-duckdb`: DuckDB со статически прилинкованными расширениями в Nova

**Статус:** ПРЕДЛОЖЕН 2026-09-06. **Подплан** плана [01-widget-on-nova.md](01-widget-on-nova.md),
выделен по слову владельца: «нужен отдельный модуль под DuckDB». Это **спутниковый пакет**
(сиблинг-репо `nova-duckdb`, как `nova-tls`, `nova-http`, `nova-polaris`), а не часть
`claude-limits`: у него свой репозиторий, теги, тесты и релизы; `claude-limits` тянет его
git-зависимостью по тегу. Хранилище приложения, схема и переход на DuckDB — подплан
[01.2](01.2-storage.md) (§0а — результаты спайка, §0б — решение о сборке с расширениями);
здесь — только сам пакет.

Факты сверены 2026-09-06: спайк [`spikes/duckdb-static/`](../../spikes/duckdb-static/VERDICT.md)
(линковка с рантаймом Nova чистая, CRT статический, +36 МБ, амальгамация без `core_functions`
и `icu`); канон спутниковых пакетов — `nova-tls` (`[ffi]` + `native/` + `.nv`-фасад),
CMake-сборка с кэшем — `nova-sdl` (план 01 §5); типы std: `Timestamp` (нс от эпохи,
`std/time/…`), `Date` (`epoch_day`), `DateTime`, `TimeZone`, `Duration`, `int128`
(`std/math/int128.nv`); SQL-шаблоны с параметрами — `std/data/sql.nv` (`sql\`…\``, `SqlValue`);
привязка к потоку — `#thread_affine` (D172).

## 0. Решения

| № | решение | почему |
|---|---|---|
| 1 | **Сборка из полного репозитория DuckDB**, сабмодуль по тегу, CMake; **амальгамация не используется** | в амальгамации нет `core_functions` и `icu`, а без них нет `date_trunc`, `time_bucket`, `TIMESTAMPTZ` (спайк §0а) |
| 2 | **Расширения `core_functions` и `icu` прилинкованы статически**, автозагрузка и автоустановка **выключены на уровне сборки и в каждом соединении** | один бинарь без сети и без `~/.duckdb`; слово владельца 2026-09-06 |
| 3 | **Один C-шим с плоскими сигнатурами**, `.nv`-фасад над ним; наружу — типизированные хендлы, никаких `*()` в API пакета | канон ffi-cookbook «Layered FFI» и `nova-tls/src/ffi.nv` |
| 4 | **Соединение `#thread_affine`**; пакет не делает свой пул и не обещает многопоточность | DuckDB потокобезопасна, но приложениям на Nova нужен один владелец (план 01 §3.1); компилятор не даст вызвать соединение из другого файбера |
| 5 | **`Connection.query(Sql)` принимает `sql\`…\``** и биндит `args` по порядку; конкатенации SQL в API нет | `std/data/sql.nv` уже даёт безопасные плейсхолдеры |
| 6 | **Appender — первоклассная часть API**, документация пакета ведёт к нему для любой записи больше одной строки | построчный `INSERT` ≈ 2 мс (спайк), Appender — микросекунды |
| 7 | **Типы отображаются строго**: `TIMESTAMP`/`TIMESTAMPTZ` ↔ `Timestamp`, `DATE` ↔ `Date`, `BOOLEAN` ↔ `bool`, `DECIMAL` ↔ `int128` + масштаб, `UUID` ↔ `Uuid` (`std/identifiers`), `ENUM` ↔ `str`; неявных приведений нет | ради типов DuckDB и выбирают; терять их на границе FFI нельзя |
| 8 | **Версия DuckDB и набор расширений — часть публичного API пакета**: в `nova.toml`, в `Database.version()`, в тесте | приложение пишет их в `schema_meta`; смена — минорный релиз пакета |
| 9 | **Шифрование файла — часть API открытия**: `Database.open(path, OpenOptions.encryption_key([]u8))` → `ATTACH … (ENCRYPTION_KEY …)`; ключ передаётся байтами, в строку SQL не склеивается, из памяти затирается после открытия | конвенция по БД §13.3 требует шифрованного файла у встраиваемой базы с ПДн; реализация AES-256-GCM на mbedTLS входит в ядро DuckDB, отдельной зависимости нет; проверяется ступенью S0 |
| 10 | **Объём привязки — ядро DuckDB плюс потребности приложения, а не весь C API** (§4.1); новые возможности добавляются по запросу потребителя минорными версиями пакета; шапка каждого модуля и README пакета говорят об этом прямо | каждая экспортированная функция под `#stable` — обязательство поддержки; обёртки без потребителя замораживают API, который никто не проверял (решение владельца 2026-09-07) |

## 2. Сборка DuckDB

Скрипт `scripts/build-duckdb.*` (флаги сверяются в Ф.0 п.5 плана 01 по CMake DuckDB 1.5):

```sh
cmake -S native/duckdb -B native/build -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_EXTENSIONS="core_functions;icu" \
  -DENABLE_EXTENSION_AUTOLOADING=0 -DENABLE_EXTENSION_AUTOINSTALL=0 \
  -DBUILD_SHELL=0 -DBUILD_UNITTESTS=0 -DBUILD_BENCHMARKS=0 \
  -DCMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded        # Windows: /MT — как рантайм Nova (спайк: конфликтов нет)
cmake --build native/build --target duckdb_static -j
```

- Выход — статическое ядро плюс по библиотеке на расширение и на вендоренную зависимость
  (`re2`, `fmt`, `utf8proc`, `hyperloglog`, `fastpforlib`, `skiplistlib`, `mbedtls`-часть, `yyjson`,
  `fsst`, `zstd`, `miniz`, …). Скрипт копирует их в `native/lib` и пишет `libs-manifest.txt`
  в порядке от зависимого к зависимости; из манифеста собирается `[ffi] libs`.
- **Кэш**: ключ `duckdb-<тег>-<ОС>-<sha256 флагов>-<версия clang>`; при совпадении сборка
  пропускается (локально — файл-метка в `native/lib/.built`; CI — `actions/cache`).
- Требования сборки: CMake ≥ 3.20, Ninja, clang (на Windows — `clang-cl` под `vcvars64`; на
  Linux — `clang++`), 8 ГБ RAM, ~40–60 мин на 16 ядрах без кэша (оценка; спайк на одном TU
  амальгамации: 11 мин Windows / 20 мин Linux при 3,5–4,8 ГБ).
- Обновление DuckDB: сменить тег сабмодуля, пересобрать, прогнать тесты, поднять минорную версию
  пакета; список библиотек может измениться — манифест перегенерируется.

Известные грабли (из спайка, повторять не нужно): `WIN32_LEAN_AND_MEAN` и `NOMINMAX` обязательны
на Windows (макрос `interface` из `windows.h`); шим определяет `DUCKDB_STATIC_BUILD` **до**
`#include "duckdb.h"`, иначе символы объявлены `dllimport`; `rstrtmgr.lib` нужен линкеру;
`at` — зарезервированное слово в SQL DuckDB.

## 3. `[ffi]` и шим

```toml
[ffi]
c_shims      = ["native/duckdb_shim.c", "native/duckdb_shim.h"]
include_dirs = ["native/", "native/duckdb/src/include"]
libs         = [ # из scripts/libs-manifest.txt, от зависимого к зависимости
  "core_functions_extension", "icu_extension", "duckdb_static",
  "duckdb_re2", "duckdb_fmt", "duckdb_utf8proc", "duckdb_hyperloglog", "duckdb_fastpforlib",
  "duckdb_skiplistlib", "duckdb_mbedtls", "duckdb_yyjson", "duckdb_fsst", "duckdb_zstd", "duckdb_miniz" ]
lib_dirs     = ["native/lib"]
```

Шим — только плоские функции над C-API DuckDB, без логики: результат и код ошибки через
выходные указатели, строки — `nova_str`/`(*u8, int)`, время — `int64` микросекунд UTC, decimal —
`(int128, scale)`. Названия — `ddb_*` (имя модуля, без вендорного префикса, как `tls_*`).
Ошибка DuckDB достаётся строкой `duckdb_result_error` / `duckdb_prepare_error` / `duckdb_appender_error`
и передаётся в Nova как `DuckError { code, message }`.

Обязательные настройки в шиме при открытии (`ddb_open`), их нельзя обойти из Nova:

```sql
SET autoinstall_known_extensions = false;
SET autoload_known_extensions = false;
SET temp_directory = '<data_dir>/tmp';        -- из аргумента open, а не ~/.duckdb
SET TimeZone = 'UTC';                         -- приложение само переводит в локальный пояс
SET memory_limit = '<opts.memory_limit>';     -- по умолчанию 512MB
SET threads = <opts.threads>;                 -- по умолчанию 2
```

## 4. Публичный API (`src/duckdb.nv`)


> **── amendment 2026-09-08 ── the facade returns `Result`, not `Fail`.**
>
> Every signature in this section used to read `Fail[DuckError] -> X`. That was
> wrong from the day it was written, and it was wrong against a source that is
> higher than this plan: `nova/docs/dev/module-conventions.md:97` — «все
> fallible-операции → `Result[T, XError]`; эффект `Fail` наружу не отдаём».
> `AGENTS.md` («Order of precedence») puts conventions above plans, so the plan is
> what changes.
>
> Found by the owner reading the package, not by any guard — which is itself worth
> noting: nothing here would have caught it. Measured at the time: 18 of 36 exported
> functions took `Fail`, none returned `Result`, and `nova-tls`, `nova-http` and
> `nova-polaris` are all the other way round. This package was the only one of the
> four built that way.
>
> **The one exception, and it is canonical:** `Appender @cleanup` keeps
> `Fail[DuckError]` and calls `@close()!!`. An auto-inserted cleanup has no caller to
> return a `Result` to; D432 §1 (2026-08-04 amendment) makes the throw a direct
> effect of whatever function left the appender unconsumed, so the failure lands in
> that signature instead of vanishing. Identical to `std/fs/fs.nv:326` for `File`.
>
> Trace: `probes/duckdb-facade-uses-fail-not-result/`.

```nova
module duckdb

type OpenOptions value { read_only bool, memory_limit str, threads int, temp_dir Option[str] }
type DuckError | Open(str) | Query(str) | Prepare(str) | Bind(str) | Append(str) | Type(str) | Closed

type Database   { ro value CDbHandle }          // #thread_affine через ffi
type Connection { ro value CConnHandle }
type Statement  { ro value CStmtHandle }
type Appender   { ro value CAppHandle }

fn Database.open(path str, opts OpenOptions) -> Result[Database, DuckError]   // ":memory:" допустим
fn Database.open_memory(opts OpenOptions) -> Result[Database, DuckError]
fn Database @connect() -> Result[Connection, DuckError]
fn Database consume @close() -> ()
fn Database.version() -> str                                              // "v1.5.5"
fn Database.extensions() -> []str                                         // ["core_functions", "icu"] — статически

fn Connection @exec(sql Sql) -> Result[int, DuckError]                        // строк затронуто; sql`…` с параметрами
fn Connection @query(sql Sql) -> Result[QueryResult, DuckError]
fn Connection @prepare(text str) -> Result[Statement, DuckError]
fn Connection @appender(table str) -> Result[Appender, DuckError]
fn Connection @begin() -> Result[(), DuckError]  /  @commit()  /  @rollback()
fn Connection consume @close() -> ()

fn Statement @bind(args []SqlValue) -> Result[(), DuckError]
fn Statement @execute() -> Result[QueryResult, DuckError]
fn Statement consume @finalize() -> ()

fn Appender @row(values []Value) -> Result[(), DuckError]                    // типы проверяются против колонок при первом row
fn Appender @flush() -> Result[(), DuckError]
fn Appender consume @close() -> Result[(), DuckError]                        // flush + destroy

type QueryResult { ro rows int, ro cols []Column }   // named QueryResult, not Result: the
                                                     // conversion above made the collision with
                                                     // std Result visible. The code always used
                                                     // QueryResult; the plan had not caught up.
type Column value { name str, kind LogicalType }
fn QueryResult @row(i int) -> Row
fn QueryResult @iter() -> Iter[Row]
fn Row @int(i int) -> i64 / @bool / @str / @f64 / @timestamp() -> Timestamp / @date() -> Date / @decimal() -> Decimal / @is_null(i int) -> bool
fn Row @get(i int) -> Value                                               // сумма всех типов ниже

type Value | Null | Bool(bool) | I8(i8) | I16(i16) | I32(i32) | I64(i64) | HugeInt(int128) | F64(f64)
           | Str(str) | Blob([]u8) | Timestamp(Timestamp) | Date(Date) | Interval(Duration) | Decimal(Decimal) | Enum(str) | Uuid(Uuid)
type Decimal value { unscaled int128, scale u8 }
```

Правила:

- `Sql` из `std/data/sql.nv` — единственный путь для текста с параметрами; `@prepare(text)`
  принимает строку без параметров-подстановок (плейсхолдеры `?` биндятся отдельно).
- Значения времени: DuckDB хранит микросекунды, Nova `Timestamp` — наносекунды; пакет
  умножает и делит на 1000 без потери (микросекунды нацело в наносекундах); `TIMESTAMPTZ`
  читается как момент UTC, локализация — дело приложения через `TimeZone`.
- `Decimal` не сворачивается в `f64` никогда; приложение решает само.
- `ENUM` в Nova — `str`; при записи через Appender неизвестное значение — `DuckError.Type`.
- Все хендлы `consume`-типы (D131/D133): использование после `close` — ошибка компиляции.

### 4.1. Объём реализации 0.1 — что покрыто и что нет

Пакет **не является полной привязкой DuckDB**. Версия 0.1 отдаёт из Nova законченное ядро и то, что
нужно `claude-limits`; остальное добавляется по мере появления потребителя, минорными версиями, без
пересборки самой библиотеки (статическая библиотека уже содержит всё).

| покрыто в 0.1 | не покрыто (добавляется по запросу) |
|---|---|
| открытие файла и `:memory:`, `OpenOptions` (read-only, память, потоки, temp, ключ шифрования) | остальные параметры конфигурации DuckDB |
| соединения, транзакции `begin/commit/rollback` | пул соединений, многопоточное использование одного соединения |
| `exec`/`query` с параметрами через `sql\`…\``, `prepare` + `bind` + `execute` | пользовательские функции (UDF), замещаемые сканы, прогресс запроса, отмена запроса |
| Appender с проверкой типов по колонкам | потоковое чтение результата чанками (весь результат материализуется) |
| скалярные типы §5: логические, целые до `HUGEINT`, дробные, `DECIMAL`, `VARCHAR`, `BLOB`, `TIMESTAMP`/`TIMESTAMPTZ`, `DATE`, `TIME`, `INTERVAL`, `ENUM`, `UUID` | `LIST`, `STRUCT`, `MAP`, `ARRAY`, `UNION`, `BIT` — `DuckError.Type` с именем колонки |
| расширения `core_functions`, `icu` статически | `parquet`, `json`, `httpfs` и другие расширения; Arrow; загрузка расширений в рантайме (выключена намеренно) |
| `version()`, `extensions()` | интроспекция каталога сверх обычного SQL к `information_schema` и `duckdb_*()` |

Шапка `src/duckdb.nv` и README пакета содержат абзац: «Привязка покрывает ядро DuckDB и потребности
первого потребителя; полный C API не обёрнут; недостающее добавляется по запросу минорной версией».
Запрос на расширение — задача в репозитории пакета с указанием потребителя и функции, а не «на
всякий случай».

## 6. Тесты (`nova test`, in-memory, без файлов и сети)

- открыть/закрыть; `version()` = тег сабмодуля; `extensions()` содержит `core_functions` и `icu`;
- **расширения прилинкованы**: `SELECT date_trunc('hour', TIMESTAMP '2025-09-06 16:07')`,
  `time_bucket(INTERVAL 5 MINUTE, …)`, `TIMESTAMPTZ '…' AT TIME ZONE 'Europe/Moscow'` — работают;
  `INSTALL json` — ошибка, обращения в сеть нет;

  **ПОЛОВИНА ЭТОГО ПУНКТА ПРОВЕРЯЕТСЯ МАШИНОЙ, ВТОРАЯ — РУКАМИ (2026-09-08).**
  Скобка «(автоустановка выключена)» стояла здесь как причина отказа и была
  НЕВЕРНА: `autoinstall`/`autoload` управляют только автоматикой, а явный `INSTALL`
  проходит мимо них. Замерено — он ушёл в сеть и втянул 22 МБ по открытому `http://`
  в процесс. Отказ теперь даёт флаг сборки `-DDISABLE_EXTENSION_LOAD`, и тест
  сверяет ИМЕННО ЭТО сообщение, а не факт какой-нибудь ошибки: тест, которому
  годится любая ошибка, зеленеет на посторонней (так в этом же файле два теста
  зеленели на разборе SQL).

  Вторая половина — «обращения в сеть нет» — машиной НЕ проверяется. Мок `Net`
  здесь не при чём: сеть трогает не Nova, а C-библиотека, мимо любого эффекта.
  Наблюдаемый признак — создаётся ли `~/.duckdb/extensions/...`; сейчас это
  смотрят глазами. Честная проверка требует файлового эффекта в наборе, который
  намеренно не касается диска, — то есть это РЕШЕНИЕ, а не забывчивость, и до тех
  пор пункт помечен как проверяемый руками. `src/duckdb_test.nv` раньше утверждал
  обратное; утверждение снято тем же ходом. [M-duckdb-extension-dir-check]
- строгость типов: строка в `TIMESTAMP`, `200` в `TINYINT`, неизвестный `ENUM` — `DuckError`;
- отображение каждого типа §5 туда и обратно, включая `Decimal(18,3)` без потери и `Timestamp`
  с наносекундами, кратными 1000;
- `sql\`…\`` с параметрами всех `SqlValue`; инъекция через параметр не срабатывает;
- Appender: 100 000 строк за < 1 с; неверный тип колонки — ошибка на первой строке;
  `flush` без `close` — данные видны в том же соединении;
- транзакция: `begin`/`rollback` откатывает Appender и `exec`;
- `#thread_affine`: **обратная проба** — вызов `Connection` из `spawn` даёт `E_THREAD_AFFINE_IN_FIBER`;
- `consume`: обращение после `close` — ошибка компиляции (негативный тест в `neg/`).

## 7. Ступени и приёмка

| ступень | что готово | приёмка (строка прогона) |
|---|---|---|
| **S0** — собирается | сабмодуль по тегу, `build-duckdb.*` на Windows и Linux, `[ffi]` из манифеста, `Database.open`/`query`/`close`, пример 01 | `nova test src` зелёный на обеих ОС; бинарь примера 01 — размер в отчёт (ожидание 45–55 МБ); `ldd`/`llvm-readobj`: CRT статический, DLL DuckDB нет; повторный запуск сборки — no-op по кэшу |
| **S1** — типы и параметры | `types.nv`, `Value`, `Row`, `sqltag.nv`, `Statement` | тесты §6 по типам и параметрам; `date_trunc`/`time_bucket`/`TIMESTAMPTZ` без сети; `~/.duckdb` не создаётся (проверка каталога до/после) |
| **S2** — запись | `Appender`, транзакции, `OpenOptions` с `temp_dir`/`memory_limit`/`threads` | 100 000 строк < 1 с; временные файлы только в `temp_dir`; `rollback` откатывает |
| **S3** — релиз v0.1.0 | README на двух языках, CI с кэшем, теги | CI зелёный с холодным кэшем (время в отчёт) и с тёплым (< 5 мин); `claude-limits` собирается с `duckdb = { git, tag = "v0.1.0" }` |

## 8. Риски

| риск | мера |
|---|---|
| Полная сборка не влезает в лимиты CI по времени или памяти | кэш `native/lib` по ключу; при холодном кэше — отдельный ручной workflow `build-duckdb` с артефактом, обычный CI берёт артефакт |
| Список вендоренных библиотек меняется между версиями DuckDB | `libs-manifest.txt` генерируется сборкой, `[ffi] libs` заполняется из него РУКОЙ, а `scripts/check-libs-manifest.py` сверяет состав И ПОРЯДОК (статический линк разрешает слева направо) и стоит в CI сразу после сборки, до выгрузки артефакта. **До 2026-09-08 здесь стояло «тест сверяет», и такого теста не существовало** — заявление без механизма |
| Конфликт CRT на Windows при переходе на новый MSVC/clang | `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded` закреплён; спайк-проверка импортов в CI (`llvm-readobj --coff-imports` без `vcruntime`/`msvcp`/`ucrtbase`) |
| Nova `Timestamp` в нс vs DuckDB мкс | преобразование в одном месте (`types.nv`), тест на граничные значения |
| `ICU` тянет таблицы локалей (+8–12 МБ) | принято решением владельца; при нужде — пересобрать без `icu` и жить в UTC (флаг сборки) |
| Построчные записи медленные | документация пакета и `claude-limits` пишут через Appender; `exec` одной строки допустим для точечных `UPDATE` |
| Дыры языка/std по дороге (FFI с int128, consume-хендлы, `Sql`-адаптер) | реестр nova `221.1`, без обходов в пакете |
