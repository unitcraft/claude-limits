# Имя экспортированной функции, совпавшее с ИМЕНЕМ ПОЛЯ записи, ломает кодоген вызова

**Приоритет:** К1 (принято чекером, отвергнуто C-компилятором; сборка невозможна,
причина в сообщении не названа).
**Найдено:** 2026-09-08, при написании `server/handlers/snapshot.nv` (claude-limits,
T2.12).
**Номер реестра:** №TBD.

## Класс

Экспортированная функция `handler(...)` вызывается в модуле, где в области видимости
есть запись с **полем** того же имени и fn-типа (`Endpoint { tag int, handler
Handler }`). Кодоген превращает ВЫЗОВ ФУНКЦИИ в косвенный вызов замыкания через
идентификатор, которого в C нет:

```c
void* b = NOVA_CLOS_CALL_ii(handler, (void*)(_nv_tmp_496));
                            ^~~~~~~  error: use of undeclared identifier 'handler'
```

`nova check` при этом зелёный. В настоящем коде это выглядело так (тот же текст
ошибки, только через vtable):

```c
((NovaValue_ServerResponse(*)(void*, NovaValue_Ctx))(((NovaClosBase*)(handler))->fn))
    (((NovaClosBase*)(handler))->env, (void*)(_nv_tmp_7535))
```

— то есть функция-фабрика была разобрана как ЗНАЧЕНИЕ типа `ApiHandler` и вызвана с
собственным аргументом на месте `Ctx`.

Несущий признак — **совпадение с именем ПОЛЯ**, а не с именем функции и не с fn-типом
возврата. Это показывают контроли.

## Проба

```
cd <repos>/claude-limits/probes/exported-fn-named-handler
../../nova.sh check src/exported_fn_named_handler.nv   # -> ok
NOVA_CACHE=0 ../../nova.sh build src/exported_fn_named_handler.nv -o probe.exe   # -> CC-FAIL
```

| форма | отличие от падающей | результат |
|---|---|---|
| `handler(ten)` при поле `Endpoint.handler` | — | **CC-FAIL**, 2 ошибки |
| `make_handler(ten)` | другое имя функции, поле то же | собралось, печатает `15` |
| `handler_plain(10)` | то же имя, аргумент `int`, а не fn-тип | собралось, печатает `15` |
| `handler(ten)` при поле `Endpoint.cb` | переименовано **ПОЛЕ**, функция та же | собралось, печатает `15` |

Последняя строка — решающая: меняется только имя поля, имя функции остаётся
`handler`, и краснота уходит. Обратный прогон с переименованным полем даёт
`15 15 1 15` — все четыре вызова считают правильно.

Промежуточные версии пробы, которые НЕ воспроизвели (полезно тому, кто будет чинить):
функция `handler`, возвращающая `int`; функция `handler`, принимающая fn-newtype и
возвращающая fn-newtype, — но БЕЗ записи с полем `handler` в области видимости. То
есть ни имя, ни fn-типы сами по себе ни при чём.

## Обход, применённый в claude-limits

`server/routes.nv` держит `Endpoint { method, handler ApiHandler }`, и это поле видно
всюду, где импортируется `on`/`route`. Поэтому фабрики хендлеров названы
`snapshot_handler`, `refresh_handler` — не по стилю, а чтобы не совпасть с полем.
Второй возможный обход — переименовать поле; выбран первый, потому что имя `handler`
у поля `Endpoint` читается точнее, чем любая замена.

## Чего проба НЕ утверждает

Не проверено, нужно ли, чтобы поле было именно **fn-типа**. Во всех наблюдениях оно
такое, и косвенный вызов в сгенерированном C намекает, что тип поля участвует в
разрешении, — но контроля с полем-`int` того же имени в пробе нет.
