# Фасад `nova-duckdb` построен на `Fail`, а конвенция требует `Result`

**Найдено:** 2026-09-08, владельцем, при чтении пакета.
**Приоритет:** высокий — это форма публичного API пакета, который вот-вот получит тег.
**Статус:** расхождение подтверждено замером; нужна переделка 18 подписей.

## Замечание владельца

> я посмотрел пакет duckdb, он весь на Fail, но у нас есть конвенция наши пакеты
> и модули писать на Result, если это возможно

## Что говорят источники

**Конвенция — `nova/docs/dev/module-conventions.md:97`, дословно:**

> Конструкторы/parse **fallible**, без default-panicking. **Все fallible-операции
> → `Result[T, XError]`** (R1, D325); **эффект `Fail` наружу не отдаём**
> (throw = `!!`, Option = `.ok()`).

**План 01.4-nova-duckdb.md:133-153 — прямо противоположное**, `Fail[DuckError]` в
каждой подписи фасада:

```
fn Database.open(path str, opts OpenOptions) Fail[DuckError] -> Database
fn Connection @exec(sql Sql) Fail[DuckError] -> int
fn Statement @bind(args []SqlValue) Fail[DuckError] -> ()
...
```

## Замер, а не впечатление

`src/duckdb.nv`: 36 экспортированных функций, из них **18 на `Fail[DuckError]`**;
вхождений `Result[` — **ноль**.

Соседние пакеты, те же команды:

| пакет | `Fail` в фасаде | `Result` |
|---|---|---|
| nova-tls | нет вовсе | да, повсеместно |
| nova-http | один — `Fail[ParseUrlError]` | да, повсеместно |
| nova-polaris | один — `Fail[TimeoutError]` | да, повсеместно |
| **nova-duckdb** | **18 подписей** | **ноль** |

Пакет — единственный из четырёх, кто устроен так.

## Старшинство: чья взяла

`AGENTS.md`, раздел «Changing the language», задаёт порядок: спецификация →
**конвенции в `docs/dev/`** → компилятор → память. План проектной работы в этом
списке НИЖЕ конвенции: он описывает, что делать, а не переопределяет, КАК пишутся
модули. Значит прав владелец, а план 01.4 в этой части ошибочен и правится.

Правило прямо запрещает мне разрешать такое расхождение молча: противоречие
МЕЖДУ источниками сообщается владельцу с цитатами обоих мест. Он его и нашёл
первым — цитаты выше.

## Почему план так написан (моя реконструкция, не оправдание)

Подписи в 01.4 писал я, опираясь на форму, которая читается короче: `Fail`
позволяет `with Fail[DuckError] = |e| {...}` один раз на весь тест и не заставляет
разворачивать `Result` на каждом шаге. Это удобство автора тестов, оплаченное
потребителем пакета: `Fail` в подписи — эффект, который обязан быть обработан
где-то выше, и он расползается по сигнатурам вызывающих. Конвенция запрещает
именно это расползание.

## Дверь

Одна: `Result[T, DuckError]` во всех 18 экспортированных подписях, `Fail` —
только внутри реализации, если он там вообще нужен. `DuckError` уже структурный
sum-тип, менять его не требуется.

Работа не механическая: тесты (`duckdb_test.nv`, 21 тест) написаны через
`with Fail[...]` и переписываются вместе с фасадом. Оценка — вся поверхность
пакета, но без изменения семантики: те же ошибки, другой способ их вернуть.

## Что НЕ делается этой правкой

`@cleanup`-методы, объявленные как `Fail[DuckError]` (`Appender @close`), — там
`Fail` приходит из авто-очистки по D432 §1 амендмент, и это отдельный вопрос:
очистка не имеет вызывающего, которому можно вернуть `Result`. Проверить, чего
требует конвенция для падающей очистки, ДО того как трогать эти подписи.
