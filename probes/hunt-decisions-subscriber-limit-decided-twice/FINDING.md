# Предел подписок решается дважды, на двух стадиях, по двум копиям одного числа

Охота 2026-09-08, трек `oracle`. Запускать из корня репозитория: `sh cmd.sh`.

## КЛАСС

**Одно правило приёма («тридцать третьему — нет») выражено двумя предикатами в двух
модулях, поверх двух копий одного константного числа.** Свойство: два места отвечают на
вопрос «взять этого клиента?» независимо, и согласие между ними держится тем, что оба
раза написали `32`.

## ДВА МЕСТА, ОДИН ВОПРОС

    src/model/store.nv:48
        const MAX_SUBSCRIBERS = 32

    src/model/store.nv:66-75
        export fn subscribe(mut reg Registry) -> int {
            if reg.count() >= MAX_SUBSCRIBERS {
                reg.rejected += 1
                return -1
            }
            ...

    src/server/handlers/events.nv:30
        /// At most this many at once (§3.4). The thirty-third is told no.
        const MAX_SUBSCRIBERS = 32

    src/server/handlers/events.nv:103-104
        export fn opening(reg Registry, last_event_id str) -> Opening {
            if reg.count() >= MAX_SUBSCRIBERS { return Opening.Refused(ApiError.too_many_subscribers()) }

Ни одна из констант не экспортирована — то есть вторая копия не «забыли переиспользовать»,
а единственный доступный способ: дверь закрыта модификатором доступа.

## ЧТО УЖЕ РАСХОДИТСЯ, НЕ ДОЖИДАЯСЬ ПРАВКИ ЧИСЛА

Счётчик отказов ведёт только `subscribe`:

    src/model/store.nv:40
        rejected int        // how many were turned away over the limit, for /api/health

А отказывает по HTTP — `opening`, который `subscribe` не зовёт (`events.nv:151-163`:
ветка `Opening.Refused` строит `problem(...)` и возвращает; ветка успеха тоже не
подписывается). Значит `rejected`, объявленный «для `/api/health`», сегодня считает
нуль всегда, а реальные `503 too_many_subscribers` не считает никто. Поле в
`HealthState`, куда это число должно приезжать, называется `sse_clients`
(`src/server/handlers/health.nv:32`) и означает другое; поля под `rejected` в
`HealthState` нет вовсе.

## ЧТО ЭТО ДАЁТ ПРИ ПЕРВОЙ ЖЕ ПРАВКЕ ЧИСЛА

Правка одной копии даёт одно из двух молчаливых состояний:

* `opening` строже — клиент получает `503`, хотя `subscribe` взял бы его;
* `subscribe` строже — `opening` пропускает, `subscribe` возвращает `-1`, и что при этом
  отдаётся клиенту, не решено НИГДЕ: у `-1` нет обработчика, поток уже открыт
  (`ServerResponse.sse`, events.nv:161).

Требование, `docs/plans/01.3-api.md:313-314` (§3.4):

    Лимит одновременных подписок — 32; 33-я получает `503 too_many_subscribers` с
    `Retry-After: 30`.

Число в плане одно; в коде их два.

## ПОЧЕМУ НЕ ЧИНИТСЯ У НОСИТЕЛЯ

Экспортировать константу из `store.nv` и убрать копию — свести два ЧИСЛА к одному, но не
два РЕШЕНИЯ: предикат «взять?» останется в двух функциях, и `opening` по-прежнему будет
судить о регистре, которым не владеет. Класс — про то, что приём и отказ разнесены по
двум модулям: тот, кто ведёт учёт (`store`), не умеет отвечать HTTP, а тот, кто отвечает
(`events`), не ведёт учёт, и синхронизировать их нечем, кроме внимания.
