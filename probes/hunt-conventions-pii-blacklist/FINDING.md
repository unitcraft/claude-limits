# Чёрный список ПДн-имён у линтера контракта — рукописная копия, и она уже короче нормы

**Трек:** oracle-формы (охота по конвенциям). **КЛЕТКА:** страница и инструменты × конвенция
по API §2.3 и §14.5, конвенция по БД §13.7. **Найдено 2026-09-08 охотником.**

## КЛАСС

**Список, по которому судит инструмент, скопирован руками из нормы — и с этой минуты живёт
своей жизнью.** Свойство шире найденного случая: класс не в четырёх пропущенных именах, а в
том, что у списка нет источника. Конвенция запрещает такую копию прямо, отдельным пунктом, —
и тот же файл линтера в шапке хвастается, что **список маршрутов** он именно поэтому не
хранит, а разбирает из плана. Одно правило, один файл, два противоположных решения.

## Норма, дословно

`docs/conventions/api.md:140-142` (§2.3):

> Проверяемая форма: линтер контракта имеет список запрещённых имён параметров (`email`,
> `phone`, `inn`, `passport`, `*_name`, `person_id`, `user_id`, `token`, `key`…) и валит
> сборку при их появлении с `in: path` или `in: query`

`docs/conventions/api.md:593-596` (§14.5):

> **Один реестр ПДн** (конвенция по БД §13.7) питает все проверки: чёрный список линтера для
> URL (§2.3), класс операции для максимума `limit` (§4.1), признак «ответ содержит ПДн» у
> операции, политику кэша (§9.3), маскирование в логах и экспортах. **Ни один из этих списков
> не ведётся руками отдельно.**

`docs/conventions/database.md:471` (§13.7): «Реестр единственный источник для всех производных
проверок: списка полей, запрещённых в URL, …».

## Решение, дословно

`scripts/lint-openapi.py:43`:

> `FORBIDDEN_PARAM_NAMES = ("email", "path", "token", "account_id")`

и шапка того же файла, `scripts/lint-openapi.py:13-16`:

> WHERE THE ROUTE LIST COMES FROM. Not from a copy kept here: the table in
> `docs/plans/01.3-api.md` section 2 is parsed … **a second list in this file would just
> drift away from the first**.

## Замер (красное и зелёное на одном и том же образце)

```
CONTROL  ?email=
   exit=1   OPENAPI LINT: FAILED
   GET /api/snapshot: parameter `email` in query -- URLs are logged, cached and pasted

GAP      ?user_id= &person_id= &phone= &inn= &last_name= &api_key= and /{user_id}
   exit=0   OPENAPI LINT: clean
   (no parameter reported)
```

Оба файла собраны из `fixtures/openapi/sample.json`, который линтер сегодня зовёт чистым;
разница между ними — только добавленные параметры. Пять имён из списка конвенции
(`phone`, `inn`, `person_id`, `user_id`, `*_name`) и путь `/api/people/{user_id}`,
параметризованный идентификатором субъекта, проходят молча.

## ДВЕРЬ

`scripts/lint-openapi.py:43` — единственное место, где линтер решает, какое имя параметра
запрещено. Дверь есть; **источника у неё нет** — она не выводится ни из чего. Реестра ПДн,
который конвенция называет единственным источником, в дереве тоже нет: греп по
`docs/plans/01.2-storage.md` находит раздел реестра (`§10`), а механизма, который превращал бы
его в этот кортеж, нет ни одного. То есть у одного правила два независимых дома:

1. `docs/conventions/api.md:140-142` — список имён в норме;
2. `scripts/lint-openapi.py:43` — список имён в машине;
3. `docs/plans/01.3-api.md:675` — третья копия, в приёмке: «ни одного параметра из чёрного
   списка конвенции (`email`, `path`, `token`)» — уже отличается от обеих предыдущих.

## ПОЧЕМУ НЕ ЧИНИТСЯ У НОСИТЕЛЯ

Дописать в кортеж `user_id`, `person_id`, `phone`, `inn` — починка ровно тех имён, которые я
назвал. Свойство останется: список по-прежнему рукописный, `*_name` и `passport` он всё равно
не покроет (это шаблон, а не имя), а конвенция §14.5 говорит не «список должен быть полным», а
«ни один из этих списков не ведётся руками отдельно». Через месяц реестр ПДн проекта получит
новую колонку, и четвёртая копия разойдётся так же тихо, как разошлась третья
(`01.3-api.md:675`), — причём именно этот механизм расхождения списков в том же файле уже
назван и решён для маршрутов.

## Воспроизведение

```
sh probes/hunt-conventions-pii-blacklist/cmd.sh
```

`scripts/lint-openapi.py` на них и печатает обе стороны. Дерево не трогает.
