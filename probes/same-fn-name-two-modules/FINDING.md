# Импорт функции ПО ИМЕНИ, когда такое же имя есть в другом модуле, даёт неопределённый символ C

**Приоритет:** К1 (принято чекером, отвергнуто C-компилятором; сборка невозможна).
**Найдено:** 2026-09-08, при написании `server/handlers/config.nv` (claude-limits,
T2.14).
**Номер реестра:** №TBD.

## Класс

Два модуля объявляют функцию с одинаковым именем — **это само по себе работает**:
обе получают разные мангленные символы и считают правильно. Ломается третий случай:
модуль, который **импортирует одну из них ПО ИМЕНИ** (`import b.two.{quote}`).
Вызов в нём генерируется как `nova_fn_quote` — **без манглинга модуля**, — и такого
символа в CU нет:

```
same_fn_name_two_modules.c:1782:12: error: returning 'int' from a function with
    incompatible result type 'nova_str'
 1782 |     return nova_fn_quote(s);
```

Сообщение C сбивает с толку вдвойне: у необъявленной функции C предполагает возврат
`int`, поэтому ошибка выглядит как расхождение ТИПОВ, а не как отсутствующий символ.
В настоящем коде это выглядело так:

```
config_test.c:56624:80: error: passing 'int' to parameter of incompatible type 'nova_str'
    nova_fn_7runtime14string_builder16str_display_spec(_nv_interp_sb_7220, (nova_fn_quote(name)), ...)
```

`grep -c nova_fn_quote` по тому файлу даёт **2** — оба вхождения вызовы, определения
нет ни одного. Рядом в том же файле стоят нормально мангленные имена
(`nova_fn_7runtime14string_builder16str_display_spec`,
`nova_fn_6server6routes3api`), так что дело именно в потере манглинга у этого вызова.

`nova check` при этом зелёный.

## Проба

```
cd <repos>/claude-limits/probes/same-fn-name-two-modules
../../nova.sh check src/same_fn_name_two_modules.nv                       # -> ok
NOVA_CACHE=0 ../../nova.sh build src/same_fn_name_two_modules.nv -o probe.exe   # -> CC-FAIL
```

| модуль | что делает | результат |
|---|---|---|
| `b.two.use_b_control` | зовёт `quote_b` — имя уникально | собралось, печатает `<x>` |
| `a.one.use_a` | зовёт СВОЙ приватный `quote` | собралось, печатает `[x]` |
| `b.two.use_b` | зовёт СВОЙ экспортированный `quote` | собралось, печатает `<x>` |
| `c.three.use_c` | **импортирует `quote` по имени** и зовёт | **CC-FAIL** |

Обратный прогон сделан честно: до добавления `c/three.nv` пакет собирался и печатал
`<x> [x] <x>` — то есть обе одноимённые функции жили рядом и считали каждая своё.
Краснота появилась ровно на добавлении импорта по имени.

## Настоящий случай, для сверки

`src/config.nv` (модуль `claude_limits.config`) держит приватную
`fn quote(s str) -> str` для TOML; `src/server/json.nv` (модуль `server.json`) —
экспортированную `quote` для JSON. Пока их никто не импортировал по имени,
всё собиралось. `src/server/dto.nv` сделал `import ...server.json.{quote, ...}`, и
первый же CU, куда попали оба модуля (`handlers/config_test`), не слинковался.

## Обход, применённый в claude-limits

Приватная `quote` в `config.nv` переименована в `toml_quote` — заодно точнее: она
ставит кавычки без экранирования, как требует TOML, а не как JSON.

## Чего проба НЕ утверждает

Не проверено, важна ли ЭКСПОРТИРОВАННОСТЬ второй функции (в пробе одна приватная,
одна экспортированная — как в настоящем случае) и важна ли одинаковая сигнатура.
Также не проверено, зависит ли это от глубины каталогов: в настоящем случае модули
были на глубине 0 и 1, в пробе — оба на 1.
