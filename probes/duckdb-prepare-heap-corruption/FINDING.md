# `defer { st.finalize() }` на голом consume-биндинге освобождает дважды

**Найдено:** 2026-09-08 01:0xZ, прогоном `./nova.sh test src` после починки сборки.
**Приоритет:** высокий — повреждение кучи, процесс умирает без диагностики.
**Статус:** воспроизведено, доказано в обе стороны, причина названа, дефект МОЙ.

## Носитель

Тесты падали с `exit=-1073740940` (`0xC0000374`, STATUS_HEAP_CORRUPTION) — девять
тестов проходили, десятый убивал процесс. Десятый — первый, где работают
подготовленные выражения.

Соблазн был очевидный и неверный: «падает первый тест, дошедший до тех 32 функций
шима, которые я написал вечером и которые ни разу не исполнялись, — значит виноваты
они». Проверка это опровергла.

## Что показала проба

Зонд, проходящий всю поверхность подготовленных выражений в форме
`consume st = e { ... }` (scope-форма), прошёл ЧИСТО: `prepare`, `param_count`,
`bind`, `execute`, `close`, `finalize` — 1→9, ни одного повреждения. Значит шим
исправен, и различие живёт не в вызовах, а в том, КАК тест связывает значение.

Тест пишет иначе:

```nova
consume st = con.prepare("INSERT INTO t VALUES (?)")
defer { st.finalize() }
```

Проба в обе стороны, одна и та же программа:

| форма | итог |
|---|---|
| с `defer { st.finalize() }` | падение, exit 127, НИ ОДНОЙ строки вывода |
| без него | 1→9 проходит, `got 1757347622000000` — точно записанное значение |

Отсутствие вывода в падающем случае само по себе улика: процесс умирает раньше,
чем `print` успевает вытолкнуть буфер, — так ведёт себя разрушенная куча, а не
исключение.

## Причина

`Statement` объявляет очистку (`src/duckdb.nv:506`):

```nova
export fn Statement consume @cleanup(outcome ScopeOutcome) -> () => @finalize()
```

По D432 (`nova/spec/decisions/02-types.md`) объявление `@cleanup` делает тип
АФФИННЫМ: компилятор сам вставляет вызов очистки на выходных путях. Компилятор
говорит и границу применения — дословно, в диагностике:

> авто-`@cleanup` (D432 §2) ставится ТОЛЬКО на bare-биндинг `consume X = e` с
> ident-паттерном

`consume st = con.prepare(...)` — ровно такой биндинг. Очистка вставляется. А
`defer { st.finalize() }` вызывает `finalize` ЕЩЁ РАЗ. `ddb_stmt_free` не
идемпотентен: `duckdb_destroy_prepare` плюс `free(st)` во второй раз — двойное
освобождение.

## КЛАСС

**Ручная очистка, добавленная поверх автоматической, потому что автор не проверил,
какая из форм связывания её получает.** Формы `consume X = e` и `consume X = e { }`
выглядят почти одинаково и ведут себя противоположно: первая получает авто-очистку,
вторая нет. Я написал `defer` по привычке из языков без аффинных типов, где забыть
освобождение — обычная ошибка, и получил ровно обратную.

Это тот же вечерний класс, но с другой стороны: раньше инструмент отвечал на
вопрос, которого ему не задавали, — здесь Я ответил на вопрос, которого мне не
задавали, и добавил освобождение, которое уже было сделано.

## Дверь

Убрать `defer { st.finalize() }` везде, где биндинг голый: авто-очистка уже там, и
она правильная — она знает про пути выхода, которых `defer` не различает. Три места
в `src/duckdb_test.nv` (строки 172, 262, 280). Там, где нужна привязка ко времени
жизни блока, — scope-форма `consume st = e { ... }`, которая ЯВНО ограничивает
время жизни и авто-очистку не получает.

## Чего эта проба НЕ доказывает

Что `defer { q.close() }` на `QueryResult` безопасен. Он в пробе остался и
падения не дал — но `QueryResult` тоже объявляет `@cleanup` (`duckdb.nv:386`), то
есть форма подозрительна той же самой подозрительностью и уцелела, возможно, лишь
потому, что `ddb_result_free` устроен снисходительнее. Проверять отдельно, а не
считать зелёное доказательством: зелёное здесь означает «не убило сейчас», а не
«освобождено один раз».
