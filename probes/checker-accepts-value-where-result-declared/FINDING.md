# Чекер принял функцию, объявленную `Result[T, E]`, но возвращающую голый `T` — и `throw` без `Fail` в подписи

**Найдено:** 2026-09-08, при переводе фасада `nova-duckdb` с `Fail` на `Result`.
**Приоритет:** высокий — молчаливое принятие, последствие — сегфолт у вызывающего.
**Дом дефекта:** компилятор Nova (чекер), НЕ пакет `nova-duckdb`.
**Статус:** воспроизведено, сужено, моя половина починена; дефект компилятора открыт.

## Что приняла проверка типов

После моей неполной правки функция выглядела так (`src/duckdb.nv`, было):

```nova
export fn QueryResult @value(row int, col int) -> Result[Value, DuckError] {
    if @is_null(row, col) { return Ok(Value.Null) }
    ...
    match @column(col).kind {
        LogicalType.Boolean => { ...; Value.Bool(v != 0) }      // голый Value
        LogicalType.TinyInt => Value.Int(@read_i64(r, c)?)      // голый Value
        ...
        LogicalType.Uuid => throw DuckError.Type("...")          // throw без Fail
    }
}
```

Одновременно нарушены **две** вещи:

1. подпись обещает `Result[Value, DuckError]`, а хвостовое выражение — `Value`;
2. в теле есть `throw`, а эффекта `Fail` в подписи НЕТ.

`./nova.sh check src` ответил: **`PASS: 5 FAIL: 0`**.

## Что из этого вышло

Вызывающий читает `Result`-образное значение там, где лежит `Value`-образное.
Разные размеры и раскладка → мусор → `0xC0000005` (обращение по недопустимому
адресу) на первом же тесте, **до** первой печати: буфер stdout не успевает
сброситься, поэтому падение выглядит как «ничего не произошло».

## Сужение (чтобы дефект не искали заново)

Проба шла шагами, каждый следующий отсекал половину:

| проба | итог |
|---|---|
| открытие + `exec` на `Result`-форме | чисто |
| `with_db` (обёртка) с телом-константой | чисто |
| `query` + `close`, без чтения значения | чисто |
| `query` + `r.value(0,0)!!` | **падение** |

Отсюда и нашлась настоящая причина — не `!!`, не `close`, не авто-очистка, а
несовпадение объявленного и фактического типа возврата у `@value`.

## Почему это дефект компилятора, а не только моя ошибка

Моя ошибка — неполная правка, и она починена. Но НАЙТИ её должен был чекер: обе
нарушенные вещи проверяемы статически и обе относятся к тому, что этот язык
проверяет специально. Эффект `Fail` объявлен строго транзитивным и обязательным в
подписи везде, где может произойти (`spec/decisions/04-effects.md` D65; обзор
`spec/effects.ru.md`) — здесь он произошёл и в подписи не появился.

Особенно важно, что молчание было ПОЛНЫМ: ни ошибки, ни предупреждения. Правка,
меняющая тип возврата у половины файла, прошла проверку и упала в исполнении —
то есть проверка типов в этом случае не даёт того, ради чего её запускают.

## Второй носитель того же вечера, тем же способом найденный

`q.value(0, 0).is_null()` — где `value` уже возвращал `Result`, а `.is_null()`
принадлежит `QueryResult`. Чекер принял; генератор привязал вызов к
`Nova_QueryResult_method_is_null` и передал ОДИН аргумент вместо трёх, что
поймал уже сишный компилятор:

```
duckdb_test.c:31589: error: too few arguments to function call, expected 3, have 1
```

То есть разрешение метода на `Result` молча ушло к методу чужого типа. Разные
проявления, общий корень: **`Result` в позиции значения не проверяется как
`Result`.**

## Что нужно от компиляторного окна — воспроизведение ПРОВЕРЕНО

`probe.nv` рядом, четырнадцать строк, DuckDB не нужен:

```nova
type ProbeError | Bad(str)

fn f() -> Result[int, ProbeError] {
    throw ProbeError.Bad("no Fail in the signature")
}

fn g() -> Result[int, ProbeError] => 42
```

Запущено 2026-09-08 в `nova-duckdb`:

```
$ ./nova.sh check src/probe_chk.nv
ok: src/probe_chk.nv
PASS: 1  FAIL: 0
```

Обе ошибки прошли МОЛЧА — ни ошибки, ни предупреждения. Это не реконструкция по
памяти и не вывод из большого файла: меньше этого примера уже не сделать.

Попутно и в пользу компилятора: первая версия пробы называла тип `E`, и это было
отклонено тремя точными диагностиками (`E_TYPE_NAME_TOO_SHORT` и две про
затенение параметров обобщений в std). То есть чекер внимателен к именам типов и
молча пропускает несовпадение типа возврата — дыра точечная, а не «проверка
выключена».

Строку реестра заводит то окно, которое чинит: дом дефекта — репозиторий
компилятора, здесь улика и способ повторить.

## Чего я НЕ проверял

Ведёт ли себя так же `novac` (самохостящийся компилятор). Проверялся только
нынешний. Если там та же дыра — это одна причина на два компилятора, и знать это
до починки полезнее, чем после.
