# Windows: аргументы и окружение приходят в ANSI, а живут как UTF-8 `str`

**Замер 2026-10-02, 00:35.** Реестр 221.1 **№1590**, К1 (номер дал интегратор 00:37). Найдено приёмкой T4.3
(агент прошёл README; первый запуск в каталоге с кириллицей упал), подтверждено чисто — без
оболочки, через Python и `CreateProcessW`.

## Как запускать

Каталог — пакет `hcap`: `nova.toml.txt` → `nova.toml`, `u1_args_env.nv.txt` →
`u1_args_env.nv`, `nova build u1_args_env.nv -o u1.exe`, затем ИМЕННО из Python (оболочка
cp1251/msys испортит текст раньше программы): `python u1run.py.txt u1.exe`.

## Замер (nova main bacdefa12)

| что | ожидается (UTF-8 «Евг») | получено |
|---|---|---|
| `std.os.args()[1]` | `d095d0b2d0b3`, len 6 | **`c5e2e3`, len 3** — cp1251 |
| `std.os.env("U1_PROBE")` | `d095d0b2d0b3`, len 6 | **`c5e2e3`, len 3** — cp1251 |
| `std.fs` `write_text`/`read_text` файла `u2_Евг.txt` (имя — литерал исходника) — третья клетка, по просьбе интегратора | файл с этим именем на диске, чтение возвращает записанное | **верно**: `write ok`, `read u2 payload`, на диске `u2_Евг.txt` (`u2_fs_name` + `python u2run.py.txt u2.exe`) |

Файловая система идёт через широкие API; портятся только ВХОДЫ из ОС — командная строка и
окружение.

## Что ломается в claude-limits

`--serve` с каталогом данных или настроек под путём с кириллицей: путь превращается в
`U+FFFD`, файлы не создаются, и старт падает с ложным «no database key at
…\ufffd\ufffd…\cfg\claude-limits.key». Тот же запуск с ASCII-каталогом проходит
(`scratchpad/loop/cyrrun.py`, контроль). У владельца профиль `C:\Users\<кириллица>`, то
есть пути по умолчанию (`LOCALAPPDATA`) — ровно этот случай.

Исправлять — в std/рантайме nova (широкие API Windows). В claude-limits обхода нет: перевод
ANSI → UTF-8 требует знать кодовую страницу машины, и это работа рантайма, а не каждой
программы.
