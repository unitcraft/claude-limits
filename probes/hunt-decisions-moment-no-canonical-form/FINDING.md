# У момента времени нет канонической записи: правило есть, производителя нет

Охота 2026-09-08, трек `oracle`. Запускать из корня репозитория: `sh cmd.sh`.

## КЛАСС

**Требование «момент на проводе — ISO 8601 в UTC с `Z`» записано, а функции, которая
его производит, в дереве нет ни одной.** Свойство: граница между внутренним
представлением момента (`int`, миллисекунды unix) и внешним (`str`) пересекается без
единого преобразователя, и каждый будущий поставщик состояния перейдёт её своими
словами.

Это второй вид находки из брифа: требование записано, механизма нет. И это не «ещё не
дошли руки»: тип, который ЗАКРЕПЛЯЕТ пропуск, уже написан и уже принят приёмкой.

## ТРЕБОВАНИЕ

`docs/plans/01.3-api.md:37-40` (§0):

    - **Время** — ISO 8601 строго в UTC с суффиксом `Z` (`2026-09-06T18:10:00Z`): смещений в ответах нет,
      эндпоинт Anthropic отдаёт смещение, бэкенд переводит в UTC при разборе; пояс бэкенда для подписей —
      поле `tz` (IANA) в `/api/snapshot`; страница считает оси в поясе браузера.

`docs/conventions/api.md` §5.3 требует того же на входе: «формат (UUID v7, **ISO 8601 с
`Z`**, десятичная строка)».

## ВХОДНАЯ ПОЛОВИНА СДЕЛАНА, ВЫХОДНОЙ НЕТ

Вход — одна дверь, и она есть:

    src/usage/parse.nv:102-106
        export fn moment_ms(iso str) -> int =>
            match iso.to_timestamp() {
                Ok(t) => t.unix_millis() as int
                Err(_) => 0
            }

Внутреннее представление — целое:

    src/window.nv:32          resets_at_ms int    // 0 when unknown
    src/model/store.nv:136    polled_at_ms int
    src/model/store.nv:146    fetched_at_ms int

Внешнее — голая строка, без конструктора и без проверки:

    src/server/dto.nv:204-205     fetched_at str    next_poll_at str
    src/server/dto.nv:141-142     polled_at str     next_poll_at str
    src/server/dto.nv:186         resets_at str
    src/server/dto.nv:155         runs_out_at str
    src/server/handlers/exporter.nv:34,42   at str   resets_at str

Между ними — ничего. Во всём `src/` нет ни одной функции, возвращающей ISO-строку:
`grep -rn "to_iso\|Z\"" src --include=*.nv` вне тестов даёт ровно одно попадание —
`format.nv:48`, где `date().to_iso()` используется как КЛЮЧ СРАВНЕНИЯ двух дат, а не
как выход. Ближайший сосед по смыслу, `model/format.nv`, владеет человеческими
подписями (`reset_caption`, `duration_words`) и о машинной записи не знает.

## ЧТО ЭТО УЖЕ ЛОМАЕТ, НЕ ДОЖИДАЯСЬ ПОСТАВЩИКОВ

Тег снимка хеширует эту непроверенную строку:

    src/server/handlers/snapshot.nv:199
        ro tag = etag_of([view.fetched_at, st.config_etag, flag])

Две записи одного момента (`...T16:47:02Z` и `...T16:47:02.000Z`, или со смещением
`+00:00`) дают разные теги при одинаковом теле — то есть `304` перестаёт работать
ровно тогда, когда поставщик сменит написание. Канонизация тут была бы бесплатной и её
нет, потому что канонизировать нечем.

## ПОЧЕМУ НЕ ЧИНИТСЯ У НОСИТЕЛЯ

Носителя ещё нет — в этом и класс. Первый поставщик состояния (файбер `store`, T2.9/Ф.2)
напишет форматирование у себя; второй (восстановление из базы, `restored: true`,
§3.3) — у себя; третий (экспорт, где момент уходит и в CSV, и в JSON) — у себя.
Починка «у носителя» после этого означает три правки и сверку глазами; сейчас это
одна функция и один тип.
