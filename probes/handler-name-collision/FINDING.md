# Находка: функция пользователя с именем `handler` ломает типизацию ВНУТРИ polaris

**Дата:** 2026-09-08. **Нашлось** при написании спайка T0.4: пакет, зависящий от
`polaris`, объявил у себя `fn handler(req ServerRequest, mut st State) -> ServerResponse`
— и сборка упала внутри чужого файла.

**Класс:** имя верхнего уровня из ПОТРЕБИТЕЛЯ влияет на разрешение имени внутри
ЗАВИСИМОСТИ. Родня по механизму — окно W6 реестра («резолв по ОБЪЯВЛЕНИЮ, а не по
строке»).

## Замер

```sh
cd probes/handler-name-collision
NOVA_CACHE=0 ../../nova.sh build src/main.nv
```

```
nova-polaris/src/serve/serve_tls.nv:92:70: error: [E7301] cannot pass `fn(..)`
as argument `handler` of type `fn([]u8) -> ServerResponse`
 92 |    ro _ = handle_connection_tls(tls_stream, handler)
note: parameter `handler` declared here --> src/net/servernet_tls.nv:44:59
```

## Контроль — ОДНО переименование, больше ничего

`fn handler(...)` → `fn my_handler(...)`. Ни вызов, ни тип, ни импорты, ни манифест не
трогались:

```
built: D:\...\probes\handler-name-collision\main.exe (19.53s)
```

**Функция ни разу не вызывается.** Достаточно её ОБЪЯВИТЬ.

## Что было исключено по дороге (и это половина работы)

Прежде чем найти имя, я проверил и снял четыре версии — каждую сборкой, а не
рассуждением:

| гипотеза | как снята |
|---|---|
| замыкание захватывает изменяемое состояние | заменил обработчик на замыкание без захвата — падает по-прежнему |
| `mut`-параметр у `build_router` | убрал — падает по-прежнему |
| секция `[ffi]` и `extern "C"` в пакете | убрал обе — падает по-прежнему |
| раскладка пакета (`src/`, `[lib] src`) | перенёс заведомо рабочий исходник соседнего спайка в ЭТОТ пакет — собирается |

Последний пункт и развернул поиск: раз чужой исходник в моём пакете собирается,
причина в моём коде. Дальше — дифф и перенос кусков по одному; сломало добавление
именованной функции, а переименование починило.

**Одна из проверок была испорчена мной:** срез манифеста по строке `[ffi]` попал в
слово `[ffi]` внутри КОММЕНТАРИЯ и разрезал прозу, отчего пропала секция
`[dependencies]` и отказ сменился на «polaris не найден». Переделал построчно по
заголовку в нулевой колонке. Якорь правки должен быть уникален — иначе снимаешь не тот
замер.

## Почему это дороже, чем выглядит

`handler` — первое имя, к которому тянется рука при написании веб-сервиса. Отказ
приходит из файла, который пользователь не открывал, и указывает на строку, которую он
не может исправить. Совет «переименуйте свою функцию» получить неоткуда: в сообщении
нет ни слова о том, что виновато имя.

## Границы

- Замерено на Windows, clang, `nova` из `main` `c25e765f5`, `polaris` v0.1.7
  (`e67815c1c`).
- Не проверено: другие имена, совпадающие с параметрами внутри зависимостей
  (`req`, `stream`, `policy`); ломает ли то же самое ТИП с именем `handler`;
  повторяется ли на других пакетах, кроме polaris.
- Номер реестра НЕ взят: номера выдаёт интегратор. Это ПЯТАЯ находка окна после
  №1033, №1036, №1037 и `option-consume-in-tuple`.

## Строка реестра: №1050

Номер выдан интегратором 2026-09-08 для `nova/docs/plans/221.1-bug-sweep.md`.

**Строка НЕ является вторым замером этой пробы.** В ней прямо сказано: «прочитал отчёт и сверил цитаты с файлом, но САМ ПРОБУ НЕ ЗАПУСКАЛ». Вердикт «блокирует тег» тоже отложен: число блокеров — это мера расстояния до релиза, и двигать её чужим замером нельзя ни вверх, ни вниз.
