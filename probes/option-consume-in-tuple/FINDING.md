# Находка: `Option[T]` с `consume`-типом внутри КОРТЕЖА ломает кодогенерацию

**Дата:** 2026-09-08. **Нашлось** в задаче T1.4: `src/accounts/login.nv` объявлял
`fn read_login(...) -> (Login, Option[Token])`, где `Token` — `consume`-тип.

**Класс:** `Option` от `consume`-типа эмитится в C в УКАЗАТЕЛЬНОЙ форме (`..._p`), а
машинерия кортежей этого не знает: ссылается на неё раньше объявления и кастует в
беcуказательное имя.

## Два симптома, и появляются они в разные моменты

**(1) Достаточно ОБЪЯВИТЬ** такую функцию — вызывать не нужно. `typedef` кортежа
эмитится РАНЬШЕ типа `Option`, на который ссылается:

```
main.c:430:80: error: unknown type name 'NovaOpt_Nova_Secret_p'
 430 | typedef struct _NovaTuple_2_8_nova_str_21_NovaOpt_Nova_Secret_p
       { nova_str f0; NovaOpt_Nova_Secret_p f1; } _NovaTuple_2_8_...;
```

при том что само имя определено НИЖЕ, на `:509`:

```
 509 | typedef struct NovaOpt_Nova_Secret_p { Nova_Secret* value; } NovaOpt_Nova_Secret_p;
```

**(2) Разбор кортежа** добавляет вторую ошибку — каст по значению против
указательного typedef:

```
main.c:5612:64: error: expected expression
 5612 |     NovaOpt_Nova_Secret_p _nv_scr_499 = (*(NovaOpt_Nova_Secret*)(got.f1));
```

В настоящем случае компилятор сам назвал разлад: «`use of undeclared identifier
'NovaOpt_Nova_Token'; did you mean 'NovaOpt_Nova_Token_p'?`».

## Изоляция — УДАЛЕНИЕМ, а не догадкой

| половина | форма | итог |
|---|---|---|
| контроль 1 | `fn -> Option[Secret]` | **собирается**, печатает `control 1, bare Option: x` |
| контроль 2 | `fn(body fn() -> Option[Secret]) -> Option[Secret]` | **собирается**, печатает `control 2, through a closure: x` |
| под тестом | `fn -> (str, Option[Secret])` | **падает**, симптом (1) |

**Первая гипотеза была неверна, и я снял её пробой, а не рассуждением.** Я решил, что
дело в объявленном типе возврата ЗАМЫКАНИЯ, — та проба собралась и отработала. Убрал
замыкание, оставив кортеж: падает по-прежнему. Значит замыкание ни при чём.

Оба контроля остаются в файле намеренно: без них отказ читается как «Option от
consume-типа не поддержан», а это неправда.

```sh
cd probes/option-consume-in-tuple
NOVA_CACHE=0 ../../nova.sh build src/main.nv        # красное, симптомы (1) и (2)
# убрать функцию pair и её использование -> собирается, оба контроля печатают
```

## Кэш сборки чуть не испортил замер, и это отдельный урок

Первый контрольный прогон сказал «`build cache hit — reusing generated C`» — то есть
судил C ПРЕДЫДУЩЕЙ удачной сборки, а не отредактированный исходник, и показал ошибку,
которой в новом коде могло уже не быть. Все выводы выше сняты с `NOVA_CACHE=0`.
Ключ кэша — `build_cache::compute_c_key` (`nova-cli/src/main.rs:5171`), выключатель —
`NOVA_CACHE=0` (`build_cache.rs:46`).

## Что сделано в плане 01

`read_login` больше не возвращает кортеж: описание логина и токен приходят двумя
разными вызовами (`read_login` и `read_token`). Это не только обход — это лучше по
существу: вызывающий, которому нужно ТОЛЬКО показать учётку, теперь физически не
получает токен, а раньше получал его в кортеже и обязан был потребить.

## Границы

- Замерено на Windows, clang, `nova` из `main` `c25e765f5`.
- Не проверено: запись (`type X { f Option[Consume] }`) вместо кортежа, кортеж без
  `Option` вокруг consume-типа, кортеж из трёх и более элементов.
- Номер реестра НЕ взят: номера выдаёт интегратор. Это ЧЕТВЁРТАЯ находка окна после
  №1033, №1036, №1037.
