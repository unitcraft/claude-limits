# `nova check` принимает КВАЛИФИЦИРОВАННУЮ ссылку на константу модуля — и существующую, и выдуманную

**Приоритет:** К1, и с отягчающим: страдает не сборка, а **доверие к зелёному
`check`**. Форма, которую чекер принимает, не компилируется вообще — ни с
существующим именем, ни с несуществующим.
**Найдено:** 2026-09-08, при сборке пакета `nova-duckdb` (claude-limits, T2.1).
**Номер реестра:** №TBD.

## Класс

Обращение `module.CONST` к константе импортированного модуля:

* **`nova check` — зелёный** и для константы, которая есть, и для имени, которого в
  модуле нет вовсе;
* **кодоген выдаёт `module->CONST`**, то есть разбирает ИМЯ МОДУЛЯ как переменную:

```
check_accepts_missing_module_member.c:5444:13:
    error: use of undeclared identifier 'consts'; did you mean 'const'?
 5444 |     return (consts->REAL);
```

Вторая половина острее первой. Для `consts.THIS_CONSTANT_DOES_NOT_EXIST` в модуле
нет вообще ничего, к чему можно было бы привязать имя, — и чекер всё равно
молчит. То есть **зелёный `check` не доказывает, что квалифицированная ссылка на
член модуля разрешается**.

Функции через тот же префикс (`ffi.ddb_open(...)`) работают: они компилируются в
`nova_fn_...`. Ломаются именно КОНСТАНТЫ.

## Проба

```
cd <repos>/claude-limits/probes/check-accepts-missing-module-member
../../nova.sh check src/check_accepts_missing_module_member.nv     # -> ok (это и есть дефект)
NOVA_CACHE=0 ../../nova.sh build src/check_accepts_missing_module_member.nv -o probe.exe
```

| форма | `nova check` | сборка |
|---|---|---|
| `REAL`, импортированная ПО ИМЕНИ (`import …consts.{REAL}`) | ok | **собралось, печатает `1`** |
| `consts.REAL` — квалифицированная, константа СУЩЕСТВУЕТ | ok | **FAIL**: `consts->REAL` |
| `consts.THIS_CONSTANT_DOES_NOT_EXIST` — константы НЕТ | ok | **FAIL**: то же |

Обратный прогон: убрал обе квалифицированные формы — собралось и напечатало `1`.
Значит рабочая форма ровно одна: импорт по имени.

**Поправка к первой редакции этой пробы.** Сначала я назвал `consts.REAL`
контролем — и он упал вместе с «падающей» формой. Контроля у меня в тот момент не
было; настоящим контролем оказался импорт по имени. Записано так, а не подогнано,
потому что «контроль тоже красный» — это находка, а не помеха.

## Чем это стоило доверия

Весь пакет `nova-duckdb` я писал, отчитываясь «`nova check` зелёный». В `src/ffi.nv`
при этом **не было объявлено ни одной константы `DDB_T_*`**, а `src/types.nv`
ссылался на `ffi.DDB_T_BOOLEAN` и ещё 22 таких имени — и check был зелёный. Дефект я
нашёл не чтением и не проверкой, а тем, что дошёл до первой настоящей C-компиляции.

Вывод для отчётов, не только для реестра: **«`nova check` зелёный» — свидетельство
слабее, чем я его подавал.** Оно не покрывает квалифицированные ссылки на члены
модулей. Для пакета с FFI единственное настоящее доказательство — сборка.

## Обход

Импортировать константы ПО ИМЕНИ (`import mod.{CONST_A, CONST_B}`) и писать их
голыми. Применено в `nova-duckdb` тем же слиянием.

## Чего проба НЕ утверждает

Не проверено, ведут ли себя так же квалифицированные ссылки на ТИПЫ (`mod.Type`) —
в пакете они используются (`ffi.CDbHandle` в объявлениях полей) и до C-компиляции
дошли, но отдельного контроля на это в пробе нет.
