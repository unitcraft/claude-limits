# Находка: TOML-парсер std расплющивает секции в корень

**Дата:** 2026-09-08. **Нашлось** в задаче T1.2: `config.nv` читал
`[poll] interval_sec = 10` и не находил его.

## Замер

```sh
cd probes/toml-sections
../../nova.sh build src/main.nv && ./main.exe
```

Вход:

```toml
schema = 1
[[folders]]
path = "~/.claude"
[poll]
interval_sec = 10
```

Выход:

```
root keys:
  path = <str>
  folders = <table>
  interval_sec = <int>
  schema = <int>
  poll = <table>
```

**Два разных нарушения в одном замере:**

1. `interval_sec` и `path` оказались в КОРНЕ, а не внутри своих секций. Секция
   создаётся пустой таблицей, а её ключи уходят наверх.
2. `[[folders]]` дало `<table>`, а не `<array>`: массив таблиц не отличается от
   таблицы.

## Это не догадка по комментарию

В `std/src/encoding/toml.nv:466` действительно стоит `TODO: nested path resolution`,
а на строке 455 — «Упрощённо: для bootstrap-stdlib просто insert empty table».
Комментарий говорит о намерении; замер выше говорит о поведении, и я привожу второе.
Шапка модуля при этом обещает обратное: «Tables `[section]` и `[[array of tables]]`»
(строка 10) — то есть документация модуля расходится с его кодом.

## Что это значит для плана 01

Файл настроек — **один TOML с секциями** (01.2 §2.1, решение 12 плана 01), и ни один
ключ приложения не лежит в корне, кроме `schema`. На std-парсере файл настроек
прочитать НЕЛЬЗЯ: `poll.interval_sec` и `server.port` пришли бы как корневые
`interval_sec` и `port`, а два ключа с одинаковым именем в разных секциях
(`enabled` есть и у `forecast`, и у `widget`) затёрли бы друг друга молча.

**Решение в T1.2:** `config.nv` читает нужное подмножество TOML сам — секции,
массивы таблиц, строки, числа, булевы, массивы строк, комментарии. Это не «свой
TOML вместо стандартного», а обход измеренного дефекта; в коде он помечен, и когда
std научится, читатель уходит.
