# Тег считается не по всем осям, по которым тело меняется — и это правило кода, применённое один раз из двух

Охота 2026-09-08, трек `oracle`. Запускать из корня репозитория: `sh cmd.sh`.

## КЛАСС

**`ETag` обязан различать всё, что различает ТЕЛО; список осей нигде не записан, и
берётся он на глаз при каждом вызове `etag_of`.** Свойство: любая новая ось вариации
представления (уровень раскрытия, флаг запроса, язык, будущий `?fields=`) по умолчанию
в тег НЕ входит, и последствие — `304` на изменившееся тело — не отличимо от
правильной работы.

Класс формулируется свойством, а не именем поля: сегодня недостающая ось —
`Disclosure`, но механизм её пропуска общий.

## ГДЕ РЕШАЕТСЯ

Хеш — одна дверь, и она правильная:

    src/server/etag.nv:29-35
        export fn etag_of(parts []str) -> str {

СОСТАВ частей — не решается нигде, он подставляется на месте вызова:

    src/server/handlers/snapshot.nv:196-199
        // `include_hidden` is IN the tag: without it a client that asked once
        // with and once without would be told 304 and shown the other answer.
        ro flag = if hidden_too { "1" } else { "0" }
        ro tag = etag_of([view.fetched_at, st.config_etag, flag])

    src/server/handlers/config.nv:87
        export fn tag_of(text str) -> str => etag_of([text])

Комментарий на строках 196-197 — это ТОЧНАЯ формулировка правила: «ось, по которой
тело различается, обязана быть в теге». Правило названо, применено к одной оси
(`include_hidden`) и не применено ко второй, стоящей на той же строке кода:

    src/server/handlers/snapshot.nv:205
        ro body = render_snapshot(view, st.disclosure)

`st.disclosure` меняет тело — `dirs[].path` становится `null`
(`src/server/dto.nv:57-63`, `dto.nv:216-217`) — и в тег не входит.

Требование, которое этим держится, `docs/plans/01.3-api.md:548-549` (§4):

    dto.nv         типы ответов/запросов (serde JSON); один источник для страницы, виджета и OpenAPI;
                   сериализация в LAN обнуляет поля класса pii-path (dirs[].path, config.path, …)

и `docs/plans/01.3-api.md:276` (§3.3): «`dirs[].path` в LAN-режиме — `null` … на loopback —
полный путь».

## КАК ЭТО СРАБАТЫВАЕТ

Слушатель переоткрывается при смене `server.bind`/`allow_lan` — это предусмотрено
самим планом (`docs/plans/01.3-api.md:465-466`, `"listener_reopened": true`). Клиент,
получивший снимок с путями до переоткрытия и запросивший его после с
`If-None-Match: <тот же тег>`, получит `304`: `fetched_at` и версия конфига в теге
есть, а уровень раскрытия — нет. Клиент останется с телом, содержащим пути, которые
ему уже нельзя показывать; §3.3 нарушено, и нарушено молча.

То же в обратную сторону: `304` от `GET /api/config` (`config.nv:583`,
сравнение с `st.etag` — хешем ТЕКСТА ФАЙЛА) не различает loopback и LAN вовсе,
хотя `render_state` подставляет `pii_path(st.disclosure, "path", st.path)`
(`config.nv:183`).

## ПОЧЕМУ НЕ ЧИНИТСЯ У НОСИТЕЛЯ

Дописать четвёртую часть в `etag_of([...])` на строке 199 — закрыть один вызов из двух;
у `config.tag_of` (config.nv:87) состав частей вообще фиксирован сигнатурой (`[text]`),
и уровень раскрытия туда не добавить, не меняя её. Списка осей нет ни в `etag.nv`, ни в
`dto.nv`, ни в `Ctx`; пока его нет, каждый новый условный ответ решает состав заново, и
ошибка выглядит как исправная работа кэша.

## ЧТО ЭТО НЕ

Не «`no-store` всё спасёт»: `Cache-Control: no-store` запрещает ХРАНИТЬ ответ
посредникам, а `304` считается по тегу, который держит сам клиент, и на него запрет
хранения не влияет — иначе не было бы и смысла в `include_hidden` внутри тега.
